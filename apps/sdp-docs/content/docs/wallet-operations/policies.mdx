title: Wallet policies
description: Wallet controls, operation permissions, and policy audit visibility.
---

A **wallet policy** constrains how a custody wallet can move funds and execute supported operations. SDP starts from default allow, then applies the wallet's active control profile: an ordered list of rules plus a default action. Policies are managed via `GET` and `PUT` on `/v1/payments/wallets/{walletId}/policies` and enforced before each wallet operation executes.

In these paths, `walletId` is the provider wallet ID: the `walletId` field returned by `GET /v1/wallets`, such as `privy_wallet_123`. The SDP wallet `id` (`cwlt_…`) and the wallet's public key are not accepted here.

Use policies for treasury wallets, automated payout wallets, or any custody wallet where unbounded outbound flow would be a liability.

## Default allow and active controls

Wallet policy evaluation starts from default allow. If no wallet control profile exists, supported wallet operations continue to run unless another product-specific check rejects them. When you activate a control profile, SDP evaluates its rules first and returns the resulting `decision` as one of `allow`, `deny`, `approval_required`, `provider_approval_required`, `review`, or `not_evaluated`.

When a request is made with an API key, SDP also evaluates that key's [API-key policy](/docs/wallet-operations/api-key-policies), if it has one, and applies the stricter of the two decisions.

The `controlProfile` object shows the active immutable revision. Treat `revisionId` and `revisionNumber` as audit references: a policy evaluation records which revision was active when the wallet operation was checked.

### Dashboard actions

The dashboard authoring flow exposes three actions: **Allow**, **Deny**, and **Require approval**. Choose **Require approval** when an operator must decide whether an operation can continue; it holds the operation and creates an [approval request](/docs/wallet-operations/approvals).

`review` is the result SDP returns when a rule cannot be evaluated safely: for example an `operation_family`, `operation_type`, or `asset` rule with no values, a `destination` rule with no addresses, an `amount` rule with neither `min` nor `max`, or a `velocity` rule whose window total could not be read. The API also accepts `review` as a rule `action` or a `defaultAction`, but it is not a dashboard authoring option. A `review` decision holds the operation and creates an approval request, like `approval_required`, but the evaluation records `requiresApproval: false`. Treat `review` as a sign that a rule needs fixing. Do not use it to model operator approval; use `approval_required` instead.

## Rule kinds

A control profile revision is an ordered list of rules. Each rule either abstains or contributes a decision; the strictest matched decision wins and the revision's `defaultAction` applies when nothing matches. For every kind except `velocity`, `action` is the decision a match produces.

| Kind | Matches | Fields |
| --- | --- | --- |
| `operation_family` | Operations in the named families. | `family`, `families` |
| `operation_type` | Operations of the named types. | `operationType`, `operationTypes` |
| `asset` | Operations moving one of the named mints. | `asset`, `assets` |
| `destination` | Destinations on the allowlist, or off the blocklist. | `allowlist`, `blocklist`, `destination`, `destinations` |
| `amount` | A single operation's amount inside `[min, max]` for the named mints. Outside the bounds the rule denies. | `min`, `max`, `asset`, `assets` |
| `velocity` | The rolling sum of prior operations plus this one exceeds `max` for the named mints. | `scope`, `window`, `max`, `asset`, `assets`, `operationTypes` |
| `approval` | Selectors match; holds the operation for an approval group. | `families`, `operationTypes`, `assets`, `approvalGroupId` |
| `always` | Every operation. | none |

### Velocity limits

A `velocity` rule caps volume over a rolling window instead of per operation:

```json title="velocity-rule.json"
{
  "id": "daily-usdc-transfers",
  "kind": "velocity",
  "scope": "organization",
  "window": "P1D",
  "max": "100000",
  "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
  "operationTypes": ["payment_transfer_execute"],
  "action": "approval_required"
}
```

- `scope` chooses whose history counts: `wallet` (default), `organization`, or `api_key`.
- `window` is an ISO 8601 duration using days, hours and minutes (`PT1H`, `P1D`, `P1DT12H`). Weeks, months, years and seconds are rejected.
- `max` is a UI-unit decimal string in the asset's units. Like `amount`, the rule must name at least one mint.
- The window sums every decided, non-failed, non-canceled wallet operation for the scope and mint, optionally narrowed by `operationTypes`. Operations still awaiting their own policy decision do not count, so concurrent requests never block each other.
- `action` is the decision **on breach** (default `deny`). Within the limit the rule abstains rather than allowing, so a velocity rule never overrides a stricter rule beside it. Set `action: "approval_required"` to route outliers into the approval flow instead of refusing them.
- A `Dry-Run: true` request reports the velocity verdict against current history without recording anything.

## Operation permissions

Wallet policies can match operations at two levels:

- **Operation family** rules apply to every evaluated operation in a broad product area.
- **Operation type** rules match one exact operation identifier and take precedence when you need a narrower decision.

These are wallet-policy selectors, not API-key permissions. API-key permissions such as `payments:write` and `tokens:write` determine whether a caller may invoke an endpoint; operation permissions determine what the selected wallet may do after the request is authorized. The wallet policy is the baseline: an [API-key policy](/docs/wallet-operations/api-key-policies) can narrow what a key may do, or route an operation into approval, but it can never expand past what the wallet policy allows. See [Manage API keys](/docs/developing-with-sdp/manage-api-keys) for caller permissions.

### Operation families

| Family | Description | Current evaluated operations |
| --- | --- | --- |
| `payment` | Outbound single and batch payments. | Single and batch transfer execution; recurring payment creation, update, and collection |
| `ramp` | Fiat-to-crypto and crypto-to-fiat ramp activity. | On-ramp and off-ramp quote creation |
| `issuance` | Token lifecycle actions signed by the wallet. | Deploy, mint, burn, force burn, seize, authority update, freeze, unfreeze, pause, unpause, metadata update, and allowlist add and remove |
| `program` | On-chain program interactions signed by the wallet. | None in the public API |
| `transfer` | Direct transfers outside the payment workflow. | None in the public API; payment transfers use the `payment` family |

Family values with no public operation type are valid policy values, but no public SDP endpoint emits an operation in those families.

### Exact operation types

| Operation type | Family | What it controls |
| --- | --- | --- |
| `payment_transfer_execute` | `payment` | Executes one outbound payment transfer from the wallet. |

| `ramp_offramp_quote` | `ramp` | Creates an off-ramp quote that draws crypto from the source wallet. |
| `issuance_deploy_execute` | `issuance` | Deploys the token using the configured signing wallet. |
| `issuance_mint_execute` | `issuance` | Executes a token mint using the configured signing wallet. |
| `issuance_burn_execute` | `issuance` | Executes a token burn using the configured signing wallet. |
| `issuance_force_burn_execute` | `issuance` | Force-burns tokens from a holder account. |
| `issuance_seize_execute` | `issuance` | Seizes tokens into the issuer-controlled destination. |
| `issuance_update_authority_execute` | `issuance` | Changes a token authority using the current authority wallet. |
| `issuance_freeze_execute` | `issuance` | Freezes a holder token account using the freeze authority wallet. |
| `issuance_unfreeze_execute` | `issuance` | Thaws a frozen holder token account using the freeze authority wallet. |
| `issuance_pause_execute` | `issuance` | Pauses all token transfers using the pause authority wallet. |
| `issuance_unpause_execute` | `issuance` | Resumes token transfers using the pause authority wallet. |

Operation-type matching is exact and case-sensitive. The API rejects operation types it does not recognize.

### Policy-gated issuance actions

Every issuance action that SDP signs with a custody wallet is checked against that wallet's policy before it runs, not only the actions that move tokens: deploy, freeze and unfreeze, pause and unpause, authority updates, on-chain metadata updates, and allowlist changes are gated the same way as mint, burn, force burn, and seize. Requests that sign nothing are not evaluated. These include the `/prepare` endpoints, which return an unsigned transaction for you to sign, token edits that change no on-chain metadata or target a token that is not deployed yet, and allowlist changes on a token without an on-chain allowlist.

## Policy evaluation and audit records

Each supported action against the wallet is recorded as a **Wallet Operation** — the attempt, whatever the outcome — before evaluation runs, and its **Policy Evaluation** — the verdict, plus a point-in-time snapshot of the operation and the policy that decided it — is recorded once SDP decides what should happen. `audit.recentEvaluations` exposes the most recent decisions for the wallet so support and customer operators can review:

- what operation was evaluated (`walletOperationId`, `operationFamily`, `operationType`)
- what decision SDP made (`decision`, `reasonCode`, `reason`, `requiresApproval`)
- whether an approval request was created (`approvalRequestId`)
- when the operation was created, updated, and evaluated

Use these records to explain allow, deny, approval-required, and review outcomes. They are an operational audit summary, not the full raw provider payload.

The request that triggered the operation reports the decision directly. A `deny` (or `not_evaluated`) decision fails the request with `403` and error code `FORBIDDEN`. A decision that holds the operation returns `202` with error code `SIGNING_PENDING` and the `approvalRequestId` in `error.details`; see [Approvals](/docs/wallet-operations/approvals) for what happens next.

## Policy control inventory

`GET /v1/policies` lists the policy controls of every wallet and API key in the project in one paginated response. Use it to find wallets still running on implicit default allow, profiles left in draft, or API keys that have policy bindings.

| Query parameter | Values |
| --- | --- |
| `target` | `wallet`, `api_key`, or `all` (default) |
| `status` | `default_allow`, `draft`, `active`, or `disabled` |
| `query` | Case-insensitive substring of the wallet display name or API-key label, up to 200 characters |
| `page` | Page number, starting at 1 (default 1) |
| `pageSize` | Rows per page, 1–100 (default 25) |

`target=wallet` requires the `wallets:read` permission, `target=api_key` requires `api-keys:read`, and `all` requires both. An API key limited to selected wallets only sees the wallets it can read.

## Provider mapping status

`providerMappingStatus` describes whether an SDP policy revision has also been mapped into a custody or ramp provider's native policy system. Current payment wallet controls are SDP-enforced first. A value of `not_applicable` means there is no provider-native mapping for that revision. `pending`, `partial`, or `failed` mean SDP still evaluates the operation, but you should not assume the same rule has been fully synced to the provider.

## Destination allowlist

Destination controls are `destination` rules in the wallet policy. They are distinct from a token's **Token Access Control** allowlist, which gates who may hold the token itself. Each entry is a single on-chain address (a base-58 Solana public key), with no patterns, ranges, or address books.

```json title="destination-rule.json"
{
  "id": "known-counterparties",
  "kind": "destination",
  "allowlist": ["7xKXz...9fGh", "5aBCd...2eFg"]
}
```

- `allowlist` (or `destination` / `destinations`): an operation whose destination is not on the list is denied. A destination on the list gets the rule's `action`, `allow` by default.
- `blocklist`: an operation whose destination is on the list is denied. Any other destination is left to the other rules.
- Each list holds up to **500 addresses** per rule.
- A `destination` rule with no addresses returns `review`.

An allowlist also denies operations that have no destination, such as pausing a token, because no address on the list can match. For a batch, destination rules are checked for each recipient.

The allowlist exists to bound risk on automated wallets (a hot wallet that should only ever pay a known set of counterparties) and to enforce treasury controls (only the corporate cold-storage address can drain the operating wallet).

## Transfer limits

Transfer limits are `amount` and `velocity` rules. Both always target specific assets, identified by mint, with native SOL under its well-known mint. There is no blanket cap across assets, and a rule that names no mint is rejected.

- **Per-operation cap**: an `amount` rule denies any single operation whose amount is below `min` or above `max` for the named mints.
- **Rolling cap**: a `velocity` rule sums prior operations over a rolling window. See [Velocity limits](#velocity-limits).

```json title="limit-rules.json"
[
  {
    "id": "max-usdc-per-transfer",
    "kind": "amount",
    "max": "10000",
    "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v"
  },
  {
    "id": "daily-usdc-cap",
    "kind": "velocity",
    "window": "P1D",
    "max": "50000",
    "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v"
  }
]
```

Amounts are **UI-unit decimal strings**: `"100.00"` means 100 tokens, regardless of the mint's decimals, matching the transfer-request convention. A rule that names several mints applies the same bound to each mint separately, so there is no aggregate cap across mints. For different thresholds per token (for example 10,000 USDC but 50 SOL), write one rule per mint.

Set both for defense in depth: a per-operation cap that catches obvious mistakes, plus a rolling cap that bounds blast radius if many small transfers are submitted in a coordinated attack.

## Updating policies

`PUT /v1/payments/wallets/{walletId}/policies` has **full-replace** semantics: the request body is the complete rule set and default action for a new immutable revision, which SDP activates immediately. To remove a rule, leave it out of the next `PUT`. To lift every restriction, send `"defaultAction": "allow"` with an empty `rules` array.

| Field | Required | Description |
| --- | --- | --- |
| `defaultAction` | Yes | `allow`, `deny`, `approval_required`, or `review`; applies when no rule matches. |
| `rules` | Yes | Up to 100 rules. Rule `id` values must be unique. |
| `commitMessage` | No | Up to 500 characters describing the change, stored on the revision. |
| `expectedRevisionId` | No | The active revision ID you last read. If another update has activated a revision since, the request fails with `409`. Use `null` to require that no profile is active yet. Omit it to overwrite unconditionally. |

Because PUT is full-replace, treat policy edits like ordinary form submissions: read the current state, present it for editing, and PUT the complete updated object with `expectedRevisionId` set to the `controlProfile.activeRevisionId` you read, so a concurrent edit fails instead of being overwritten. Don't construct partial patches.

### Who can change wallet policies

Updating a wallet policy requires the `wallets:write` and `payments:write` permissions and an admin caller:

- An API key with the `api_admin` role. A key with any other role receives `403 FORBIDDEN`, even when it holds both permissions.
- In the dashboard, an organization admin.

Reading a wallet policy requires `wallets:read` and `payments:read`. API-key policies have their own authoring rules; see [API key policies](/docs/wallet-operations/api-key-policies#who-can-manage-api-key-policies).

## Interaction with compliance

Wallet policies enforce **structural** constraints (where funds can go, how much, how fast). They do not replace compliance screening. If your organization has compliance screening enabled, screening happens on the destination address as a separate check, in addition to any `destination` rule. A transfer can be rejected by either layer; both must pass to reach the network.

See the [Compliance API reference](/docs/reference/api/compliance) for address-screening flows that complement policies.
