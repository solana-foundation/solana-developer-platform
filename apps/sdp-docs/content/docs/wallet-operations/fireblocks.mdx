Connect your own Fireblocks workspace to use its Solana wallets in SDP.
Fireblocks keeps the wallet signing keys and applies your transaction policy.

## Before you start

- Sign in to SDP as an **organization admin**. Ask the SDP team to enable
  Fireblocks if it isn't offered in wallet setup.
- Have a Fireblocks workspace owner available to approve the API user and an
  authorized operator to configure policies.
- Choose the right SDP project: **Sandbox** uses devnet; **Production** uses
  mainnet and requires [mainnet access](/docs/guides/go-to-mainnet).

## 1. Download a CSR from SDP

Open **Integrations → Fireblocks → Add connection**. Enter a **Connection name**
and click **Generate and download CSR**.

SDP creates the API authentication key. Upload only the
[CSR](https://developers.fireblocks.com/docs/integrate-fireblocks-with-third-party-service-providers)
to Fireblocks, never a private key. Complete registration within seven days or
generate a new CSR.

## 2. Register an API user in Fireblocks

In Fireblocks, open **Developer center → API users → Add API user**. Enter a
descriptive name, select **Editor**, upload the CSR, and click **Add user**.
Have the workspace owner approve it and wait until active.

If the key uses [IP restrictions](https://developers.fireblocks.com/docs/whitelist-ips-for-api-keys),
ask an authorized operator to allow SDP's outbound IPs under **⋯ → Allowlist IP
address**. Get the IPs from the SDP team.

## 3. Connect your vaults

Copy **API User (ID)** from Fireblocks into SDP and click **Load vaults**.
Select up to **20 vaults**, then click **Connect and verify**.

SDP verifies and imports the existing wallets using their vault names.

## 4. Set approvals and send a payment

SDP submits direct payments as
[one-time address transfers](https://developers.fireblocks.com/reference/transaction-sources-destinations#one_time_address).
Your workspace and Transfer policy must allow them.

In Fireblocks, open **Security → Policies → Transfer**. Have your authorized
operator choose **Edit policy → Add rule** and configure:

- **Scope:** select this SDP API user as **Initiator**, then the source vaults,
  destinations, and an address type that permits one-time addresses.
- **Funds:** select the assets and amount limits your organization permits.
- **Action:** choose **Request approval**, set **Approver set** and **Threshold**,
  then choose **Designated signer → Users** and select your organization's signer.

Publish the rule, then open **Settings → General** and set **One-time address
transactions** to **Allow**. Complete the required approvals for both changes.

Manage any address whitelist in **Whitelisted addresses** and check the Solana
network and address. SDP contacts do not whitelist recipients in Fireblocks.

Open **Accounts → Vault**, select the source vault's Solana wallet, and use its
deposit address. Fund it with **SOL for network fees**, including when sending
USDC. Fireblocks signs and broadcasts direct SOL/canonical USDC payments;
SDP fee sponsorship does not apply.

Send a [small payment](/docs/payments/send-basic-payment) and approve it in
Fireblocks. SDP tracks it while approval is pending.

SDP relies on your Fireblocks policy. The **Pay** reminder does not detect
missing policies: the Editor role cannot read them. Check the policy yourself.

## Manage and troubleshoot

<details>
<summary>Check the signer (optional)</summary>

Direct SOL/USDC payments don't need this check. **Prove ownership**, batch
payments, and other RAW-signing operations require workspace RAW enablement
and a RAW policy permitting the SDP API user with your designated signer.
If disabled, contact your Fireblocks Customer Success Manager for enablement.
You don't need an API Co-signer for this connection.

For the check, open the wallet's **Settings → Ownership → Prove ownership**.
Approve promptly in Fireblocks. SDP requests a RAW signature and simulates
without broadcasting; a configured, funded SDP fee payer is required.

</details>

<details>
<summary>Rotate credentials</summary>

Open **Integrations → Fireblocks**, select the connection, and choose
**Rotate secret**. Generate a new CSR and register a replacement API user as
above. Before switching, update policies that name the old **Initiator** to
include the replacement user and configure its IP allowlist.

Select the original verification vault. SDP checks every wallet before
switching. Keep the previous user active and permitted during the 24-hour
rollback window.

</details>

<details>
<summary>Disconnect</summary>

In Fireblocks, open **Developer center → API users → ⋯ → Delete** for the SDP
API user. If unavailable, ask an authorized workspace operator.

SDP blocks connection deactivation while wallets remain active. Fireblocks
wallet deactivation is not supported from SDP; contact the SDP team for cleanup.

Deleting the user does not cancel payments Fireblocks already accepted.
Reject or cancel them there too; cancellation can race execution.

</details>

<details>
<summary>How credentials are stored</summary>

Wallet signing keys stay in Fireblocks. SDP stores API credentials in GCP
Secret Manager by default on hosted SDP or encrypted database storage when
self-hosted. Pending CSR keys are encrypted and deleted after registration or
expiry.

</details>

<details>
<summary>Fireblocks refused a payment</summary>

Open **Transaction history**, expand the transaction, and read **Status** and
**Sub-status**. **Inspect Policy** uses the current policy, which may differ
from the one that evaluated the transaction. Pending approval is not a refusal.

A refused submission or replay returns **HTTP 422** with
`error.code: "CUSTODY_POLICY_REFUSED"`. A later refusal appears as a failed
transfer. The dashboard shows:

> Fireblocks blocked signing due to a wallet policy. Review the policy in
> Fireblocks or adjust the request.

If a submission times out, keep its original
[Idempotency-Key](/docs/developing-with-sdp/idempotency) and check the existing
payment before intentionally starting another.

</details>
