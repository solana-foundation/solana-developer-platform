Embedded Yield lets your platform offer vault yield without SDP ever holding your users' funds. Your backend asks SDP to **build** an unsigned Solana transaction for the customer's own wallet, the customer signs it in your app, and your backend **submits** the signed bytes back. SDP verifies the signatures, records the movement, then broadcasts it. Withdrawals work the same way in reverse.

Two properties define the surface:

- **Non-custodial.** SDP holds no key for your customers' wallets. The customer's signature is the authorization, every time.
- **Server-side.** Your SDP API key stays on your backend. The browser or mobile app only ever sees unsigned transaction bytes and returns signed ones.

All endpoints live under `/v1/earn`. Every code sample uses one Solana SDK, `@solana/kit`; nothing here needs `@solana/web3.js`.

## Choose an access tier

| Capability | Without an API key | With an API key |
| --- | --- | --- |
| List and inspect strategies | Yes | Yes |
| Preview deposits and withdrawals | Yes | Yes |
| Build unsigned external-wallet transactions | Yes, owner pays | Yes, owner or your `feePayer` |
| Submit signed transactions through SDP | No | Yes, `earn:write` |
| Track movements, positions, balances, and earnings | No | Yes, `earn:read` |

Keyless requests use the deployment's environment (the preview deployment is Solana devnet) and create no record: the response carries no `movementId`, and you sign, broadcast, and track the transaction yourself. Keyed requests carry your project and environment, can name a `feePayer`, and can be submitted to SDP, which records the movement before broadcast and reconciles it to a terminal state.

**The key.** Create a Developer API key for your project in the dashboard; that role includes `earn:read` and `earn:write`. Start in sandbox, which runs on devnet. A strategy is depositable when `fundable` is `true` and `status` is `active`.

## Without an API key

List the catalogue and build a deposit with nothing but a strategy id and the customer's funded devnet wallet:

```bash
export SDP_API_URL=https://api-preview.solana.com

curl --fail-with-body --silent --show-error "$SDP_API_URL/v1/earn/strategies"

curl --fail-with-body --silent --show-error \
  --request POST \
  --header 'Content-Type: application/json' \
  --data '{ "strategyId": "<STRATEGY_ID>", "ownerAddress": "<OWNER_ADDRESS>", "amount": "1" }' \
  "$SDP_API_URL/v1/earn/external-wallet/deposit-transactions"
```

If the strategy's `depositSlippage` is non-null, call `POST /v1/earn/vault-deposit-previews` first and include a quote-derived `minSharesOut` (see [Floors and previews](#floors-and-previews)).

Sign and broadcast the response's base64 `transaction.transaction` yourself. `build` is the parsed JSON of the build response; `owner` is a kit `CryptoKeyPair` here, or your wallet's signer in a real app:

```ts
import {
  createSolanaRpc,
  getBase64EncodedWireTransaction,
  getBase64Encoder,
  getSignatureFromTransaction,
  getTransactionDecoder,
  partiallySignTransaction,
} from "@solana/kit";

const rpc = createSolanaRpc("https://api.devnet.solana.com");
const transaction = getTransactionDecoder().decode(
  getBase64Encoder().encode(build.data.transaction.transaction),
);
const signed = await partiallySignTransaction([owner], transaction);
await rpc.sendTransaction(getBase64EncodedWireTransaction(signed), { encoding: "base64" }).send();
const signature = getSignatureFromTransaction(signed);
// Poll rpc.getSignatureStatuses([signature]) until finalized, and give up once
// the block height passes build.data.transaction.lastValidBlockHeight.
```

Do not call SDP's submit endpoint for a keyless build; there is no server-side row to consume. For a keyless withdrawal, preview and build take `{ strategyId, ownerAddress, shares }`; an anonymous caller never supplies a `positionId`.

## With an API key

Authenticate with `Authorization: Bearer <SDP_API_KEY>`. The dashboard's **Embedded Yield → Integrate** page generates a complete server module for the strategy you pick; the calls below are the same ones, in order.

| Step | Endpoint |
| --- | --- |
| Discover strategies | `GET /v1/earn/strategies` |
| Preview a deposit | `POST /v1/earn/vault-deposit-previews` |
| Build a deposit | `POST /v1/earn/external-wallet/deposit-transactions` |
| Submit the signed deposit | `POST /v1/earn/external-wallet/deposits` |
| Poll a movement | `GET /v1/earn/external-wallet/movements/{movementId}` |
| Balance and earnings | `GET /v1/earn/external-wallet/earnings?ownerAddress=…` |
| Activity feed | `GET /v1/earn/external-wallet/movements?ownerAddress=…` |
| Live positions | `GET /v1/earn/external-wallet/positions?ownerAddress=…` |
| Portfolio totals | `GET /v1/earn/external-wallet/positions/summary` |
| Preview a withdrawal | `POST /v1/earn/external-wallet/withdrawal-previews` |
| Build a withdrawal | `POST /v1/earn/external-wallet/withdrawal-transactions` |
| Submit the signed withdrawal | `POST /v1/earn/external-wallet/withdrawals` |

Every per-owner read addresses the customer's wallet the same way: a required `ownerAddress` query parameter.

## 1. Pick a strategy

`GET /v1/earn/strategies` returns the catalogue, ranked by deposit size, with the live APY your UI can show. All a build needs from a row is its `id`; the cluster comes from your key's environment and the deposit token from the strategy itself.

Two fields gate what you may offer:

- **`fundable`** answers whether the instrument exists on your environment's cluster. `false` is definitive: the row is browse-only (a mainnet strategy seen from sandbox, for example).
- **`status`** is the catalogue lifecycle; only `active` strategies accept new deposits. Positions in a strategy that later pauses stay fully withdrawable: money out is never gated by money-in rules.

`depositSlippage` and `withdrawalSlippage` say whether that direction needs a quote-derived floor; see [Floors and previews](#floors-and-previews). `feeSponsored` describes SDP's own Treasury paymaster and has no effect on Embedded Yield builds: your customer pays unless you name a `feePayer`.

Jupiter Lend contributes its mainnet USDT Earn market (deposits mint jlUSDT receipt tokens; withdrawals redeem them when protocol liquidity allows). Ondo contributes USDY on mainnet with no vault program: a deposit is a USDC to USDY swap through Jupiter, the position is the wallet's USDY balance, a withdrawal is the reverse swap, and both directions require a live quote. Both are mainnet-only and appear in sandbox as browse-only rows.

## 2. Deposit: build, sign, submit, poll

```ts
const SDP_API_URL = process.env.SDP_API_URL ?? "https://api.solana.com";
const STRATEGY_ID = "earn_strategy_…"; // from the catalogue or the Integrate page

function sdpHeaders(extra: Record<string, string> = {}) {
  const apiKey = process.env.SDP_API_KEY;
  if (!apiKey) throw new Error("SDP_API_KEY is required");
  return { Authorization: `Bearer ${apiKey}`, "Content-Type": "application/json", ...extra };
}

async function sdpFetch(path: string, init?: RequestInit) {
  const response = await fetch(`${SDP_API_URL}${path}`, init);
  const result = await response.json().catch(() => null);
  if (!response.ok) {
    const code = result?.error?.code ? ` ${result.error.code}` : "";
    throw new Error(`SDP ${response.status}${code}: ${result?.error?.message ?? "Request failed"}`);
  }
  return result.data;
}
```

**Build.** SDP simulates the deposit before handing anything out, so a wallet that cannot fund it fails here with a readable 400 instead of a landed, failed transaction.

```ts
const { transaction } = await sdpFetch("/v1/earn/external-wallet/deposit-transactions", {
  method: "POST",
  headers: sdpHeaders(),
  body: JSON.stringify({
    strategyId: STRATEGY_ID,
    ownerAddress, // the customer's wallet
    amount: "25", // decimal string in the strategy's deposit token
  }),
});
// { transactionId, transaction, lastValidBlockHeight, feePayer?, ... }
```

Add `minSharesOut` when the strategy's `depositSlippage` is non-null ([Floors and previews](#floors-and-previews)).

**Sign.** Hand the base64 `transaction.transaction` to the customer's wallet and get signed bytes back. With a kit wallet signer (for example `useWalletAccountTransactionSigner` from `@solana/react`):

```ts
import { getBase64EncodedWireTransaction, getBase64Encoder, getTransactionDecoder } from "@solana/kit";

const unsigned = getTransactionDecoder().decode(getBase64Encoder().encode(transaction.transaction));
const [signed] = await walletSigner.modifyAndSignTransactions([unsigned]);
const signedTransaction = getBase64EncodedWireTransaction(signed);
```

Any wallet library works as long as it returns the signed transaction as base64; the submit only checks signatures.

A built transaction expires with its blockhash, about a minute. If the customer walks away, build a fresh one: submitting an expired build is refused with `409 TRANSACTION_EXPIRED` before anything is recorded.

**Submit.** The `Idempotency-Key` header is required. Reuse the same key when retrying: a retry returns the original movement with `replayed: true` instead of moving money twice, and each built transaction is consumable exactly once.

```ts
const { deposit } = await sdpFetch("/v1/earn/external-wallet/deposits", {
  method: "POST",
  headers: sdpHeaders({ "Idempotency-Key": idempotencyKey }),
  body: JSON.stringify({ transactionId: transaction.transactionId, signedTransaction }),
});
// { movementId, positionId, status, signature, ... }
```

**Poll.** Each read of the movement checks the transaction's exact signature on chain and advances the recorded status immediately, so state lands as fast as the network decides it. A background reconciler covers RPC outages.

```ts
const { movement } = await sdpFetch(
  `/v1/earn/external-wallet/movements/${encodeURIComponent(deposit.movementId)}`,
  { headers: sdpHeaders() },
);
```

Statuses are `requested` (SDP recorded the signed transaction but has not yet seen it on the network), `submitted`, `confirmed`, `finalized`, `failed`. Treat `confirmed` as **Done** in customer-facing UI: stop the foreground spinner, show the updated balance, and let the customer continue. SDP keeps reconciling the movement to the durable ledger outcome, `finalized` or `failed`, in the background. Use `finalized` only when your own backend needs an irreversible signal for accounting or another high-stakes side effect. A `failed` movement carries a `failureReason`.

## 3. Who pays fees and rent

**By default, the customer's wallet pays everything**: the network fee, plus about 0.002 SOL of rent when a first deposit creates their share token account (refunded when the position fully exits). A customer holding only stablecoins cannot complete that transaction.

**To pay on your customers' behalf, name a `feePayer` on the build.** The named wallet, one you control, becomes the transaction's fee payer and funds the account rent, and the build echoes it back. The transaction then needs its signature alongside the customer's: co-sign server-side after the customer signs, then submit.

```ts
import {
  createKeyPairFromBytes,
  getBase64EncodedWireTransaction,
  getBase64Encoder,
  getTransactionDecoder,
  partiallySignTransaction,
} from "@solana/kit";

// 1. Build with your sponsor wallet as the fee payer.
const { transaction } = await sdpFetch("/v1/earn/external-wallet/deposit-transactions", {
  method: "POST",
  headers: sdpHeaders(),
  body: JSON.stringify({ strategyId: STRATEGY_ID, ownerAddress, amount, feePayer: SPONSOR_ADDRESS }),
});

// 2. The customer signs in your app, exactly as before.

// 3. Co-sign with the sponsor's key on your backend, then submit.
const sponsor = await createKeyPairFromBytes(SPONSOR_SECRET_KEY);
const decoded = getTransactionDecoder().decode(getBase64Encoder().encode(customerSignedTransaction));
const signedTransaction = getBase64EncodedWireTransaction(
  await partiallySignTransaction([sponsor], decoded),
);
```

The generated module wraps step 3 as `createSponsorSigner(secretKey)`, so `signEarnTransaction(built, customerSigner, sponsorSigner)` collects both signatures whenever the build echoes a `feePayer`.

What to know when sponsoring:

- **Both signatures are required.** The submit verifies every signature and names a missing or invalid fee-payer signature, so a co-signing bug on your side is distinguishable from a customer-side one.
- **The fee payer is committed at build time.** It is inside the signed message, so it cannot be swapped at submit; rebuild if you need a different sponsor.
- **Keep a SOL float.** The sponsor pays the fee on every sponsored transaction and the rent on every first deposit. The build simulates with your sponsor as the payer and refuses with a 400 naming it when it cannot pay.
- **Rent comes back to you.** SDP records your sponsor as the rent funder, and a full exit refunds the share account's rent to the recorded funder, not to the customer.
- **Mind the clock.** Build, customer signature, your co-signature, and submit must all fit inside the blockhash window. Co-sign programmatically, not through a manual approval step.
- Passing the customer's own address as `feePayer` means the default; the build does not echo it. Program-derived addresses cannot sign, so an off-curve fee payer can never be submitted.
- Applies to `withdrawal-transactions` identically, and to the standalone swap transaction of a split swap-funded deposit.

### Protect the sponsor key

The sponsor is a hot key on your backend by design: it has to co-sign inside the blockhash window, so it cannot sit behind a manual approval. That makes it a target. Nothing SDP does limits what a stolen or abused sponsor key can spend, because the key never touches SDP; the controls are yours. Treat the following as the minimum before you sponsor on mainnet.

- **Dedicated signer.** Use a keypair whose only job is co-signing SDP builds. Never reuse a treasury, deployer, or hot-wallet key: a compromise of the sponsor must cost you at most the sponsor's float.
- **Programmatic co-sign only, and only of SDP builds.** Sign transactions your own backend just received from `deposit-transactions`, `withdrawal-transactions`, or a split swap, for a customer session you authenticated, and nothing else. Do not expose a "sign this" endpoint that accepts arbitrary bytes, and do not let the key sign from a client. Verify the fee payer and the program IDs in the decoded message match what you asked SDP to build before signing.
- **Bound the float.** Keep only what a day or two of expected sponsorship costs in the sponsor wallet, and top it up from a cold or multisig-controlled source on a schedule.
- **Monitor spend and alert on it.** Track the sponsor's SOL balance and outflow per hour. Alert on the balance crossing your refill threshold, on outflow above your expected ceiling, and on any transfer from the sponsor that is not a fee or rent payment.
- **Rate-limit sponsorship per customer.** A build costs you nothing until you co-sign, so decide per customer and per session how many sponsored transactions you will sign in a window. SDP does not know which of your customers a wallet belongs to.
- **Plan rotation.** Keep the sponsor address in configuration, not code. Rent refunds go to the funder recorded at deposit time, so a position sponsored by a retired key still refunds to that key on exit; keep retired sponsor keys retrievable until their positions are closed.
- **Store the key like a secret.** A secrets manager or KMS-backed signer, never an environment variable in a repository or a file in an image.

## 4. Show balances and activity

A customer who has not deposited yet is not an error: every per-owner read answers `200` with empty lists and zero counts.

- `GET /v1/earn/external-wallet/earnings?ownerAddress=…` returns, per deposit token, `currentValue`, `totalDeposited`, `totalWithdrawn`, and `earned`, where `earned` is current value plus withdrawn minus deposited. It covers positions the customer currently holds; a fully exited position's history lives in the activity feed. `earned` is stated only when exact; while a movement is still pending, or when a withdrawal's payout could not yet be read from its landed transaction (SDP keeps retrying that read for two weeks), it is absent with a named `earnedUnavailableReason`. Render a dash for an absent figure, never $0.
- `GET /v1/earn/external-wallet/movements?ownerAddress=…` is the customer's activity feed, newest first, keyset-paged via `before`. Render `tokenAmount` in `tokenMint` units for both directions; `amount` and `denomination` are the on-chain quantity, which is shares on a withdrawal. A withdrawal's `tokenAmount` is `null` until it finalizes.
- `GET /v1/earn/external-wallet/positions?ownerAddress=…` lists live positions. Page it to completion; a silently short list hides withdrawable money. Read `id` and `withdrawableShares` here to drive withdrawals. A position closes when a withdrawal empties it and drops out of this list (`closedAt` set); a later deposit reopens it. If live RPC hydration fails, `shares`, `withdrawableShares`, and `tokenValue` are absent, never zero: show an unavailable state and disable withdrawal until a fresh read returns the ceiling.
- `GET /v1/earn/external-wallet/positions/summary` aggregates your whole project across customers, by strategy and token. By default it is address-free: each strategy total carries `walletCount` and token totals, and no `ownerAddresses`. Pass `includeOwnerAddresses=true` only from a surface that has to show per-customer detail; that list is the full set of your customers' wallet addresses, and any `earn:read` key that requests it becomes a holder of personal data. Add `includePositions=true` to receive the hydrated positions inside each strategy total; it is rejected without the explicit `includeOwnerAddresses=true`.

  **Changed in 0.77:** earlier releases included `ownerAddresses` unless you passed `includeOwnerAddresses=false`. If your integration reads that field, or passes `includePositions=true` on its own, add `includeOwnerAddresses=true` to the request.

## 5. Withdraw

Same build, sign, submit shape. The build names the customer's **position** (never a strategy), so exits keep working even when a vault is delisted or its provider is disabled for new deposits.

```ts
// What would these shares pay right now? Read-only; nothing is built.
const quote = await sdpFetch("/v1/earn/external-wallet/withdrawal-previews", {
  method: "POST",
  headers: sdpHeaders(),
  body: JSON.stringify({ positionId, shares }),
});
// { assetsOut, assetDecimals, blockingIssues }

const { transaction } = await sdpFetch("/v1/earn/external-wallet/withdrawal-transactions", {
  method: "POST",
  headers: sdpHeaders(),
  body: JSON.stringify({ positionId, shares }), // + minAmountOut when withdrawalSlippage is non-null, + feePayer to sponsor
});
// customer signs (and your sponsor co-signs, if sponsoring), then submit:
const { withdrawal } = await sdpFetch("/v1/earn/external-wallet/withdrawals", {
  method: "POST",
  headers: sdpHeaders({ "Idempotency-Key": idempotencyKey }),
  body: JSON.stringify({ transactionId: transaction.transactionId, signedTransaction }),
});
```

## Floors and previews

Both previews work for every provider and are the figures to show a customer before they confirm. Whether a build also takes a protection floor depends on the strategy row:

| Field | Non-null | Null |
| --- | --- | --- |
| `depositSlippage` | The build requires `minSharesOut`. Preview first and derive the floor from `sharesOut` minus the tolerance your customer chose (`defaultToleranceBps` is a suggested start). | `minSharesOut` is optional; the deposit takes the live rate. |
| `withdrawalSlippage` | The build requires `minAmountOut`, derived from `assetsOut` the same way. | The vault's withdraw instruction takes only a share amount, so no floor can be enforced on chain. Do not pass `minAmountOut`; the build refuses it with a 400. |

Derive a floor from the live quote, never from the amount you sent; the tolerance covers only the state moving between the quote and the transaction landing. The generated module includes `floorForTolerance`, an exact decimal floor without a JavaScript number round-trip, and applies it only for strategies that require one.

## Swap-funded deposits

Pass `sourceTokenMint` to accept a stablecoin the vault does not take: SDP prepends a Jupiter swap inside the same transaction, `amount` becomes the source amount, and the response's `transaction.swap` reports the derived deposit. Accepted source tokens are USDC, USDG, PYUSD, and USDT on mainnet; USDT has no devnet mint. Jupiter has no devnet routes, so swap-funded deposits cannot be exercised in sandbox.

If the composed transaction cannot fit one Solana packet, the response is `{ requiresSeparateSwap: true, swap, followUp }` instead: have the wallet sign `swap.transaction` and broadcast it yourself, then build again with the `followUp` body, which echoes your original `minSharesOut` and `feePayer` so the follow-up keeps the same protections.

Recovery across that split is yours: persist the swap signature and the `followUp` body before broadcasting, and reconcile before you rebuild, because SDP records no movement for the standalone swap. For keyed builds SDP records that it handed the swap out and flags owners whose deposit-token balance rose by the swap's floor with no follow-up deposit after a grace period, so a dropped follow-up will be noticed; it will not be repaired for you. Keyless builds store nothing.

## Idempotency and errors, in one place

| Call | Rule |
| --- | --- |
| Builds | No `Idempotency-Key`. A build moves no money and expires with its blockhash. |
| Submits | `Idempotency-Key` header required. Same key on retry returns the original movement (`replayed: true`). |

| Response | Meaning | What to do |
| --- | --- | --- |
| `400` | The request or the current vault state must change. | Fix the request or show the message; do not retry unchanged. |
| `409 TRANSACTION_EXPIRED` | The build's blockhash expired before submit. Nothing was recorded. | Build again and have the customer sign the new transaction. |
| `409 CONFLICT` (any other message) | The build was already consumed under a different idempotency key, or the key was reused with a different body. | Look up the existing movement; do not rebuild. |
| `422 SIGNING_REJECTED` | A fee sponsor refused the transaction by policy. | The same transaction will be refused again; change it. |
| `503 PROVIDER_UNAVAILABLE` | Live provider or RPC state could not be read. | Retry the read-only preview or build with bounded backoff. |
| Timeout or 5xx on a submit | Outcome uncertain. | Retry the exact signed bytes with the same `Idempotency-Key`. |

## Before production

Work through this in sandbox before you go live. Each item is something SDP cannot check for you.

- Your submit path retries an uncertain response with the same signed bytes and the same `Idempotency-Key`, rebuilds on `409 TRANSACTION_EXPIRED`, and looks up the movement on any other `409`.
- Your UI treats `confirmed` as Done and leaves foreground loading immediately. Any backend workflow that needs irreversible finality keeps tracking `finalized` or `failed` without blocking the customer.
- Absent fields render as absent (a dash, never `$0`), and you handle every status in the vocabulary rather than collapsing unknown ones.
- If you accept swap-funded deposits, you have run one small split-swap recovery drill on mainnet: a swap broadcast, a simulated crash, and the follow-up deposit rebuilt from persisted state. Sandbox cannot exercise it.
- If you sponsor fees, the sponsor key meets every point in [Protect the sponsor key](#protect-the-sponsor-key), and the spend alerts have fired at least once in a drill.
