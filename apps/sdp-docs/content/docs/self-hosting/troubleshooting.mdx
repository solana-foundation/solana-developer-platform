---
title: Troubleshooting
description: Diagnose common startup and configuration failures on a self-hosted stack.
---

Most self-hosting problems appear at startup. Start by looking at the service state and the logs:

```bash title="Terminal"
cd ~/sdp
docker compose ps
docker compose logs -f sdp-api
```

## Docker is not ready

The install script checks for Docker before it does anything else. It reports when Docker is not
installed, when Compose v2 is unavailable, or when the daemon is unreachable. Install or start
Docker, then run the script again. See the
[Docker Engine](https://docs.docker.com/engine/install/) and
[Compose](https://docs.docker.com/compose/install/) documentation.

## A required variable is missing

`compose.yml` fails fast when a required variable is unset. The message names the variable, for
example `set POSTGRES_PASSWORD in .env`.

Confirm that a `.env` file exists next to `compose.yml`, and that it fills in every required
variable. The [configurator](/docs/self-hosting/configurator) produces a complete file. The
[environment reference](/docs/self-hosting/env-reference) lists what is required.

## Images do not pull

If `docker compose pull` reports access denied or a missing manifest:

- Confirm that `SDP_IMAGE_REGISTRY` and `SDP_VERSION` point at a registry and a tag you can reach.
- Pull a single image directly to see the underlying error, for example
  `docker pull ghcr.io/solana-foundation/sdp/sdp-api:latest`.
- Run `docker login` for the registry first, if the registry is private.

## Port already in use

The API, web, and docs services default to ports `8787`, `3000`, and `3001`. A service cannot bind
its port when another process already holds it.

Override the host port in `.env` with `SDP_API_PORT`, `SDP_WEB_PORT`, or `SDP_DOCS_PORT`. Then run
`docker compose up -d` again.

## Migrations failed

`sdp-migrate` runs once before the API starts. The API stays down when it fails. Inspect the
migration logs:

```bash title="Terminal"
docker compose logs sdp-migrate
```

A failure here is usually a database connection problem. Check the `POSTGRES_*` variables, or
`DATABASE_URL`, and confirm that `docker compose ps` reports the `postgres` service as healthy.

## Database connection refused

The API and the migration service wait for Postgres to report healthy before they start. If they
still cannot connect, verify the credentials in `.env`. For an external database, where
`DATABASE_URL` is set, also verify that the database is reachable from inside the Docker network.

## Authentication errors in the dashboard

A sign-in problem points at the Clerk configuration. Re-check
`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, and `CLERK_ISSUER` against your Clerk
application. Confirm that all three keys come from the same Clerk instance, because Clerk issues
separate keys for its development instance and its production instance.

Two sets of environment names meet on this page, and they are not the same thing. Clerk names its
own instances *development* and *production*. SDP names its environments *sandbox* and
*production*, where `sandbox` runs against the Solana devnet cluster and `production` runs against
mainnet. Choose the Clerk instance that matches the deployment you run, and choose the Solana
cluster separately in `SOLANA_RPC_URL`.

## None of these steps fixed the problem

Capture the logs of the failing service, and capture your `.env` settings with the secrets removed.
Then open an issue on the
[project repository](https://github.com/solana-foundation/solana-developer-platform).
