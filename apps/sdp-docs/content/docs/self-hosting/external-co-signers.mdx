---
title: External co-signers
description: Host provider-specific signing automation outside the default self-hosted SDP stack.
---

Some signing providers need an operator-managed co-signer or automation process in addition to the
SDP API. Run those processes outside the default self-hosted SDP stack.

The self-hosted `compose.yml` stays unchanged by default. It starts the SDP API, the web app, the
docs app, the database, the cache, and the migrations. Provider co-signers are separate operational
services, because they usually have their own secret handling, identity, ingress, and availability
requirements.

## Production pattern

Use a managed container service for a provider-specific co-signer runtime. Google Cloud Run is one
example, and the equivalent service in your own cloud works the same way.

- Use the co-signer image and runtime that the provider or your operator team supplies.
- Store co-signer secrets in a cloud secret manager, not in the SDP compose file.
- Run the co-signer with a dedicated service account. Give that account read access to only the
  secrets it needs.
- Configure ingress and invoker IAM for the provider flow. Prefer private or authenticated ingress
  when the provider does not require a public callback.
- Set `minScale` to `1` when callback latency or provider availability matters. Use scale-to-zero
  only when a cold start is acceptable.
- Keep the development, staging, and production co-signers separated. Separate them by provider
  account, cloud project, service account, and secrets.
- Alert on failed signing attempts, container restarts, authentication failures, and stale or
  expired key material.

## Utila readiness

Utila is the provider that motivates this pattern. When Utila signer support lands, host the
co-signer as an external operator service, for example on Cloud Run. SDP keeps its API, web, docs,
database, and cache inside the normal self-hosted stack.

This page does not make Utila a live SDP signing provider. Do not set `SIGNING_PROVIDER=utila`
until the Utila signer integration adds that provider option and the required runtime
configuration.

Operator scaffolding for a Utila Cloud Run deployment lives in `infra/utila/cloud-run/`. That
scaffold hosts the co-signer endpoint before Utila becomes a default self-hosted service. You can
deploy your own co-signer image, protect the endpoint with Cloud Run IAM or runtime-level request
verification, and pass the resulting service URL and token into a custom SDP Utila integration.
