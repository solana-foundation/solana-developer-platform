title: External Co-Signers
description: Host provider-specific signing automation outside the default self-hosted SDP stack.

Some signing providers need an operator-managed co-signer or automation process
in addition to the SDP API. Run those processes outside the default self-hosted
SDP stack.

`infra/self-hosted/compose.yml` is intentionally unchanged by default. It starts
the SDP API, web app, docs app, database, cache, and migrations. Provider
co-signers are separate operational services because they usually have their own
secret handling, identity, ingress, and availability requirements.

## Production pattern

Use a managed container service such as Google Cloud Run, or the equivalent in
your cloud, for provider-specific co-signer runtimes.

- Use the provider- or operator-supplied co-signer image and runtime.
- Store co-signer secrets in a cloud secret manager, not in the SDP compose file.
- Run the co-signer with a dedicated service account that can read only the
  secrets it needs.
- Configure ingress and invoker IAM for the provider flow. Prefer private or
  authenticated ingress when the provider does not require a public callback.
- Set `minScale` to `1` when callback latency or provider availability matters;
  use scale-to-zero only when cold starts are acceptable.
- Keep development, staging, and production co-signers separated by provider
  account, cloud project, service account, and secrets.
- Alert on failed signing attempts, container restarts, authentication failures,
  and stale or expired key material.

## Utila

Utila is a supported SDP signing provider. The SDP API signs through your Utila
vault directly, using a Utila service account. Anything else your Utila setup
needs to approve or sign a transaction, such as a co-signer, runs outside the
SDP stack using the production pattern above.

### Configure the SDP API

In the [configurator](/docs/self-hosting/configurator), add **Utila** to the
deployment signing providers. `utila` is also an accepted `SIGNING_PROVIDER`
value. The configurator then asks for these variables:

| Variable | Required | Description |
|---|---|---|
| `UTILA_SERVICE_ACCOUNT_EMAIL` | Yes | Service account email, in the form `…@vault.….utilaserviceaccount.io`. |
| `UTILA_SERVICE_ACCOUNT_PRIVATE_KEY` | Yes | PKCS#8 private key PEM for the service account. Use escaped newlines in `.env`. |
| `UTILA_VAULT_ID` | Yes | The Utila vault SDP creates and signs wallets in. |
| `UTILA_WALLET_ID` | Yes | Utila wallet ID. |
| `UTILA_NETWORK` | Yes | `networks/solana-devnet` (default) or `networks/solana-mainnet`. |
| `UTILA_API_BASE_URL` | No | Defaults to `https://api.utila.io`. |
| `UTILA_POLL_INTERVAL_MS` | No | How often SDP polls a pending signature, in milliseconds. Defaults to `1000`. |
| `UTILA_MAX_POLL_ATTEMPTS` | No | How many times SDP polls before giving up. Defaults to `60`. |
| `UTILA_DESIGNATED_SIGNERS` | No | Comma-separated Utila user resources that sign SDP's requests. Defaults to `users/$UTILA_SERVICE_ACCOUNT_EMAIL`. |

SDP treats Utila as configured on the deployment once
`UTILA_SERVICE_ACCOUNT_EMAIL`, `UTILA_SERVICE_ACCOUNT_PRIVATE_KEY`, and
`UTILA_VAULT_ID` are set. Utila is a manual provider, so each organization also
needs it enabled: add
`{"sdp": {"providerOverrides": {"custody": {"utila": true}}}}` to the
organization's private metadata in the Clerk dashboard, the same way
[First Devnet Deployment](/docs/self-hosting/first-devnet-deployment) enables
the local signer. Merge it with any overrides already there.

When an organization sets up Utila, SDP creates a new Solana wallet inside the
configured vault. Additional wallets are created in the same vault.

### How signing works

For each transaction, SDP submits a signing request to Utila naming the
designated signers, without publishing it, then polls until Utila returns the
signed transaction. With the defaults, SDP waits for 60 polls one second apart,
about a minute, before the signing request fails. The designated signers must
approve or sign within that window.

If your Utila vault needs an operator-run co-signer to sign as a designated
signer, host it outside the SDP stack as described in
[Production pattern](#production-pattern). Operator scaffolding for running a
co-signer on Cloud Run lives in `infra/utila/cloud-run/`. Protect the endpoint
with Cloud Run IAM or runtime-level request verification.
