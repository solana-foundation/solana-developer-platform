SDP puts each of its modules behind one stable API in front of interchangeable providers. Operations use project-scoped authentication.

<ModuleTable />

## Background

Institutional capital is moving onchain: [$35 billion in tokenized real-world assets](https://app.rwa.xyz/) across public blockchains, [$3.2 billion of it on Solana](https://app.rwa.xyz/networks/solana), and [tokenized stocks](https://app.rwa.xyz/stocks) — where Solana settles most trading volume — as the fastest-growing slice.

Assets at this scale need regulated custody, enforceable compliance, and auditable controls. SDP provides them as one API, so bringing an asset onchain does not require a team of Solana developers.

### Unified Programming Interface

SDP puts one stable API in front of the Solana ecosystem's providers, so you integrate once and swap or add providers without changing your code. The same call works for every custody provider. The `provider` field is the only thing that changes.

<Tabs items={["JavaScript", "Python", "curl"]}>
<Tab value="JavaScript">
```javascript title="create-wallet.js"
const response = await fetch("https://api.solana.com/v1/wallets", {
  method: "POST",
  headers: {
    Authorization: "Bearer sk_test_...",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    provider: "privy",
    label: "Treasury wallet",
  }),
});
const wallet = await response.json();
```
</Tab>
<Tab value="Python">
```python title="create_wallet.py"
import requests

response = requests.post(
    "https://api.solana.com/v1/wallets",
    headers={"Authorization": "Bearer sk_test_..."},
    json={"provider": "privy", "label": "Treasury wallet"},
)
wallet = response.json()
```
</Tab>
<Tab value="curl">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/wallets \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{ "provider": "privy", "label": "Treasury wallet" }'
```
</Tab>

### Wallet Custody

Provision signing wallets through integrated custody providers, so your team never handles private keys. Hosted keys never leave the provider's MPC or TEE infrastructure and SDP only handles the signed transaction. Local development keys are encrypted at rest with `AES-256-GCM` using per-organization derived keys, and every signing request passes authentication, permission and allowed-operation checks before it executes.

- **Built on `@solana/keychain`**

   The unified Solana signing interface. Every custody backend is a keychain adapter behind the same signing API, which is what makes providers interchangeable.

- **[Grants by module](/docs/developing-with-sdp/manage-api-keys#grants-by-module)**

   Limit what an API key may do. A key holds an explicit list of actions, such as reading one module or executing in another, and every other route is refused before it runs.

- **Scoped custody configuration**

   Custody settings resolve per project, then organization, then environment, so different teams can run different providers side by side.
</Step>

### Onchain Transfers

SDP exposes unified endpoints for onchain transfers, built on official Solana program implementations like [Subscriptions](https://github.com/solana-program/subscriptions) and [Solana Pay](https://github.com/solana-foundation/pay). These power Recurring Payments, Payment Requests, and Batch Transfers within SDP.

<Tabs items={["Recurring Payments", "Payment Requests", "Batch Transfers"]}>
<Tab value="Recurring Payments">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/recurring-payments \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: recurring-subscriber-42" \
  -H "Content-Type: application/json" \
  -d '{
    "sourceCustodyWalletId": "cwlt_123",
    "counterpartyId": "cp_...",
    "counterpartyAccountId": "cpa_...",
    "token": "USDC",
    "amount": "25.00",
    "periodHours": 720
  }'
```
</Tab>
<Tab value="Payment Requests">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/requests \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "walletId": "privy_wallet_123",
    "token": "USDC",
    "amount": "25.00",
    "expiresAt": "2026-08-31T00:00:00.000Z"
  }'
```
</Tab>
<Tab value="Batch Transfers">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfer-batches \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: payroll-2026-06-30" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "payroll_2026_06_30",
    "sourceCustodyWalletId": "cwlt_example",
    "token": "USDC",
    "recipients": [
      {
        "externalId": "payroll_row_001",
        "counterpartyId": "cp_...",
        "counterpartyAccountId": "cpa_...",
        "amount": "25.00"
      }
    ]
  }'
```
</Tab>

### Audit Trails

Every sensitive operation is recorded automatically. Each entry captures the acting user or API key, the resource touched, success or failure, client IP, user agent, request id, and secret-redacted metadata, and is queryable per organization.

| Area                    | Recorded events                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------- |
| API keys                | Create, revoke, and rotate, for both organization and project-scoped keys          |
| Custody                 | Provider configuration, wallet provisioning, and credential lifecycle changes      |
| Transactions & signing  | Signing requests, submissions, and failed submissions                              |
| Organization & access   | Members, invitations, projects, and project membership             |
| Counterparties          | Counterparty and Counterparty Account changes                                      |
