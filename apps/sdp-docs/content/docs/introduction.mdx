SDP gives you tokenization, custody, payments, and compliance through one API. The API stays the same
when you change providers. Every operation authenticates against a project.

| Module | What it does |
| --- | --- |
| **Issuance** | Deploy, mint, burn, freeze, pause, and seize tokens built on Token-2022 |
| **Custody** | Provision and operate Solana wallets through interchangeable custody providers |
| **Payments** | Move funds onchain: transfers, batches, recurring payments, payment requests, and ramps |
| **Compliance** | Screen wallets and transactions against your regulatory program |

## Background

Institutional capital is moving onchain. Public blockchains now hold
[$35 billion in tokenized real-world assets](https://app.rwa.xyz/), and
[$3.2 billion of that sits on Solana](https://app.rwa.xyz/networks/solana).
[Tokenized stocks](https://app.rwa.xyz/stocks) grow fastest, and Solana settles most of their
trading volume.

Assets at this scale need regulated custody, enforceable compliance, and auditable controls. SDP
gives you all three through one API. You do not need a team of Solana developers to bring an asset
onchain.

### One interface for every provider

SDP puts one API in front of the providers in the Solana ecosystem. You integrate once. You can
then add a provider, or change to another one, without changing your code.

The onramp call below works for every ramp provider. Only the `provider` field changes.

<Tabs items={["JavaScript", "Python", "curl"]}>
<Tab value="JavaScript">
```javascript title="onramp-quote.js" rotate-providers
const response = await fetch(
  "https://api.solana.com/v1/payments/ramps/onramp/quote",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      provider: "moonpay",
      counterpartyId: "cp_...",
      destinationCustodyWalletId: "cwlt_...",
      assetRail: "usdc.solana",
      fiatCurrency: "USD",
      fiatAmount: "100.00",
    }),
  },
);
const quote = await response.json();
```

### Wallet custody

Create signing wallets through a custody provider. Your team never handles a private key.

A hosted key never leaves the provider's MPC or TEE infrastructure. SDP receives only the signed
transaction. SDP encrypts local development keys at rest with `AES-256-GCM`, using a key derived
per organization. Every signing request passes a policy check and a permission check before it
runs.

- **Built on `@solana/keychain`**

   `@solana/keychain` is the common signing interface for Solana. Each custody provider is an
   adapter behind that interface. This is what lets you change providers.

- **[Wallet policies](/docs/wallet-operations/policies)**

   A policy limits how a wallet moves funds. It can restrict destinations, cap amounts, allow or
   deny operations, and require an approval. SDP applies the policy before the operation runs.

- **Custody settings resolve by scope**

   SDP reads custody settings from the project first, then the organization, then the environment.
   Two teams can therefore run two different providers side by side.
</Step>

### Issuance and compliance with Token-2022

Create a token from a template, such as a stablecoin or a tokenized security. You can also
configure your own token with Token-2022 extensions. Deploy the token, then mint, burn, and manage
its supply from the dashboard or the API.

The same extensions make compliance enforceable onchain. You can freeze one balance, pause all
transfers, seize tokens, and manage the token's **Token Access Control** list. Some compliance
actions accept a reason or a memo for the audit trail. Each action is one POST to the same token
endpoints.

### Ramps and onchain transfers

SDP gives you one set of endpoints for onchain transfers and for ramps, across every provider. They
build on the official Solana programs
[Subscriptions](https://github.com/solana-program/subscriptions) and
[Solana Pay](https://github.com/solana-foundation/pay). SDP uses these programs for recurring
payments, payment requests, and batch transfers.

<Tabs items={["Recurring Payments", "Payment Requests", "Batch Transfers"]}>
<Tab value="Recurring Payments">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/recurring-payments \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "sourceCustodyWalletId": "cwlt_123",
    "counterpartyId": "cp_...",
    "counterpartyAccountId": "cpa_...",
    "token": "USDC",
    "amount": "25.00",
    "periodHours": 720
  }'
```
</Tab>
<Tab value="Payment Requests">
```bash title="Terminal"

  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "walletId": "privy_wallet_123",
    "counterpartyId": "cp_...",
    "token": "USDC",
    "amount": "25.00",

```
</Tab>

```bash title="Terminal"
      }
    ]
  }'
```

The same API covers onramps and offramps. Rate estimates, quotes, and settlement behave the same way
for every provider and every corridor.

Money can therefore enter as fiat, stay onchain as a token you issued, and leave again as fiat. You
get the full cycle, from issuance to circulation to redemption, without a separate integration for
each provider.

See [Payments](/docs/payments) for transfers. See [Ramps](/docs/payments/ramps) for the supported
providers, currencies, and corridors.

### Audit trails

SDP records every sensitive operation. You can query the records for your organization.

Each entry holds the user or API key that acted, the resource it touched, and whether the operation
succeeded. It also holds the client IP address, the user agent, the request ID, and metadata with
the secrets removed.

| Area                    | Recorded events                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------- |
| API keys                | Create, revoke, and rotate, for both organization and project-scoped keys          |
| Token issuance          | Deploy, mint, burn, force-burn, supply changes, and authority updates              |
| Compliance actions      | Freeze, unfreeze, pause, unpause, seize, and Token Access Control changes          |
| Custody                 | Provider configuration, wallet provisioning, and credential lifecycle changes      |
| Transactions & signing  | Signing requests, submissions, and failed submissions                              |
| Organization & access   | Members, invitations, projects, project membership, and login sessions             |
| Counterparties & assets | Counterparty and Counterparty Account changes, asset profile changes               |
