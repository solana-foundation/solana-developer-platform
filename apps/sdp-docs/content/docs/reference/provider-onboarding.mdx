This page is for a vendor who wants to contribute an infrastructure provider integration to SDP. It
covers the intake forms, the evaluation criteria, and what the contributed pull request must
contain.

This page is not an activation guide. It does not explain how to enable an existing provider for
your organization, and it does not explain how to configure a provider on a self-hosted deployment.
If you arrived here looking for either of those, see
[Ramp providers](/docs/payments/ramps-providers) for how SDP checks provider availability on every
call, and see the
[self-hosting environment reference](/docs/self-hosting/env-reference) for the variables a
self-hosted deployment reads.

SDP supports infrastructure provider integrations across custody, RPC, compliance, and ramps. SDP
adds more integration categories as the product expands.

An onboarded provider appears as an available integration. SDP does not endorse or recommend it.
Each institution that uses SDP is responsible for its own provider due diligence.

## Categories and intake forms

Select the category that matches your integration. Complete the intake form, and review the
criteria, before you open a pull request.

| Category | Intake form | Criteria |
| --- | --- | --- |

| RPC infrastructure | [Complete RPC intake](https://solanafoundation.typeform.com/to/cq5m65jI) | [Download RPC criteria PDF](/provider-onboarding/rpc-providers.pdf) |

Contact the SDP team before you open a pull request if your integration is for compliance, or for
another infrastructure category without a published intake.

## Onboarding steps

1. Review the criteria PDF for your category.
2. Complete the matching intake form.
3. Provide sandbox or playground API access.
4. Share your documentation, test credentials, supported Solana clusters, rate limits, and sandbox
   limitations.
5. Build the SDP integration, with tests and documentation.
6. Open a pull request that links to the intake submission or to the tracking issue.

The SDP team reviews intake completeness within five business days. Gate evaluation usually takes
one to three weeks. The exact time depends on the category, the completeness of the documentation,
and the technical validation the category requires.

## Evaluation

Each category uses the finalized criteria linked above. Every review starts with the hard gates. A
scored evaluation follows, where one applies.

SDP evaluates the following:

- Solana compatibility for the category.
- Stable sandbox or playground access.
- Clear API and integration documentation.
- Predictable error handling and testability.
- Operational readiness and support.
- The regulatory, compliance, or security posture that the category requires.

The SDP team can track a provider that does not clear the required gates, for future support. SDP
does not present that provider as available until the gaps are resolved.

A provider that clears evaluation becomes available according to the deployment's configuration.
It is either generally available to every organization, or it is gated behind a per-organization
Manual Provider Activation. The gated path applies when commercial or operational onboarding is
still required.

## Access requirements

Provide access that supports repeatable validation, including:

- Sandbox API keys, or equivalent credentials.
- Test accounts, wallets, endpoints, or settlement routes, where the flow requires them.
- The Solana clusters you support.
- Known rate limits, feature conditions, and sandbox limitations.
- A technical support contact for the review.

## Pull request expectations

An SDP infrastructure provider contribution usually includes:

- Provider metadata and capability registration.
- API support for setup, configuration, and the runtime operations of the category.
- Dashboard support, where it applies.
- Tests for setup, success paths, failure states, disabled configuration, and missing credentials.
- User-facing documentation for setup, sandbox behavior, and provider limits.

Open the pull request after your intake is complete. You can also open it after the SDP team
creates a tracking issue while the intake is being finalized.
