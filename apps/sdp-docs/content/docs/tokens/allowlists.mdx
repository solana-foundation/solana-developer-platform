**Token Access Control** decides who may hold or receive your token. This page covers its
`allowlist` mode.

A token created with `requiresAllowlist: true` enforces a list of approved destination addresses.
That check runs on the issuance flows that respect the allowlist, such as minting and
administrative transfers. The `tokenized-security` template turns the mode on by default.

Token Access Control is not the same thing as two other lists in SDP. The transfer allowlist of a
wallet belongs to a wallet policy. The Platform Allowlist controls admission to deployment. Keep
each one separate.

## Prerequisites

- A token created with `requiresAllowlist` enabled
- The `tokens:write` permission on the API key

## How it works

<HowItWorks>

<Step number={1} title="Enable the allowlist">

You configure the allowlist when you create the token. Decide before you create it whether your
token needs one. You cannot change the setting after the token is deployed.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Open the **Create token** flow.
2. Open the operational settings.
3. Turn **Allowlist** on.

The `tokenized-security` template turns the allowlist on by default. You can change that setting
while the token is still a draft.

After the token is deployed, the **Operations** tab of the token detail page shows **Approved
recipients**. That section holds an Address field and a Label field. The Control Lists panel next
to it tracks the entry count and the frozen account count.

![Operational settings during token creation, with the Allowlist transfer control turned on](/images/tokens/token-create-settings.png)

</Tab>
<Tab value="API">

Set `requiresAllowlist: true` when you create the token:

```typescript title="enable-allowlist.ts"
body: JSON.stringify({
  name: "Acme Security",
  symbol: "ACMES",
  decimals: 8,
  template: "tokenized-security",
  requiresAllowlist: true,
  isMintable: true,
  isFreezable: true,
}),
```

After the deployment, SDP enforces the allowlist on the issuance flows that respect it.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Add an address">

Add a wallet address to the allowlist before you mint to it. Add it before you use it as the
destination of an administrative transfer.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Open the token detail page.
2. Open the **Operations** tab.
3. Select **Approved recipients**.
4. Enter the wallet address.
5. Enter a label. This field is optional.
6. Select **Approve recipient**.

SDP enforces the address on the next operation that checks the allowlist.

For an onchain list, SDP uses its authority wallet when exactly one custody wallet matches. If
several custody records match, select the signer in the confirmation dialog. A database-only list
needs no signer.

![Approved recipients section with empty Address and Label fields, ready for a new entry](/images/tokens/allowlist-empty.png)

The new entry then appears below the form, with a **Remove entry** control.

![Approved recipients list containing the new entry and its Remove entry control](/images/tokens/allowlist-entry-added.png)

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/allowlist \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "address": "7xKXz...9fGh",
    "label": "Treasury wallet"
  }'
```

```typescript title="add-allowlist-entry.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/allowlist",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ address: "7xKXz...9fGh", label: "Treasury wallet" }),
  }
);
// res.data.entry.id — save this to remove the entry later
```

For an onchain addition, the JSON body accepts an optional `signingCustodyWalletId`. That value is
an exact `cwlt_…` record ID.

The wallet must control the current authority of the list. That authority can differ from the
freeze authority of the token. Without the selector, several matching custody records return
`409`. Selecting a wallet does not bypass the permission checks or the runtime availability
checks.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Review the list">

Check which addresses are approved. Review the list before you mint to a new destination, and
during a compliance audit.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The **Approved recipients** section shows every approved address, its label, and the date SDP
added it.

Use the search field to find an address by label or by public key.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl "https://api.solana.com/v1/issuance/tokens/tok_abc123/allowlist?search=So1&label=Treasury" \
  -H "Authorization: Bearer sk_test_..."
```

```typescript title="list-allowlist.ts"
const { data, meta } = await res.json();
// meta: { total, page, pageSize, hasMore }
```

Query parameters:

- `page`, `pageSize` — pagination (`pageSize` max 500, default 50).
- `search` — contains-style match over the entry address **and** label. A blank value is treated as no filter.
- `label` — restrict to entries with this exact label.

The search and the label filter both run on the server, across the whole list. The results are
therefore not limited to the current page.

To populate a label filter, fetch the distinct labels in use. The response also returns `total`,
the unfiltered entry count, for a summary display.

```bash
curl https://api.solana.com/v1/issuance/tokens/tok_abc123/allowlist/labels \
  -H "Authorization: Bearer sk_test_..."
```

```typescript
const { data } = await res.json();
// data: { labels: ["Market maker", "Treasury"], total: 42 }
```

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={4} title="Remove an address">

Remove an address when the compliance status of a holder changes. Removal does not affect the
tokens that the holder already owns. It blocks only the future flows that enforce the allowlist.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Open the **Operations** tab of the token detail page.
2. Select **Approved recipients**.
3. Select **Remove entry** next to the address.
4. Choose the signer in the confirmation dialog. This step applies to an onchain list when several
   custody wallets match.

The list and its count refresh after a successful removal.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X DELETE \
  https://api.solana.com/v1/issuance/tokens/tok_abc123/allowlist/alw_abc123 \
  -H "Authorization: Bearer sk_test_..."
```

Use the `entry.id` that SDP returned when you added the address.

For an onchain removal, pass the optional exact signer as a query parameter:
`?signingCustodyWalletId=cwlt_example`.

To find the current authority of the list, request
`GET /v1/issuance/tokens/{tokenId}?includeAllowlistAuthority=true` and read
`data.allowlistAuthority`. That field is `null` for a database-only list.

Match that address against your wallets. Do not infer it from the freeze authority of the token.

</Tab>
</Tabs>
</StepPanel>

</Step>

</HowItWorks>

## Typical workflow for a tokenized security

1. Create the token with `requiresAllowlist: true` and the template `tokenized-security`.
2. [Deploy the token](/docs/tokens/deploy-a-token).
3. Collect wallet addresses from investors who passed KYC.
4. Add each verified address to the allowlist.
5. [Mint tokens](/docs/tokens/mint-and-burn) to the allowlisted addresses.
6. Remove an address when the compliance status of its holder changes.
