**Token Access Control** decides who may hold or receive your token. This page covers its `allowlist` mode (`requiresAllowlist: true`): only listed addresses can receive mints and force transfers. It's on by default for `tokenized-security` tokens.

The token's list is separate from an API key's [grants](/docs/developing-with-sdp/manage-api-keys#grants-by-module), which limit what the key may do.

## Prerequisites

- A token with `requiresAllowlist` on
- The `issuance.enforce` grant to add or remove entries, or `issuance.read` to list them

## How it works

<HowItWorks>

<Step number={1} title="Enable the allowlist">

Choose the access list before you deploy. You can change `requiresAllowlist` on a draft, but after deployment the API refuses the change with `400`.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

In **Create a draft**, on **What this token can do**, set **Access list** to **Allowlist · only named addresses may hold**. A stablecoin offers **Blocklist** or **Allowlist**; a non-security digital token offers **Allowlist** or **Off**.

On the token page, the **Compliance** tab shows **Approved recipients**, with the entry count and the frozen accounts.

<img src="/docs/images/tokens/token-create-settings.png" alt="What this token can do step with every control on and Access list set to Allowlist" width="693" height="594" style={{ display: "block", maxWidth: "100%", height: "auto", margin: "0 0 18px" }} />

</Tab>
<Tab value="API">

Set `requiresAllowlist: true` when you create the token. `tokenized-security` turns it on by default; with `false`, that template uses a blocklist instead.

```typescript title="enable-allowlist.ts"
body: JSON.stringify({
  name: "Acme Security",
  symbol: "ACMES",
  decimals: 8,
  template: "tokenized-security",
  requiresAllowlist: true,
  isMintable: true,
  isFreezable: true,
}),
```

SDP creates the onchain list when the token deploys and enforces it from then on.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Add an address">

Add an address before you force-transfer tokens to it. Mints check the list as follows:

- With an onchain list, a mint to an unlisted address adds it to the list first. An address you removed is refused with `403 DESTINATION_REVOKED`.
- With a list kept only in SDP, a mint to an unlisted address fails with `403 NOT_ON_TOKEN_ALLOWLIST`.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

On the token page, open **Compliance**. Under **Add an address**, enter the **Address** and an optional **Label**, then click **Add entry**.

For an onchain list, SDP signs with the list's authority wallet. If several custody wallets match, choose the signer in the dialog. A list kept only in SDP needs no signer.

![Compliance tab with no approved recipients yet and an empty Add an address form](/images/tokens/allowlist-empty.png)

The entry appears under **Approved recipients**, with a trash button that removes it.

![Approved recipients listing the Treasury wallet with its label, the date added and a trash button](/images/tokens/allowlist-entry-added.png)

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/control-list \
  -H "Authorization: Bearer sf_..." \
  -H "Content-Type: application/json" \
  -d '{
    "address": "7xKXz...9fGh",
    "label": "Treasury wallet"
  }'
```

```typescript title="add-allowlist-entry.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/control-list",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sf_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ address: "7xKXz...9fGh", label: "Treasury wallet" }),
  }
);
const { data } = await res.json();
// data.entry.id: keep it to remove the entry later
```

For an onchain list, the body takes an optional `signingCustodyWalletId` (a `cwlt_…` id). It must control the list's current authority, which can differ from the token's freeze authority. Without it, several matching custody wallets return `409`. Naming a wallet doesn't skip permission or availability checks.

</Tabs>
</StepPanel>

<Step number={3} title="Review the list">

Check which addresses are approved, before minting to a new destination or during a compliance audit.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

**Compliance** lists each address with its **Label** and the date it was **Added**, 25 per page.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl "https://api.solana.com/v1/issuance/tokens/tok_abc123/control-list?search=So1&label=Treasury" \
  -H "Authorization: Bearer sf_..."
```

```typescript title="list-allowlist.ts"
const { data, meta } = await res.json();
// data: the entries
// meta: { total, page, pageSize, hasMore }
```

Query parameters:

- `page`, `pageSize`: pagination (`pageSize` defaults to 50, max 500)
- `search`: contains-style match over the address **and** the label, 1 to 100 characters
- `label`: only entries with exactly this label

Search and the label filter run over the whole list, not just the current page.

To fill a label filter, fetch the labels in use. The response returns `data.labels` and the unfiltered `data.total`:

<Step number={4} title="Remove an address">

Remove an address when the holder's compliance status changes. Existing holdings are unaffected; the address just can't receive the token through mints or force transfers.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

On **Compliance**, click the trash button beside the address. For an onchain list with several matching wallets, choose the signer in the dialog. The list and its count refresh.

</Tab>
<Tab value="API">

<ApiExample operation="remove-token-allowlist-entry" />

Use the entry `id` (`tal_…`) from the add response. A removal returns `204`. If the onchain removal fails, the entry stays active and you can retry.

For an onchain list, pass the signer as a query parameter: `?signingCustodyWalletId=cwlt_example`. To find the list's current authority, request `GET /v1/issuance/tokens/{tokenId}?includeAllowlistAuthority=true` and read `data.allowlistAuthority` (`null` for a list kept only in SDP). Match that address against your wallets; don't infer it from the freeze authority.

</Tab>
</Tabs>
</StepPanel>

</Step>

## Typical workflow for a tokenized security

1. Create the token with template `tokenized-security`; the allowlist is on by default.
2. [Deploy the token](/docs/tokens/deploy-a-token).
3. Collect wallet addresses from KYC-verified investors.
4. Add each verified address to the allowlist.
5. [Mint tokens](/docs/tokens/mint-and-burn) to listed addresses.
6. Remove addresses when their compliance status changes.
