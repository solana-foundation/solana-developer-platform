After [creating a token](/docs/tokens/create-a-token), deploy it onchain. Deployment creates the mint account on Solana and signs the deployment with the exact SDP Wallet selected for execution.

## Prerequisites

- A token in `pending` status
- `tokens:write` permission on the API key
- The exact SDP Wallet `id` returned by `GET /v1/wallets` (for example, `cwlt_*`)

## How it works

<HowItWorks>

<Step number={1} title="Open the deploy action">

Locate the token you want to deploy. Deployment is irreversible — the mint account and its configured authorities are created onchain.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

In the **Issuance** list, open the draft token.

The **Deploy** button is in the token header. It stays disabled while you have unsaved changes in the token's **Settings**; save or discard them first.

</Tab>
<Tab value="API">

You need the `tokenId` returned when you created the token. If you don't have it, list your tokens:

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens \
  -H "Authorization: Bearer sk_test_..."
```

Note the token `id` (e.g., `tok_abc123`) — required for all deploy and post-deploy calls. Also list your wallets and use the wallet record's `id`, not its provider-specific `walletId` or public key:

```bash title="Terminal"
curl https://api.solana.com/v1/wallets \
  -H "Authorization: Bearer sk_test_..."
```

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Deploy the token">

SDP signs and submits the deploy transaction using `signingCustodyWalletId`. If you supply it here, it overrides the pending draft's execution wallet; if you omit it, SDP uses the value stored on the draft. One of those values is required. An override changes the deployment signer and historical attribution, but it does not rewrite immutable authority values already captured in the token's configuration.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

Click **Deploy**. The **Deploy token** dialog shows the signing wallet that will authorize the transaction. Review it, then click **Deploy token**.

SDP submits the transaction to Solana. A "Deploy transaction finalized." toast appears when deployment completes.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/deploy \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: deploy-acme-001" \
  -d '{"signingCustodyWalletId":"cwlt_abc123"}'
```

```typescript title="deploy-token.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/deploy",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",
      "Idempotency-Key": "deploy-acme-001",
    },
    body: JSON.stringify({ signingCustodyWalletId: "cwlt_abc123" }),
  }
);
const { data } = await res.json();
// data.token.mintAddress — the onchain mint address
```

Always pass an `Idempotency-Key` — retrying with the same key after a network error prevents double-deployment.

The deployment wallet holds the mint authority. To give the metadata, freeze, or permanent-delegate authority to other wallets, pass their SDP Wallet IDs in `authorityCustodyWalletIds` (`metadata`, `freeze`, `permanentDelegate`); omitted roles keep their template defaults. `feePayment` is `sponsored` (default) or `wallet`.

SDP checks the deploy against the deployment wallet's policy before signing. A `deny` returns `403 FORBIDDEN`; a deploy held for approval returns `202` with error code `SIGNING_PENDING` and `error.details.approvalRequestId`. A separate metadata wallet must be allowed outright: if its policy denies or holds the deploy, the request returns `403`. See [Wallet policies](/docs/wallet-operations/policies).

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Confirm deployment">

Once the transaction is confirmed, the token is active and ready for minting and transfers.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The token header now shows the mint address and the token's status. The actions in the **Operations** section, such as **Mint tokens**, become available, and the **Activity** section lists the deploy transaction.

</Tab>
<Tab value="API">

The deploy response includes the confirmed state:

```typescript title="deploy-token.ts"
// data.token.status      — "active"
// data.token.mintAddress — e.g., "AcMeXYZ..."
// data.token.signingCustodyWalletId — exact wallet used for deployment
```

After deployment, `signingCustodyWalletId` is historical deployment attribution. Mint and admin actions resolve their current on-chain authority, while a standard burn uses its exact source wallet; none use the deployment wallet as a fallback.

Fetch the token at any time to verify:

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens/tok_abc123 \
  -H "Authorization: Bearer sk_test_..."
```

</Tab>
</Tabs>
</StepPanel>

</Step>
