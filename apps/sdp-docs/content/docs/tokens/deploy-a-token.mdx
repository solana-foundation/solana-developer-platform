---
title: Deploy a token
description: Write a token draft to Solana and confirm the mint account it creates.

  - Open the deploy action
  - Deploy the token
  - Confirm the deployment
---

After you [create a token](/docs/tokens/create-a-token), deploy it onchain. The deployment creates
the mint account on Solana. The custody wallet you select signs that transaction.

## Prerequisites

- A token draft with the status `pending`
- The exact SDP wallet `id` that `GET /v1/wallets` returns, for example `cwlt_abc123`

## How it works

<HowItWorks>

<Step number={1} title="Open the deploy action">

Find the draft that you want to deploy. Deployment is irreversible. SDP creates the mint account
and its configured authorities onchain, and you cannot undo that.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Open the **Issuance** list.
2. Select the token that carries a **Draft** badge.

The token detail page shows a **Deploy** control. The same control appears in the fund management
panel.

![Token detail page for a draft, showing the status Not deployed and the Deploy control](/images/tokens/token-detail-pending.png)

</Tab>
<Tab value="API">

You need the `tokenId` that SDP returned when you created the token. If you do not have it, list
your tokens:

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens \
  -H "Authorization: Bearer sk_test_..."
```

Note the token `id`, for example `tok_abc123`. Every deploy call and every later call needs it.

List your wallets as well. Use the `id` of the wallet record. Do not use the provider-specific
`walletId`. Do not use the public key.

```bash title="Terminal"
curl https://api.solana.com/v1/wallets \
  -H "Authorization: Bearer sk_test_..."
```

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Deploy the token">

SDP signs and submits the deploy transaction with the wallet in `signingCustodyWalletId`.

If you supply that field here, it replaces the execution wallet stored on the draft. If you omit
it, SDP uses the value stored on the draft. One of the two values is required.

An override changes the deployment signer and the historical attribution. It does not rewrite the
immutable authority values already captured in the configuration of the token.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Select **Deploy**. A dialog shows the signer wallet that authorizes the transaction.
2. Check the wallet ID and the public key in that dialog.
3. Select **Deploy now**.
4. Select **Deploy now** again in the confirmation prompt. That prompt asks you to confirm the
   onchain submission.

![Deploy dialog listing the signer wallet ID and public key that will authorize the deployment](/images/tokens/token-deploy-modal.png)

![Confirmation prompt asking you to confirm the onchain deploy submission](/images/tokens/token-deploy-confirm.png)

SDP submits the transaction to Solana and polls for confirmation. The page updates when the
deployment completes.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/deploy \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: deploy-acme-001" \
  -d '{"signingCustodyWalletId":"cwlt_abc123"}'
```

```typescript title="deploy-token.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/deploy",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",
      "Idempotency-Key": "deploy-acme-001",
    },
    body: JSON.stringify({ signingCustodyWalletId: "cwlt_abc123" }),
  }
);
const { data } = await res.json();
// data.token.mintAddress — the onchain mint address
```

Always pass an `Idempotency-Key`. A retry with the same key after a network error prevents a second
deployment.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Confirm the deployment">

When the network confirms the transaction, the token is active. You can then mint it and transfer
it.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The status badge changes from **Not deployed** to the onchain mint address. The detail page then
shows the Mint and Burn actions in the Operations tab. The Transactions table shows the confirmed
deploy transaction.

![Deployed token detail page with the mint address, the Operations tab, and a confirmed deploy transaction](/images/tokens/token-deployed.png)

</Tab>
<Tab value="API">

The deploy response includes the confirmed state:

```typescript title="deploy-token.ts"
// data.token.status      — "active"
// data.token.mintAddress — e.g., "AcMeXYZ..."
// data.token.signingCustodyWalletId — exact wallet used for deployment
```

After the deployment, `signingCustodyWalletId` records historical deployment attribution only.

Mint and administrative actions resolve their current onchain authority. A standard burn uses its
exact source wallet. No later action falls back to the deployment wallet.

Fetch the token at any time to verify its state:

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens/tok_abc123 \
  -H "Authorization: Bearer sk_test_..."
```

</Tab>
</Tabs>
</StepPanel>

</Step>

</HowItWorks>
