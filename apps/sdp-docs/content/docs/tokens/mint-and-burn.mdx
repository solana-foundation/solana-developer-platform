After [deploying a token](/docs/tokens/deploy-a-token), mint new supply to any address, and burn supply that a custody wallet holds. A force burn removes tokens from any holder without their signature, using the permanent delegate.

## Prerequisites

- A deployed token with status `active`. A paused token refuses mint and burn with `400 TOKEN_PAUSED`.
- The `issuance.execute` grant, or `issuance.enforce` for a force burn
- For a standard burn, the SDP wallet `id` (`cwlt_…`, from `GET /v1/wallets`) that holds the tokens

## How it works

<HowItWorks>

<Step number={1} title="Select the token and action">

Open the token. Mint and burn both live on its **Operations** tab.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

In **Issuance**, open a token marked **Live onchain** and go to **Operations**.

The **Supply** block shows the **Issued supply** with **Mint** and **Burn**, the **Supply cap**, and the **Mint authority**. **Mint tokens** on **Overview** opens the same mint form.

![Token Operations tab showing Mint and Burn actions](/images/tokens/token-deployed.png)

</Tab>
<Tab value="API">

Supply operations share one URL pattern:

```text title="Endpoints"
POST /v1/issuance/tokens/{tokenId}/mint
POST /v1/issuance/tokens/{tokenId}/burn
POST /v1/issuance/tokens/{tokenId}/force-burn
```

`amount` is a decimal string in **UI units**: `"1"` is one token and `"1.5"` is one and a half. SDP converts it to base units with the token's `decimals`.

`signingCustodyWalletId` is always the SDP wallet `id`, never a provider `walletId` or a public key. A standard burn requires it: that wallet holds the tokens and signs. For mint and force burn it's optional, but a wallet you name must hold the current mint or permanent-delegate authority. Without one, exactly one custody wallet must hold that live authority, or the call returns `409`. No call falls back to the deployment wallet.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Mint tokens">

Issue new tokens to a destination address. SDP creates the destination's token account if it doesn't exist.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

Click **Mint**. Under **Issued supply**, fill in:

- **Destination**: a Solana address, or one of the project's wallets
- **Amount**: in token units, such as `1.5`
- **Memo**: optional, recorded onchain

If several wallets hold the mint authority, choose the signing wallet first. Click **Mint tokens** (it shows the amount once you enter one), then **Mint now** in the confirmation.

![Mint Tokens modal with amount and memo filled in](/images/tokens/mint-modal-filled.png)

![Mint tokens confirmation dialog: click Mint now to submit the transaction on-chain](/images/tokens/mint-confirm.png)

The toast reads "Mint transaction finalized." and **Transactions** lists the mint.

![Operations tab showing confirmed mint entry and Mint transaction finalized toast](/images/tokens/mint-confirmed.png)

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/mint \
  -H "Authorization: Bearer sf_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: mint-001" \
  -d '{
    "signingCustodyWalletId": "cwlt_abc123",
    "mint": {
      "destination": "7xKXz...9fGh",
      "amount": "1000",
      "memo": "Initial distribution"
    }
  }'
```

```typescript title="mint-tokens.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/mint",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sf_...",
      "Content-Type": "application/json",
      "Idempotency-Key": "mint-001",
    },
    body: JSON.stringify({
      signingCustodyWalletId: "cwlt_abc123",
      mint: {
        destination: "7xKXz...9fGh",
        amount: "1000",
        memo: "Initial distribution",
      },
    }),
  }
);
```

The response holds the `transaction` and the destination's `tokenAccount`. A mint past the token's `maxSupply` fails with `400 MAX_SUPPLY_EXCEEDED`. On a token with an access list, [Allowlists](/docs/tokens/allowlists) explains which destinations a mint accepts.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Burn tokens">

Reduce supply by burning tokens that a custody wallet holds. To burn from any other holder, use a force burn.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

Click **Burn**. Under **Issued supply**, enter the **Source**: a project wallet that holds the token, or its token account.

![Burn Tokens modal with empty source field](/images/tokens/burn-modal-empty.png)

![Burn Tokens modal with source wallet dropdown open](/images/tokens/burn-modal-source.png)

Enter the **Amount** and an optional **Memo**. Burning can't be undone. Click **Burn tokens**, then **Burn now** in the confirmation.

![Burn Tokens modal filled with source, amount, and memo](/images/tokens/burn-modal-filled.png)

![Burn tokens confirmation dialog](/images/tokens/burn-confirm.png)

The toast reads "Burn transaction finalized." and **Transactions** lists the burn.

![Operations tab showing confirmed burn transaction and finalized toast](/images/tokens/burn-confirmed.png)

For a force burn, open **Recovery** on **Operations** and click **Force burn**. It needs the permanent delegate; see [Freeze and Compliance](/docs/tokens/freeze-and-compliance).

</Tab>
<Tab value="API">

**Burn from a custody wallet.** The `source` must be the signing wallet or its token account, or the call fails with `400 INVALID_BURN_SOURCE`. A wallet that holds too little gets `400 INSUFFICIENT_TOKEN_BALANCE`.

```typescript title="burn-tokens.ts"
await fetch("https://api.solana.com/v1/issuance/tokens/tok_abc123/burn", {
  method: "POST",
  headers: {
    Authorization: "Bearer sf_...",
    "Content-Type": "application/json",
    "Idempotency-Key": "burn-001",
  },
  body: JSON.stringify({
    signingCustodyWalletId: "cwlt_abc123",
    burn: { source: "3xYZa...2aBc", amount: "250", memo: "Redemption" },
  }),
});
```

**Force burn from any holder** (needs `issuance.enforce`):

```typescript title="force-burn-tokens.ts"
await fetch("https://api.solana.com/v1/issuance/tokens/tok_abc123/force-burn", {
  method: "POST",
  headers: {
    Authorization: "Bearer sf_...",
    "Content-Type": "application/json",
    "Idempotency-Key": "force-burn-001",
  },
  body: JSON.stringify({
    signingCustodyWalletId: "cwlt_abc123",
    forceBurn: { source: "3xYZa...2aBc", amount: "250", memo: "Compliance action" },
  }),
});
```

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={4} title="Refresh supply">

The token's `totalSupply` is cached. Refresh it from the mint account when you need the onchain value.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The dashboard reloads the token after each confirmed operation, so **Issued supply** updates on its own. **Transactions** lists every operation (deploy, mint, burn) with its status.

![Operations tab showing confirmed burn, mint, and deploy transactions](/images/tokens/operations-history.png)

Reload the page if the supply looks stale.

</Tab>
<Tab value="API">

<ApiExample operation="refresh-token-supply" />

Call it after a mint or burn whose outcome you didn't see, such as a timeout: it reconciles the cached supply with the chain. It's rate-limited per key and per organization (`429 RATE_LIMITED`).

</Tab>
</Tabs>
</StepPanel>
