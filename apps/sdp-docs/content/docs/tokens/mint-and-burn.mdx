After you [deploy a token](/docs/tokens/deploy-a-token), you can mint new tokens to any address.
You can also burn tokens from an account that you control. Force-burn removes tokens from any
holder account without the signature of that holder.

## Prerequisites

- A deployed token with the status `active`
- The `tokens:write` permission on the API key, or `tokens:admin` for force-burn
- For a standard burn, the exact SDP wallet `id` that `GET /v1/wallets` returns, for example
  `cwlt_abc123`

## How it works

<HowItWorks>

<Step number={1} title="Select the token and the action">

Open the token that you want to manage. Mint and burn both start from the token detail page.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Open the **Issuance** list.
2. Select an active token.

The fund management panel shows the current supply. It offers two actions, **Mint** and **Burn**.

![Token Operations tab with the current supply and the Mint and Burn actions available](/images/tokens/token-deployed.png)

</Tab>
<Tab value="API">

All supply operations share this URL pattern:

```text title="Endpoints"
POST /v1/issuance/tokens/{tokenId}/mint
POST /v1/issuance/tokens/{tokenId}/burn
POST /v1/issuance/tokens/{tokenId}/force-burn
```

The `amount` field is a decimal string in display units. `"1"` means one token. `"1.5"` means one
and a half tokens. SDP converts the value to onchain base units with the `decimals` of the token.

`signingCustodyWalletId` always means the exact SDP wallet `id`. It is never a provider-specific
`walletId` and never a public key.

A standard burn requires the field, because that wallet owns the source and signs for it. Mint and
force-burn treat the field as optional. When you do supply it, the wallet must control the current
mint authority or the current permanent-delegate authority.

When you omit the field, SDP requires exactly one accessible wallet to match that live authority.
A later action never falls back to the deployment wallet of the token.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Mint tokens">

Issue new tokens to a destination address. SDP derives the associated token account from that
address.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Select **Mint**. A dialog shows the signer wallet and a destination picker.
2. Select the destination wallet, or enter the destination address.
3. Enter the amount in display units, for example `1.0`.
4. Enter a memo. This field is optional, and SDP records the memo onchain.
5. Select **Mint tokens**.
6. Select **Mint now** in the confirmation prompt to submit the transaction onchain.

![Mint dialog with the destination, amount, and memo completed](/images/tokens/mint-modal-filled.png)

![Confirmation prompt for the mint transaction](/images/tokens/mint-confirm.png)

The message "Mint transaction finalized." appears when the network confirms the transaction. The
mint then appears in the Transactions table with the status `confirmed`.

![Transactions table with a confirmed mint entry and the finalized message](/images/tokens/mint-confirmed.png)

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/mint \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: mint-001" \
  -d '{
    "signingCustodyWalletId": "cwlt_abc123",
    "mint": {
      "destination": "7xKXz...9fGh",
      "amount": "1000",
      "memo": "Initial distribution"
    }
  }'
```

```typescript title="mint-tokens.ts"
const res = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_abc123/mint",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",
      "Idempotency-Key": "mint-001",
    },
    body: JSON.stringify({
      signingCustodyWalletId: "cwlt_abc123",
      mint: {
        destination: "7xKXz...9fGh",
        amount: "1000",
        memo: "Initial distribution",
      },
    }),
  }
);
```

Set the priority with `options.priorityFee`. It accepts `"none"`, `"low"`, `"medium"`, `"high"`, or
a micro-lamport value.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Burn tokens">

A standard burn reduces the supply from an account that your wallet controls. Force-burn reduces
the supply from any holder account, without the signature of that holder.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

1. Select **Burn**. A dialog shows the signer wallet and an empty source field.
2. Select the wallet that holds the tokens you want to remove.
3. Enter the amount.
4. Enter a memo. This field is optional.
5. Select **Burn tokens**.
6. Select **Burn now** in the confirmation prompt to submit the transaction onchain.

![Burn dialog with the source field still empty](/images/tokens/burn-modal-empty.png)

![Burn dialog with the source wallet list open](/images/tokens/burn-modal-source.png)

![Burn dialog with the source, amount, and memo completed](/images/tokens/burn-modal-filled.png)

![Confirmation prompt for the burn transaction](/images/tokens/burn-confirm.png)

The message "Burn transaction finalized." appears when the network confirms the transaction. The
burn then appears in the Transactions table with the status `confirmed`.

![Transactions table with a confirmed burn entry and the finalized message](/images/tokens/burn-confirmed.png)

**Force burn** needs the `tokens:admin` permission. Run it from the Compliance tab, not from the
Operations tab. Force burn removes tokens from any holder account without the signature of that
holder.

</Tab>
<Tab value="API">

Burn from an account that you control:

```typescript title="burn-tokens.ts"
await fetch("https://api.solana.com/v1/issuance/tokens/tok_abc123/burn", {
  method: "POST",
  headers: {
    Authorization: "Bearer sk_test_...",
    "Content-Type": "application/json",
    "Idempotency-Key": "burn-001",
  },
  body: JSON.stringify({
    signingCustodyWalletId: "cwlt_abc123",
    burn: { source: "3xYZa...2aBc", amount: "250", memo: "Redemption" },
  }),
});
```

Force-burn from any holder. This call needs the `tokens:admin` permission:

```typescript title="force-burn-tokens.ts"
await fetch("https://api.solana.com/v1/issuance/tokens/tok_abc123/force-burn", {
  method: "POST",
  headers: {
    Authorization: "Bearer sk_test_...",
    "Content-Type": "application/json",
    "Idempotency-Key": "force-burn-001",
  },
  body: JSON.stringify({
    signingCustodyWalletId: "cwlt_abc123",
    forceBurn: { source: "3xYZa...2aBc", amount: "250", memo: "Compliance action" },
  }),
});
```

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={4} title="Check the supply">

SDP caches the total supply of a token. Confirm that the cached total reflects your mint or burn.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The dashboard refreshes the supply after a confirmed operation. The Transactions table lists every
completed operation, including the deploy, the mint, and the burn, each with the status
`confirmed`.

![Transactions table with confirmed burn, mint, and deploy entries](/images/tokens/operations-history.png)

Select **Refresh supply** if the displayed value still looks stale.

</Tab>
<Tab value="API">

Call the refresh endpoint to update the cached total after a mint or a burn:

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/supply/refresh \
  -H "Authorization: Bearer sk_test_..."
```

The call is safe to include in an automated workflow that runs after a mint.

</Tab>
</Tabs>
</StepPanel>

</Step>

</HowItWorks>
