SDP provides two categories of compliance tooling:

- **Token controls** — freeze individual accounts (tokens created with `isFreezable`), pause all transfers (tokens with the `pausable` extension), or seize tokens (tokens with a permanent delegate).
- **Address screening** — check a wallet against your organization's compliance providers before approving a destination or adding it to a token's Token Access Control allowlist.

Token-control actions require `tokens:admin` permission on the API key. Address screening requires `payments:read`.

When SDP signs a freeze, unfreeze, pause, unpause, or seize with a custody wallet, it first checks the action against that wallet's policy. A `deny` returns `403 FORBIDDEN`; an action held for approval returns `202` with error code `SIGNING_PENDING` and `error.details.approvalRequestId`. See [Wallet policies](/docs/wallet-operations/policies).

## How it works

<HowItWorks>

<Step number={1} title="Screen an address">

Check a Solana address against your compliance providers before onboarding a wallet or approving it as a transfer destination.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

The dashboard screens addresses automatically when you add a destination to a wallet's destination allowlist and when you add a crypto account to a counterparty.

To screen a token holder, use the API.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/compliance/address-screenings \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "address": "8dHEsGLp...hQWRGZ",
    "network": "solana",
    "intent": "transfer_destination"
  }'
```

`network` defaults to `solana`. `intent` is `transfer_destination`, `wallet_address_addition`, or `unknown` (the default).

```typescript title="screen-address.ts"
const { data } = await res.json();
// data.screening.providers[]
// → { provider, status, riskScore, riskLevel, providerStatus, message, evaluatedAt }
```

SDP screens the address with every compliance provider enabled for your organization: `range`, `elliptic`, `trm`, or `chainalysis`. If none is enabled, the request returns `403 FORBIDDEN`. On a self-hosted deployment, a provider is enabled by its API credentials, such as `RANGE_API_KEY`.

Each provider result has a normalized `status`:

| `status` | Meaning |
| --- | --- |
| `ok` | The provider completed the screening and returned a verdict. Only this value can count as a pass. |
| `pending` | The provider accepted the request but has not finished. |
| `unavailable` | The provider is not configured for this deployment. |
| `error` | The call failed, or the response was malformed or ambiguous. |

`providerStatus` keeps the provider's own status word for your records.

See the [Compliance API reference](/docs/reference/api/compliance) for the full schema.

<Step number={2} title="Freeze and unfreeze an account">

Prevent a specific holder from sending or receiving this token. The freeze targets one associated token account — other accounts are unaffected.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

On the token detail page, open the **Operations** section. Under **Transfers**, click **Manage** next to **Freeze a balance**.

Choose the signing wallet, enter the holder's **Wallet Address** and an optional reason, then click **Freeze balance** and confirm the on-chain submission. A "Freeze transaction finalized." toast appears, and the **Frozen Accounts** count in the **Operations** section updates.

To lift the freeze, open the same form, enter the wallet address, and click **Unfreeze balance**.

</Tab>
<Tab value="API">

**Freeze:**

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/freeze \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "accountAddress": "3xYZa...2aBc",
    "reason": "Suspicious activity investigation"
  }'
```

`accountAddress` accepts a holder wallet or its token account — SDP derives the associated token account when needed. `signingCustodyWalletId` is optional; when supplied, it must be the exact SDP Wallet `id` of a wallet that controls the current freeze authority.

**Unfreeze:**

```typescript title="unfreeze-account.ts"
await fetch("https://api.solana.com/v1/issuance/tokens/tok_abc123/unfreeze", {
  method: "POST",
  headers: { Authorization: "Bearer sk_test_...", "Content-Type": "application/json" },
  body: JSON.stringify({ accountAddress: "3xYZa...2aBc" }),
});
```

**List frozen accounts:**

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens/tok_abc123/frozen \
  -H "Authorization: Bearer sk_test_..."
```

<Step number={3} title="Pause and unpause the token">

Halt all minting and transfer activity globally. Requires the `pausable` extension on the token.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

On the token detail page, open the **Operations** section. Under **Transfers**, click **Pause** next to **Pause transfers**, then confirm with **Pause all transfers**.

The prompt uses the only matching authority wallet automatically. If several custody records control the same authority, select the signer before confirming. Unpausing uses the same selection rules.

A "Pause transaction finalized." toast appears, the token's status changes to **Paused**, and an **Unpause** button appears in the token header. Supply operations are blocked until you resume.

To resume, click **Unpause** in the header, or **Resume** next to **Resume transfers**, and confirm.

</Tab>
<Tab value="API">

```bash title="Terminal"
# Pause
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/pause \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{"signingCustodyWalletId":"cwlt_example"}'

# Unpause
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/unpause \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{"signingCustodyWalletId":"cwlt_example"}'
```

`signingCustodyWalletId` is optional when exactly one in-scope custody record matches the current pause authority; send `{}` to use that resolution. Multiple matches without a selector return `409`. An explicit choice must control the live authority and pass authorization and runtime checks. Reusing an idempotency key with a different wallet returns `409`.

While paused, mint, burn, force-burn, and seize requests return `TOKEN_PAUSED`, and onchain transfers are blocked until unpause.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={4} title="Seize tokens">

Force-transfer tokens from a holder to a recovery address without the holder's signature. For court orders and regulatory enforcement. Requires `tokens:admin` and a token with a permanent delegate.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

In the **Operations** section, open **Recovery & permanent changes** and click **Recover** next to **Force transfer**. Choose the signing wallet, provide the source, destination, amount, and a memo (strongly recommended for audit records), then click **Force transfer** and confirm.

</Tab>
<Tab value="API">

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/seize \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: seize-001" \
  -d '{
    "seize": {
      "source": "3xYZa...2aBc",
      "destination": "9aBCd...4eEf",
      "amount": "250",
      "memo": "Court order #12345"
    }
  }'
```

To sign the seizure yourself, call `POST /v1/issuance/tokens/{tokenId}/seize/prepare` with the same body. It returns an unsigned transaction in `preparedTransaction.serialized` for you to sign and submit. See the [execution model](/docs/developing-with-sdp#execution-model).

</Tab>
</Tabs>
</StepPanel>

</Step>

## Compliance response workflow

1. **Screen** the address via the Compliance API
2. **Freeze** the affected account while investigating
3. Based on findings — **Unfreeze** if cleared, **Seize** tokens to a recovery address, or **Force-burn** (see [Mint and Burn](/docs/tokens/mint-and-burn))
4. Record all actions with `memo` fields for the audit trail
