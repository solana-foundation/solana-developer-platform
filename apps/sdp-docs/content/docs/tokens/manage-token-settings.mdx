After a token is deployed, you can rotate its authorities and adjust operational settings. Authority management is separate from compliance actions — for freeze, pause, and seize flows see [Freeze and Compliance](/docs/tokens/freeze-and-compliance).

To edit token information, send `PATCH /v1/issuance/tokens/{tokenId}`. For a deployed token, `name`, `description`, `uri`, and `imageUrl` are also written to the onchain metadata through the current metadata authority. `symbol`, `decimals`, and `requiresAllowlist` can't change after deployment, and `maxSupply` can change only until the mint authority is revoked. To change what the token's asset profile says about it, see [Asset profile and hosted metadata](/docs/tokens/create-a-token#asset-profile-and-hosted-metadata).

For on-chain metadata edits, `PATCH /v1/issuance/tokens/{tokenId}` accepts optional `signingCustodyWalletId`. It selects the exact custody record controlling the current metadata authority for this request, not a new deployment wallet or authority. Omission requires exactly one matching in-scope record; multiple matches return `409`. Database-only edits need no signer. In the dashboard, edit these fields in the token's **Settings** section and click **Save changes**; when more than one wallet controls the metadata authority, choose the signer beside the save button. Historical `data.token.signingCustodyWalletId` does not change.

To select that signer after an external authority rotation, request `GET /v1/issuance/tokens/{tokenId}?includeMetadataAuthority=true` and use `data.metadataAuthority`. For tokens with a mint this is read live from the chain; tokens without a mint return their stored metadata authority or mint authority without RPC. RPC failure returns `502`, never the stored value as a fallback. The update rechecks the authority before signing. This read changes neither the stored token nor its deployment wallet.

SDP checks every on-chain metadata update and authority change against the signing wallet's policy before signing. A `deny` returns `403 FORBIDDEN`; a change held for approval returns `202` with error code `SIGNING_PENDING` and `error.details.approvalRequestId`. Database-only edits sign nothing and skip this check. See [Wallet policies](/docs/wallet-operations/policies).

## Prerequisites

- A deployed token with status `active`
- `tokens:admin` permission on the API key to change authorities; `tokens:write` to edit token information

## How it works

<HowItWorks>

<Step number={1} title="View current settings">

Review the token's current authorities and configuration before making changes.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

Open the token detail page. The header shows the token address, issued supply, and supply cap.

The **Permissions** section lists each permission — **Who can mint tokens?**, **Who can freeze balances?**, **Who can update token information?**, and **Who can recover or destroy balances?** — and the wallet that holds it. Authorities held outside SDP custody are flagged.

The **Settings** section shows the token's name, symbol, decimals, supply cap, description, website, and metadata URI, along with its controls.

</Tab>
<Tab value="API">

Fetch the current token state:

```bash title="Terminal"
curl https://api.solana.com/v1/issuance/tokens/tok_abc123 \
  -H "Authorization: Bearer sk_test_..."
```

```typescript title="get-token-settings.ts"
const { data } = await res.json();
// data.token.mintAuthority   — mint authority address
// data.token.freezeAuthority — freeze authority address
// data.token.extensions      — Token-2022 extensions, including permanentDelegate
// data.token.status          — "pending" | "active" | "paused" | "revoked"
```

To read a live authority from the chain, add `includeFreezeAuthority=true`, `includeMetadataAuthority=true`, `includePauseAuthority=true`, or `includeAllowlistAuthority=true`. The result is returned beside the token as `data.freezeAuthority`, `data.metadataAuthority`, `data.pauseAuthority`, or `data.allowlistAuthority`.

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={2} title="Rotate an authority">

Transfer a token authority to a different wallet. Use this to move signing responsibilities or to hand off control to an external key holder.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

On the token detail page, open **Permissions** and click the wallet shown next to the permission you want to change. Select another controlled wallet or choose **Use custom address**, then click **Save authority** and confirm the on-chain submission.

![Mint Authority modal showing current authority wallet, new authority dropdown with controlled wallets, and Save authority button](/images/tokens/token-authority-edit.png)

> Once an authority is rotated to an external wallet, SDP can no longer sign operations that require it. Rotate the authority back to a controlled wallet to resume using SDP's deploy, mint, and compliance actions.

</Tab>
<Tab value="API">

SDP signs the authority rotation:

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/issuance/tokens/tok_abc123/authority \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: rotate-001" \
  -d '{
    "authority": {
      "role": "mint",
      "newAuthority": "9aBCd...4eEf"
    }
  }'
```

`role` can be `mint`, `freeze`, `permanentDelegate`, or `metadata`. `signingCustodyWalletId` is optional; when supplied, it must be the exact SDP Wallet `id` of a wallet that controls the authority being changed.

To sign the change yourself, call `POST /v1/issuance/tokens/{tokenId}/authority/prepare` with the same body. It returns an unsigned transaction in `preparedTransaction.serialized` for you to sign and submit. See the [execution model](/docs/developing-with-sdp#execution-model).

</Tab>
</Tabs>
</StepPanel>

</Step>

<Step number={3} title="Revoke an authority">

Permanently remove an authority from the token. This action is irreversible — the token will no longer be mintable, freezable, or delegatable depending on which authority is revoked.

<StepPanel>
<Tabs items={["UI", "API"]} groupId="how-it-works">
<Tab value="UI">

In **Permissions**, open the permission and set the new authority to **None**, then click **Save authority**. A warning explains the consequences; click **Yes, set to None** to proceed. Some authorities can be reassigned but not removed, and the dialog says so.

To cap supply for good, open **Recovery & permanent changes** in the **Operations** section and use **Lock supply on-chain**. It mints the remaining supply up to your maximum supply, then revokes the mint authority.

</Tab>
<Tab value="API">

Set `newAuthority` to `null` to revoke:

```typescript title="revoke-authority.ts"
body: JSON.stringify({
  authority: {
    role: "mint",
    newAuthority: null,
  },
}),
```

After revoking the mint authority, no new tokens can ever be minted. Revocation is permanent and cannot be undone.

</Tab>
</Tabs>
</StepPanel>

</Step>

</HowItWorks>
