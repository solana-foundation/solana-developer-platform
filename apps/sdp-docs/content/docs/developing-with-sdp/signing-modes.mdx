---
title: Signing modes
description: When SDP signs and submits a transaction for you, and when it returns an unsigned transaction for you to sign and submit.
---

Every SDP operation that changes on-chain state ends in a Solana transaction that someone has to sign. SDP offers two ways to get there:

- **Execute:** SDP builds the transaction, signs it with a custody wallet in your project, submits it, and records the result. Most routes work this way.
- **Prepare:** SDP builds the transaction and returns it unsigned. You sign it, submit it to Solana yourself, and track the result. Prepare routes have `prepare` in their path.

## Which operations support which mode

| Operation | Execute | Prepare |
| --- | --- | --- |
| Token deploy | `POST /v1/issuance/tokens/{tokenId}/deploy` | — |
| Mint, burn | `POST .../mint`, `POST .../burn` | `POST .../mint/prepare`, `POST .../burn/prepare` |
| Seize, force burn | `POST .../seize`, `POST .../force-burn` | `POST .../seize/prepare`, `POST .../force-burn/prepare` |
| Authority transfer | `POST .../authority` | `POST .../authority/prepare` |
| Pause, unpause, freeze, unfreeze, allowlist changes | Yes | No |
| Transfers and transfer batches | `POST /v1/payments/transfers`, `POST /v1/payments/transfer-batches` | No |
| Recurring payments | `/v1/payments/recurring-payments` routes | No |

For mint, burn, seize, force burn, and authority transfer, the prepare route takes the same request body as the execute route.

## Execute

On an execute route, SDP runs the whole transaction itself:

1. It checks the API key's permissions and its access to the custody wallet that will sign.
2. Issuance execute routes, transfers, and transfer batches are checked against [wallet policy](/docs/wallet-operations/policies) before SDP signs. A policy can deny the operation or hold it for approval.
3. SDP signs with the custody wallet and submits the transaction.
4. The response carries the operation record with its on-chain `signature` and `status`. A transfer can come back `processing` while SDP is still confirming it; don't create a replacement transfer for it.

Transfers, transfer batches, and most issuance execute routes accept an `Idempotency-Key` header, so a retried request returns the original record instead of signing again. See [Idempotency](/docs/developing-with-sdp/idempotency) for the list.

## Prepare

Every prepare response carries the unsigned transaction in the same shape:

| Field | Meaning |
| --- | --- |
| `serialized` | Base64-encoded wire-format transaction with empty signature slots |
| `blockhash` | Recent blockhash the transaction was built with |
| `lastValidBlockHeight` | Last block height at which the transaction can land, as a decimal string |

Submit the signed transaction before the cluster passes `lastValidBlockHeight`. After that it can't land, and you need to prepare a new one.

Prepare routes differ from execute routes in three ways:

- **No policy evaluation.** Prepare routes don't run wallet policy or approvals. Permission checks, wallet access checks, and issuance token rules such as control lists and maximum supply still run.
- **No idempotent replay.** Prepare routes don't use `Idempotency-Key`. Every call builds a new transaction and creates a new operation record.
- **SDP doesn't submit.** You submit the signed transaction to Solana and check the outcome on-chain; SDP isn't told whether it landed.

### Issuance: mint, burn, seize, force burn, authority

The response contains:

- `transaction`: the SDP operation record for this operation, created with status `pending`
- `preparedTransaction`: the unsigned transaction
- `simulation`: present when you set `options.simulate` to `true`
- `tokenAccount` (mint only): the destination's token account

**Who signs.** The custody wallet in your project that holds the authority for the operation: the mint authority for mint, the permanent delegate for seize and force burn, the authority being changed for an authority transfer, and the wallet that owns the tokens for burn. To choose it, pass the SDP Wallet `id` (`cwlt_…` from `GET /v1/wallets`) as `signingCustodyWalletId`. It's required for burn and optional for the others. The same wallet is the fee payer: it pays the network fee, and for mint the rent for a new destination token account. SDP doesn't sponsor fees on prepared issuance transactions. The key for this wallet lives with your custody provider, so the signing step happens outside SDP.

**Who submits.** You do. No route reports the result back to SDP, so the operation record stays `pending`. Use the signature returned when you submit to check the outcome on-chain. After a mint or burn lands, `POST /v1/issuance/tokens/{tokenId}/supply/refresh` re-reads the token's supply from the chain.

**Maximum supply.** A prepared mint counts against the token's maximum supply as soon as SDP returns it, because it can still land until its blockhash expires. If the amount would exceed the cap, the request fails with `MAX_SUPPLY_EXCEEDED`.

**Permissions.** Mint and burn need `tokens:write`. Seize, force burn, and authority transfer need `tokens:admin`. The API key must also have access to the signing wallet with that permission.

**Rate limit.** Issuance prepare routes share a separate quota of 30 requests per minute per API key and 120 per organization. Requests over the quota return `429 RATE_LIMITED`.

```typescript title="prepare-mint.ts"
import {
  createSolanaRpc,
  getBase64EncodedWireTransaction,
  getBase64Encoder,
  getTransactionDecoder,
} from "@solana/kit";

const response = await fetch(
  "https://api.solana.com/v1/issuance/tokens/tok_123/mint/prepare",
  {
    method: "POST",
    headers: {
      "Authorization": "Bearer sk_test_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      mint: {
        destination: "7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU",
        amount: "100",
      },
      options: { simulate: true },
    }),
  }
);
const { data } = await response.json();
// data.transaction: the SDP operation record (status "pending")
// data.preparedTransaction: { serialized, blockhash, lastValidBlockHeight }

const unsigned = getTransactionDecoder().decode(
  getBase64Encoder().encode(data.preparedTransaction.serialized)
);

// Placeholder: sign with the custody wallet that holds the mint authority,
// through your custody provider's own signing API.
const signed = await signWithCustodyWallet(unsigned);

const rpc = createSolanaRpc("https://api.devnet.solana.com");
const signature = await rpc
  .sendTransaction(getBase64EncodedWireTransaction(signed), { encoding: "base64" })
  .send();
// Check the outcome on-chain with this signature; SDP isn't told about it.
```

## Choosing a mode

| If you need | Use |
| --- | --- |
| SDP to sign with a custody wallet, submit, and return the recorded result | Execute |
| Wallet policy and approvals to apply | Execute. Prepare routes don't evaluate policy. |
| Safe retries after timeouts | Execute with an `Idempotency-Key` |
| SDP to keep the operation record up to date | Execute. Prepared issuance records stay `pending`. |
| Fee sponsorship | Execute. SDP doesn't sponsor prepared issuance transactions. |
| The unsigned transaction, to inspect or simulate before you sign it with the custody wallet's key outside SDP | Prepare |
| Pause, freeze, allowlist changes, transfers, transfer batches, or recurring payments | Execute. These operations have no prepare route. |
