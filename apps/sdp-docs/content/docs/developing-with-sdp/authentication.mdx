---
title: Authentication
description: Authenticate an API request with a project-scoped API key, and see the controls that key carries.
---

SDP authenticates an API request with an API key that belongs to one project. Several controls
apply to the same key: its role, its per-key permissions, its wallet bindings, its policy profiles,
and its IP allowlist. Together they limit the key to the access its integration needs, and no more.

An authenticated API request carries the API key in the `Authorization` header:

```bash title="Terminal"
curl https://api.solana.com/v1/wallets \
  -H "Authorization: Bearer sk_test_..."
```

The `Bearer` prefix is optional. SDP also accepts a raw key in the `Authorization` header.

## Key scope

SDP issues a key for one **project**, and the key takes that project's environment. A `sk_test_`
key belongs to a sandbox project, which runs on devnet. A `sk_live_` key belongs to a production
project, which runs on mainnet.

A key reaches only the wallets, tokens, and payments of the project it was issued for. There is no
key that covers several projects, and no key that covers a whole organization.

## Authorization layers

A request must pass every layer that its key has configured:

| Layer | What it controls |
| --- | --- |
| **Role** | The baseline set of permissions. See the role table below. |
| **Per-key permissions** | Optional overrides of the role's defaults, one permission at a time. A key can hold only the permissions its creator holds. |
| **Wallet bindings** | The custody wallets the key can operate. Each binding has its own permission list. |
| **Policy profiles** | Rule sets that SDP evaluates before a bound wallet moves funds. A rule can restrict a destination, cap an amount, or require an approval. |
| **IP allowlist** | Optional IPv4, IPv6, or CIDR ranges that the key can be used from. |

| Role | Description |
| --- | --- |
| `api_admin` | Full access, including custody operations and platform operations. |
| `api_developer` | Read and write access to tokens, payments, counterparties, wallets, and webhooks. It excludes custody administration. |
| `api_readonly` | Read-only access to every resource, including audit records. |

## Errors

Your code can tell every authentication failure and authorization failure apart:

| Condition | Status | Code |
| --- | --- | --- |
| The request needs a key and carries none | 401 | `UNAUTHORIZED` |
| The key is malformed or unknown | 401 | `INVALID_API_KEY` |
| You deleted the key, or SDP revoked it | 401 | `REVOKED_API_KEY` |
| The key is past its expiry date or its rotation deadline | 401 | `EXPIRED_API_KEY` |
| The request comes from an address outside the key's IP allowlist | 403 | `FORBIDDEN` |
| The key lacks a required permission | 403 | `INSUFFICIENT_PERMISSIONS` |
| The key is over its rate limit | 429 | `RATE_LIMITED` |

SDP rate limits each key separately. The standard tier allows 100 requests per minute.

See [Manage API keys](/docs/developing-with-sdp/manage-api-keys) to create, rotate, and delete a
key.
