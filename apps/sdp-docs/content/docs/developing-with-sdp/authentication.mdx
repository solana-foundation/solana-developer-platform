---
title: Authentication
description: Authenticate API requests with project-scoped API keys, layered with roles, wallet bindings, and network controls.
---

SDP layers independent controls onto a single API key — role, per-key permissions, wallet bindings, policy profiles, and IP allowlist — so a key grants exactly the access its integration needs, and no more.

Authenticated API requests carry an API key in the `Authorization` header:

```bash title="Terminal"
curl https://api.solana.com/v1/wallets \
  -H "Authorization: Bearer sk_test_..."
```

The `Bearer` prefix is optional — a raw key in the `Authorization` header is also accepted.

## Key scope

Every key is scoped to exactly one **project** and inherits that project's environment: `sk_test_` keys belong to the sandbox project (devnet), `sk_live_` keys to the production project (mainnet-beta). A key can only reach the wallets, tokens, and payments of its own project; there is no cross-project or organization-wide key. Requests for another project's resources return `404`, and `GET /v1/projects` returns only the key's own project. See [Manage API Keys](/docs/developing-with-sdp/manage-api-keys#choose-the-project) for how a key ends up in the sandbox or production project.

## Authorization layers

A request must clear every layer that is configured on its key:

| Layer | What it controls |
| --- | --- |
| **Role** | Baseline permission set — see the table below |
| **Per-key permissions** | Optional fine-grained overrides of the role's defaults. A creator can only grant permissions it holds, unless it has `org:admin` (organization admins and `api_admin` keys do) |
| **Wallet bindings** | Restrict which custody wallets the key can operate, each binding with its own permission list |
| **Policy profiles** | Rule sets (destination controls, amount limits, approval requirements) evaluated before a bound wallet moves funds |
| **IP allowlist** | Optional IPv4/IPv6/CIDR ranges the key may be used from |

| Role | Description |
| --- | --- |
| `api_admin` | All permissions, including custody administration, token admin operations, API-key and project management, and policy authoring |
| `api_developer` | Read and write access to tokens, payments, counterparties, and wallets, plus read access to compliance. Excludes token admin operations (pause, freeze, seize, force-burn, authority transfer), custody administration, and API-key and project management |
| `api_readonly` | Read-only access to tokens, payments, counterparties, wallets, and compliance. No access to API keys or projects |

Only an `api_admin` key can create or rotate another `api_admin` key.

### Policy authoring

Policies constrain what keys can do, so only administrators can write them. Updating a wallet's policy (`PUT /v1/payments/wallets/{walletId}/policies`) and creating, revising, activating, or binding API-key policy profiles (`/v1/api-keys/{keyId}/policy-profiles`, `PUT /v1/api-keys/{keyId}/policy-bindings`) require an `api_admin` key. A key with any other role gets `403`, even if its custom permissions include the write permissions those routes check. In the dashboard, only organization admins can author policies.

## Errors

Authentication and authorization failures are always machine-distinguishable:

| Condition | Status | Code |
| --- | --- | --- |
| No API key on a keyed-only request | 401 | `UNAUTHORIZED` |
| Malformed or unknown key | 401 | `INVALID_API_KEY` |
| Key has been revoked | 401 | `REVOKED_API_KEY` |
| Key past its expiry or rotation deadline | 401 | `EXPIRED_API_KEY` |
| Request origin not in the key's IP allowlist | 403 | `FORBIDDEN` |
| Policy authoring with a non-`api_admin` key that holds the route's permissions | 403 | `FORBIDDEN` |
| Key lacks a required permission | 403 | `INSUFFICIENT_PERMISSIONS` |
| Resource belongs to another project | 404 | `NOT_FOUND` |
| Per-key rate limit exceeded | 429 | `RATE_LIMITED` |

Requests are rate limited per key; the standard tier allows 100 requests per minute.

See [Manage API Keys](/docs/developing-with-sdp/manage-api-keys) for creating, rotating, and revoking keys.
