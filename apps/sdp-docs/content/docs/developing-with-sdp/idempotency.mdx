---
title: Idempotency
description: Retry mutations safely with the Idempotency-Key header. Required on the routes that move money, accepted on every other payments, recurring payments, wallets, counterparties and compliance mutation.
---

Clients time out, connections drop and workers die mid-run. Send an `Idempotency-Key` header so a retry returns the first attempt's answer instead of doing the work twice.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfers \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: 0192f8a4-6c1e-7d4b-8f3a-b7e52c8d9f0a" \
  -H "Content-Type: application/json" \
  -d '{ ... }'
```

## Where keys apply

**Required.** These routes move money. A request without a key returns `400 IDEMPOTENCY_KEY_REQUIRED`, and nothing runs.

- `POST /v1/payments/transfers`
- `POST /v1/payments/transfer-batches`
- `POST /v1/payments/recurring-payments`
- `POST /v1/payments/recurring-payments/{id}/activate`
- `POST /v1/payments/recurring-payments/{id}/cancel`
- `POST /v1/payments/recurring-payments/{id}/collect`
- `POST /v1/payments/recurring-payments/{id}/resume`

**Accepted.** The key is optional, and honored when sent.

- Wallets: `POST /v1/wallets`, `POST /v1/wallets/initialize`, `POST /v1/wallets/signer-check`, `PATCH /v1/wallets/{walletId}`, `DELETE /v1/wallets`
- Recurring payments: `PATCH /v1/payments/recurring-payments/{id}`
- Subscription plans and subscriptions: `POST /v1/payments/subscription-plans`, `PATCH /v1/payments/subscription-plans/{planId}`, `POST /v1/payments/subscriptions`
- Counterparties: `POST`, `PATCH` and `DELETE` on `/v1/counterparties` and on counterparty accounts
- Compliance: `POST /v1/compliance/address-screenings`

**Not used.** `POST /v1/payments/transfer-batches/estimate` moves and stores nothing. The subscription `prepare-*` routes and subscription-plan `prepare-create` return an unsigned transaction bound to a fresh blockhash, which a stored replay would hand back after it expired. Neither reads the key.

Issuance operations keep their own key handling for now: a key is scoped to your organization across every issuance operation and token, and reusing it for a different request returns `409`.

## Choosing a key

- A key is 1–255 printable ASCII characters. Anything else returns `400`.
- Generate one key per logical operation (a UUIDv4 or UUIDv7 works well), store it with the operation before you send it, and send the same key on every retry of that operation.
- A new operation needs a new key, even when its request is identical to an earlier one.
- Keys are scoped to your organization, project, HTTP method and route, and bound to the credential that sent them. The same key value on two different routes is two separate keys.

## What a retry returns

Access is checked before the key on every request, so a retry passes exactly the checks a new request passes, and a request refused for access never claims the key.

| Situation | Response |
| --- | --- |
| Same key, same request, original finished | The original status and body, with the response header `Idempotent-Replayed: true`. |
| Same key, original still running | `409 IDEMPOTENCY_KEY_IN_FLIGHT` with `Retry-After`. Wait, then retry with the same key. |
| Same key, different request or different credential | `422 IDEMPOTENCY_KEY_REUSED`. Nothing runs. |
| Same key, but the credential has since lost access to the wallet or resource | `403`. The stored response is not returned. |
| Original was refused with `400`, `401`, `403`, `409` or `429` before it wrote anything | Nothing was stored. Fix the cause and retry with the same key; the request runs again. |
| A transfer or transfer batch failed after writing its record (for example `400 TRANSACTION_FAILED`, or `409` for a signer mismatch) | Stored: the same error, with `Idempotent-Replayed: true`. After 24 hours the record answers with the same status and code. The key is spent: send the request again with a new key to try again. |
| A recurring-payment action failed | Not stored. A failed attempt leaves the schedule as it was, so a same-key retry runs the action again. |
| Original returned a `5xx` | Stored and replayed: use a new key to try again. The routes that move money, and `PATCH /v1/payments/recurring-payments/{id}`, are the exception: a same-key retry runs again and answers from the record the first attempt wrote, so it never sends twice. That answer carries no `Idempotent-Replayed` header. |

"Same request" means the same path, query parameters, body and credential. Recipient order in a transfer batch, and `"1.0"` versus `"1"` for an amount, do not change the request.

Keys are scoped to the credential that sent them. A rotated API key is a new credential, so a retry under the new API key with the old `Idempotency-Key` gets `422`. A retry under a new `Idempotency-Key` is a new request and can move money again. After a rotation, read the resource with `GET` (for example `GET /v1/payments/transfers` or `GET /v1/payments/recurring-payments/{id}`) to learn whether the original request ran before you send it again.

An organization that has been deleted or has lost production access is refused before the key is read: `401` or `403`, even for a retry of a request that completed.

## Replays are snapshots

A replay returns the response as it was first sent: a transfer stored as `processing` replays as `processing`. To see current state, read the resource with `GET`. Never re-send a request to learn its outcome.

When the answer comes from the original record instead (a same-key retry after a `5xx`, or after the 24-hour window), it reflects that record as it stands now. A recurring-payment lifecycle action answered this way returns the schedule as it is, which may still be mid-transition; poll `GET /v1/payments/recurring-payments/{id}` until it settles.

## Retention

Keys are kept for 24 hours after the original request. After that, a same-key retry on most accepted routes starts a new request. On the routes that move money, the record the first attempt wrote still holds its key, so a late retry is answered from that record, or refused if the request differs; a failed transfer answers with the status and code it failed with.

## Creating wallets

`POST /v1/wallets` with a key never provisions a second wallet for one operation: a retry returns the wallet an earlier attempt created, within 24 hours or after, and the same key on a different request returns `422`. Privy and Coinbase CDP also dedupe the request at the provider. A provider failure is stored as a `503` for 24 hours, so try again with a new key.

## The dashboard and the Postman collection

The dashboard sends a key on every request to the routes that require one, and keeps it until it gets a definitive answer, so a retried click never moves money twice.

The [Postman collection](/docs/reference/postman-collection) saves one key per operation for the required routes (the `idempotencyKey.<operationId>` collection variable). It mints the key only when the variable is unset and clears it after a definitive answer: a replay, or any status below `500` other than `409` and `429`. Resending after a timeout or a `5xx` reuses the key. Clear the variable yourself to start a new operation with an identical body.

## Recommendations

- Send a key on every mutation that accepts one, not only where it is required.
- Retry timeouts, connection errors and `409 IDEMPOTENCY_KEY_IN_FLIGHT` with backoff, reusing the key.
- After a `5xx`, retry with the same key on the routes that move money; elsewhere, use a new key.
- Outside a key rotation, treat `422 IDEMPOTENCY_KEY_REUSED` as a bug in your client: the key was attached to two different operations.
- Persist the returned resource ID before moving to the next operation, so a restarted worker can resume without guessing.
