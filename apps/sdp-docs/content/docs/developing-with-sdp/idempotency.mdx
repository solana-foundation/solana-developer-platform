---
title: Idempotency
description: Retry mutations safely with the Idempotency-Key header. Required on the routes that move money, accepted on every other stable mutation.
---

Clients time out, connections drop and workers die mid-run. Send an `Idempotency-Key` header so a retry returns the first attempt's result instead of doing the work twice.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfers \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: 0192f8a4-6c1e-7d4b-8f3a-b7e52c8d9f0a" \
  -H "Content-Type: application/json" \
  -d '{ ... }'
```

## Choosing a key

- A key is 1–255 printable ASCII characters. Anything else returns `400`.
- Generate one key per logical operation (a UUIDv4 or UUIDv7 works well), store it with the operation, and send the same key on every retry of that operation.
- A new operation needs a new key, even when its request is identical to an earlier one.
- Keys are scoped to your organization, project, HTTP method and route. The same key value on two different routes is two separate keys.

## Where keys apply

| Endpoints | Key |
| --- | --- |
| `POST /v1/payments/transfers`<br />`POST /v1/payments/transfer-batches`<br />`POST /v1/payments/recurring-payments`<br />`POST /v1/payments/recurring-payments/{id}/activate`, `/cancel`, `/resume`, `/collect`<br />`POST /v1/wallets/approval-requests/{approvalRequestId}/approve` | **Required.** A request without one returns `400 IDEMPOTENCY_KEY_REQUIRED`. |
| Wallets: `POST /v1/wallets`, `/initialize`, `/signer-check`; `PATCH /v1/wallets/{walletId}`<br />Approval requests: `POST .../reject`, `.../cancel`<br />Payments: `PATCH /v1/payments/recurring-payments/{id}`, subscription plans (`POST`, `PATCH`, `prepare-create`), subscriptions (`POST`, `prepare-*`)<br />Counterparties and counterparty accounts: `POST`, `PATCH`<br />Compliance: `POST /v1/compliance/address-screenings` | **Accepted.** Optional, and honored when sent. |

Issuance operations keep their own key handling for now: a key is scoped to your organization across every issuance operation and token, and reusing it for a different request returns `409`.

## What a retry returns

| Situation | Response |
| --- | --- |
| Same key, same request, original finished | The stored status and body, with the response header `Idempotent-Replayed: true` |
| Same key, original still running | `409 IDEMPOTENCY_KEY_IN_FLIGHT` with `Retry-After`. Wait and retry with the same key. |
| Same key, different request or different credential | `422 IDEMPOTENCY_KEY_REUSED`. Nothing runs. |
| Original returned `400`, `401`, `403`, `409` or `429` | Nothing was stored. Fix the cause and retry with the same key; the request runs again. |
| Original returned a `5xx` | Stored and replayed; use a new key to try again. Transfers, transfer batches and recurring-payment creation are the exception: a same-key retry runs again and recovers the original record instead of creating a second one. That recovered response is a fresh answer, so it carries no `Idempotent-Replayed` header; the same holds for a same-key retry of these routes after the 24-hour record expires. |

"Same request" means the same path, query parameters, body and credential. A request made after rotating an API key is a new request, so it gets `422` if it reuses the old key.

A replay returns the response as it was first sent. To see current state (for example, whether a `processing` transfer has finalized), read the resource with `GET`.

A `Dry-Run: true` request on transfers and transfer batches needs no key, and may reuse the key of a real request without consuming it.

## Retention

Keys are kept for 24 hours after the original request. After that, the same key starts a new request, except on transfers, transfer batches and recurring-payment creation: those records keep their key permanently, so a late retry still returns the original record, or `422` if the request differs.

## Recommendations

- Send a key on every mutation, not only where it is required.
- Retry timeouts, connection errors and `409 IDEMPOTENCY_KEY_IN_FLIGHT` with backoff, reusing the key. A replayed `5xx` means the original failed: on transfers, transfer batches and recurring-payment creation, retry with the same key; elsewhere, use a new key.
- Treat `422 IDEMPOTENCY_KEY_REUSED` as a bug in your client: the key was attached to two different operations.
- Persist the returned resource ID before moving to the next operation, so a restarted worker can resume without guessing.
