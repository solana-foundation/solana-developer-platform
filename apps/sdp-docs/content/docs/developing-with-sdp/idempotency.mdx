---
title: Idempotency
description: Replay-safe mutations through the Idempotency-Key header, claimed by the record itself.
---

Retries are a fact of distributed systems: clients time out, connections drop, workers die mid-run. SDP lets you replay a mutation safely by sending an `Idempotency-Key` header — a unique value (a UUID works well) that you mint once per logical operation and reuse on every retry of that operation.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfers \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: 8a2f6c1e-9d4b-4f3a-b7e5-2c8d9f0a1b3c" \
  -H "Content-Type: application/json" \
  -d '{ ... }'
```

## How replay resolution works

SDP's model differs from response-cache designs: the idempotency key is claimed by the **business record itself**, not by a snapshot of the original response.

1. The first request creates the record — a transfer, a batch, an issuance transaction — carrying your key and a fingerprint of the normalized request payload.
2. A retry with the same key and the same payload returns **HTTP 200 with the stored record**, in the normal success envelope. Because it is the live record and not a cached response, a replay reflects current state — a transfer that has since finalized comes back `finalized`, not the `processing` you would have seen on the first attempt. Freeze and unfreeze differ in one case: replaying one whose original attempt failed returns **400** with the original error.
3. A request with the same key but a **different payload** is rejected with **409 `CONFLICT`** ("Idempotency key already used with different request payload"). For transfers and batches, a different source wallet also counts as a different payload. The fingerprint comparison is field-normalized, so formatting differences don't cause false conflicts.

Keys are retained for the lifetime of the record they claimed — there is no TTL, and a replay works for as long as the record exists. If a mint fails before anything is submitted on-chain, though, SDP releases the key, so a retry with the same key runs as a new request.

The header is optional. Every `/v1` route validates it when present (1–255 printable ASCII characters, otherwise `400 BAD_REQUEST`) and echoes it back on the response, but among the public endpoints only the operations below consume it. Elsewhere it is accepted and ignored.

## Where it applies

These twelve operations accept an `Idempotency-Key`. Each domain claims keys in its own namespace, and the namespaces are scoped differently:

| Operation | Endpoint | Key namespace |
| --- | --- | --- |
| Create a transfer | `POST /v1/payments/transfers` | Per project |
| Create a transfer batch | `POST /v1/payments/transfer-batches` | Per project |
| Deploy a token | `POST /v1/issuance/tokens/{tokenId}/deploy` | Issuance, per organization |
| Mint | `POST /v1/issuance/tokens/{tokenId}/mint` | Issuance, per organization |
| Burn | `POST /v1/issuance/tokens/{tokenId}/burn` | Issuance, per organization |
| Force-burn | `POST /v1/issuance/tokens/{tokenId}/force-burn` | Issuance, per organization |
| Seize | `POST /v1/issuance/tokens/{tokenId}/seize` | Issuance, per organization |
| Freeze an account | `POST /v1/issuance/tokens/{tokenId}/freeze` | Issuance, per organization |
| Unfreeze an account | `POST /v1/issuance/tokens/{tokenId}/unfreeze` | Issuance, per organization |
| Pause token transfers | `POST /v1/issuance/tokens/{tokenId}/pause` | Issuance, per organization |
| Unpause token transfers | `POST /v1/issuance/tokens/{tokenId}/unpause` | Issuance, per organization |
| Update an authority | `POST /v1/issuance/tokens/{tokenId}/authority` | Issuance, per organization |

Namespaces are independent across domains — the same key value used on a transfer and on a mint are two separate claims that never collide. Within issuance, however, the namespace is organization-wide: reusing a key for a different issuance operation, even on a different token, returns 409. Issuance keys aren't separated by project either, so never reuse one between your sandbox and production projects.

## This model is open to change

The per-domain differences above reflect the order in which these surfaces shipped, not a finished design. Treat the core contract as stable — one key per logical operation, replay returns the record, payload mismatch returns 409 — and treat the scoping details (per-project vs per-organization namespaces, which endpoints consume the header) as subject to change.
