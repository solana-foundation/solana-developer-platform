---
title: Idempotency
description: Replay a mutation safely with the Idempotency-Key header, which the created record claims.
---

Retries are part of every distributed system. A client times out, a connection drops, or a worker
stops in the middle of a run.

SDP lets you replay a mutation safely. Send an `Idempotency-Key` header with a unique value. A UUID
works well. Create that value once per logical operation, and send the same value on every retry of
that operation.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfers \
  -H "Authorization: Bearer sk_test_..." \
  -H "Idempotency-Key: 8a2f6c1e-9d4b-4f3a-b7e5-2c8d9f0a1b3c" \
  -H "Content-Type: application/json" \
  -d '{ ... }'
```

## How replay resolution works

The SDP model is not a response cache. The **business record** claims the idempotency key, not a
snapshot of the first response.

1. The first request creates the record. The record is a transfer, a batch, or an issuance
   transaction. It carries your key and a fingerprint of the normalized request payload.
2. A retry with the same key and the same payload returns **HTTP 200 with the stored record**, in
   the normal success envelope. The response is the live record, not a cached copy, so a replay
   shows the current state. A transfer that has finalized since the first attempt comes back as
   `finalized`, not as the `processing` you saw first.
3. A request with the same key and a **different payload** returns **409 `CONFLICT`**, with the
   message "Idempotency key already used with different request payload". SDP normalizes each field
   before it compares the fingerprints, so a difference in formatting does not create a false
   conflict.

SDP keeps a key for as long as the record that claimed it exists. There is no time to live, and a
replay works for as long as the record exists.

SDP validates the header on every `/v1` route. The value must be 1 to 255 printable ASCII
characters. Only the endpoints below act on it. Every other route accepts the header and ignores
it.

## Where it applies

Each domain claims a key in its own namespace, and the namespaces have different scopes:

| Domain | Operations | Key namespace |
| --- | --- | --- |
| Payments (transfers) | `POST /v1/payments/transfers` | Per project |
| Payments (batches) | `POST /v1/payments/transfer-batches` | Per project |
| Issuance | Execute-mode deploy, mint, burn, force-burn, freeze, thaw, pause, unpause, seize, and authority transfer | Per organization, shared across **all** issuance operations and tokens |
| Custody | Provider credential submission (dashboard flow) | Required on every submission |

The namespaces are independent across domains. The same key value on a transfer and on a mint makes
two separate claims, and they never collide.

Inside issuance the namespace covers the whole organization. If you reuse a key for a different
issuance operation, SDP returns 409, even when the operation targets a different token.

## This model is open to change

The differences between domains above follow the order in which these API areas shipped. They are
not a finished design, and we expect them to converge.

Treat the core contract as stable: one key per logical operation, a replay returns the record, and
a payload mismatch returns 409.

Treat the scoping details as open to change: which namespace is per project versus per
organization, and which endpoints act on the header. We are considering two changes. We may act on
the header on more mutation endpoints, and we may give every domain the same namespace scope.
