---
title: Manage API Keys
description: Create, rotate, and revoke API keys with role-based access, wallet bindings, and zero-downtime rotation.
---

Create, list, rotate, and revoke the API keys that authenticate SDP API requests. Each key belongs to one project, inherits its environment, and carries a role plus optional fine-grained controls — see [Authentication](/docs/developing-with-sdp/authentication) for how those layers are enforced.

The full secret is returned exactly once — at creation and at rotation. SDP stores only a hash and a display prefix; a lost key cannot be recovered, only rotated or replaced. Every key tracks `lastUsedAt` so you can identify stale credentials before revoking them.

## Key format

| Environment | Prefix | Solana network |
| --- | --- | --- |
| Sandbox | `sk_test_` | devnet |
| Production | `sk_live_` | mainnet-beta |

## Choose the project

Every organization has a sandbox project and a production project, and a key's environment comes from the project it is created in. No request field sets the environment, and a key can't be moved to another project later.

- **Dashboard:** the key is created in the project selected in the workspace switcher. Switch to the production project before creating a production key.
- **API:** `POST /v1/api-keys` creates the key in the same project as the key that authenticates the request. `POST /v1/projects/{projectId}/api-keys` does the same, and `{projectId}` must be the authenticating key's own project.

An API key can't create keys in the other project, so your first production key has to come from the dashboard. See [Set Up Your Organization & Projects](/docs/guides/setup-organization) for the workspace switcher and production access.

## Roles

| Role | Description |
| --- | --- |
| `api_admin` | All permissions, including custody administration, API-key management, and policy authoring |
| `api_developer` | Read and write access to tokens, payments, counterparties, and wallets; no token admin operations, custody administration, or API-key management |
| `api_readonly` | Read-only access to tokens, payments, counterparties, wallets, and compliance |

Managing keys through the API takes the `api-keys:read` and `api-keys:write` permissions. `api_admin` keys have them; `api_developer` and `api_readonly` keys don't. Only an `api_admin` key can create or rotate another `api_admin` key.

A key can also carry explicit `permissions` that override the role's defaults. A creator can only grant permissions it holds, unless it has `org:admin`, as organization admins and `api_admin` keys do.

## Create a key

<Tabs items={["Dashboard", "API"]}>
<Tab value="Dashboard">

Only organization admins can create, rotate, and delete keys in the dashboard; members can view them.

1. In the workspace switcher at the top of the sidebar, select the project the key is for.

2. Navigate to **API keys** in the sidebar. You start with an empty list.

   ![API keys page with no keys yet](/images/getting-started/api-keys-empty.png)

3. Click **Create new API key** (or **New API key** once the project has keys) and work through the four steps:
   - **Details** — a descriptive **Name** (e.g., "CI deploy key") and an optional **Expiration**. The **Environment** is read-only and comes from the selected project.
   - **Permissions** — the role: Admin, Developer, or Read only.
   - **Wallet access** — **All wallets**, or **Selected wallets** with a default signing wallet.
   - **Review** — check the summary and click **Create key**.

4. Click **Copy** on the **API key generated** modal and save the key — it will not be shown again.

   ![API key generated modal showing the full key](/images/getting-started/api-key-generated.png)

5. Dismiss the modal. The key now appears in the table with its prefix, environment, access, and status.

   ![API keys list with one active key](/images/getting-started/api-keys-list.png)

</Tab>

```java title="CreateApiKey.java"
    .uri(URI.create("https://api.solana.com/v1/api-keys"))
    .header("Authorization", "Bearer sk_test_...")
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString("""
        {
          "name": "CI deploy key",
          "role": "api_developer",
          "walletScope": "all",
          "expiresAt": "2026-12-31T23:59:59Z"
        }"""))
    .build();
```
</Tab>
</Tabs>

The new key belongs to the project of the key that created it and inherits that project's environment — there is no environment field on the request. `POST /v1/projects/{projectId}/api-keys` accepts the same body. The response includes the full `key` value — **save it, it is only returned once**.

`name` and `walletScope` are required; `role` defaults to `api_developer`. Optional fields: `description`, `permissions` (fine-grained overrides), `allowedIps` (IPv4/IPv6/CIDR ranges), `expiresAt`, `signingWalletId` / `signingWalletIds`, `walletBindings` (per-wallet permission lists), and `provisionWallet` with `walletLabel` and `walletPurpose` to create and bind a new custody wallet (requires `custody:admin`).

Keys can also carry policy profiles that limit which operations they can perform, managed through `/v1/api-keys/{keyId}/policy-profiles` and `PUT /v1/api-keys/{keyId}/policy-bindings` (see the [API Keys API reference](/docs/reference/api/api-keys)); a key created by another key starts with a copy of that key's profiles and bindings.

</Tabs>

## List keys

`GET /v1/api-keys` lists the keys in the authenticating key's project, newest first; `GET /v1/projects/{projectId}/api-keys` returns the same list for that project. Revoked keys are left out. Each entry carries the `keyPrefix`, `role`, `environment`, `status`, wallet access, `lastUsedAt`, and `expiresAt` — never the secret. `GET /v1/api-keys/{keyId}` returns one key in full, including its `permissions`, `allowedIps`, and rotation details.

<Tab value="curl">
```bash title="Terminal"

  -H "Authorization: Bearer sk_test_..."
```
</Tab>

## Rotate a key

Rotation replaces the secret without an availability gap: the new key is a fresh record that clones the old key's name, role, permissions, IP allowlist, expiry, wallet bindings, and policy profiles, while the old key keeps working until its grace deadline. During the grace period both keys are valid; after it, the old key fails with `EXPIRED_API_KEY`. A key can be rotated once: rotating it again while its replacement is active returns `409 CONFLICT` naming the replacement.

<Tabs items={["Dashboard", "API"]}>
<Tab value="Dashboard">

1. In the API keys table, open the **Actions** dropdown next to the key and click **Rotate key (24h grace)**. The dashboard always uses a 24-hour grace period — use the API for a custom value (0–168h).

   ![Actions dropdown showing Rotate key and Delete key options](/images/getting-started/api-key-rotate.png)

2. Copy the new key value from the generated key modal — it is shown once.

</Tab>
<Tab value="API">

<Tabs items={["curl", "TypeScript", "Java"]}>
<Tab value="curl">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/api-keys/key_abc123/rotate \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{ "gracePeriodHours": 24 }'
```
</Tab>
<Tab value="TypeScript">
```typescript title="rotate-api-key.ts"
const response = await fetch(
  "https://api.solana.com/v1/api-keys/key_abc123/rotate",
  {
    method: "POST",
    headers: {
      "Authorization": "Bearer sk_test_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ gracePeriodHours: 24 }),
  }
);
const { data } = await response.json();
// data.apiKey — the new key, only shown once
// data.previousKey.rotationDeadline — when the old key stops working
```
</Tab>
<Tab value="Java">
```java title="RotateApiKey.java"
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.solana.com/v1/api-keys/key_abc123/rotate"))
    .header("Authorization", "Bearer sk_test_...")
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString("""
        { "gracePeriodHours": 24 }"""))
    .build();
```
</Tab>
</Tabs>

`gracePeriodHours` accepts 0–168 (default 24). A key cannot rotate itself — authenticate the rotation with a different key in the same project, or rotate from the dashboard.

</Tab>
</Tabs>

## Revoke a key

<Tabs items={["Dashboard", "API"]}>
<Tab value="Dashboard">

Open the **Actions** dropdown next to the key and click **Delete key**, then type the key's name to confirm. The key stops working immediately and cannot be restored.

</Tab>
<Tab value="API">

<Tabs items={["curl", "TypeScript", "Java"]}>
<Tab value="curl">
```bash title="Terminal"
curl -X DELETE https://api.solana.com/v1/api-keys/key_abc123 \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{ "confirmation": "CI deploy key" }'
```
</Tab>
<Tab value="TypeScript">
```typescript title="revoke-api-key.ts"
await fetch("https://api.solana.com/v1/api-keys/key_abc123", {
  method: "DELETE",
  headers: {
    "Authorization": "Bearer sk_test_...",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ confirmation: "CI deploy key" }),
});
```
</Tab>
<Tab value="Java">
```java title="RevokeApiKey.java"
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.solana.com/v1/api-keys/key_abc123"))
    .header("Authorization", "Bearer sk_test_...")
    .header("Content-Type", "application/json")
    .method("DELETE", HttpRequest.BodyPublishers.ofString("""
        { "confirmation": "CI deploy key" }"""))
    .build();
```
</Tab>
</Tabs>

The `confirmation` field must match the key's **name**. Revocation takes effect immediately, is idempotent (revoking an already-revoked key succeeds), and cannot be undone. As with rotation, a key cannot revoke itself.

</Tab>
</Tabs>
