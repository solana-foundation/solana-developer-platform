This tutorial pays two contractors in USDC from a custody wallet in your sandbox project. You will:

1. Register each contractor as a counterparty with a Solana wallet account.
2. Estimate the transfer batch that pays them.
3. Create the batch with an `Idempotency-Key`.
4. Poll the batch until every recipient has settled.
5. Find the batch's transactions in `GET /v1/transactions`.

Every step uses the public API. Response examples are trimmed to the fields this tutorial uses. The [Payments API reference](/docs/reference/api/payments) and [Counterparties API reference](/docs/reference/api/counterparties) list every field.

## Before you start

### A custody wallet that holds USDC

You need a custody wallet in your sandbox project. A batch names the wallet that pays: you pass its SDP Wallet `id` (`cwlt_…`, from `GET /v1/wallets`) as `sourceCustodyWalletId`. There is no default wallet. If you don't have one yet, see [Set Up Wallets](/docs/guides/setup-wallets).

The wallet must hold at least the batch total in USDC. `USDC` resolves to the USDC mint on your project's network, which is devnet for a sandbox project. Check the balance with [Wallet balances](/docs/wallet-operations/balances). The wallet doesn't need SOL for this flow: SDP's fee payer pays the network fees and the rent for any recipient token account that doesn't exist yet.

### An API key with the right access

Use a sandbox key (`sk_test_…`). It needs these permissions:

| Step | Endpoint | Permissions |
| --- | --- | --- |
| 1. Register recipients | `POST /v1/counterparties`, `POST /v1/counterparties/{counterpartyId}/accounts` | `counterparties:write` |
| 2. Estimate | `POST /v1/payments/transfer-batches/estimate` | `payments:read`, `wallets:read`, `counterparties:read` |
| 3. Create the batch | `POST /v1/payments/transfer-batches` | `payments:write`, `wallets:read`, `counterparties:read` |
| 4. Poll the batch | `GET /v1/payments/transfer-batches/{batchId}` | `payments:read` |
| 5. List transactions | `GET /v1/transactions?module=payments` | `payments:read` |

The `api_admin` and `api_developer` [roles](/docs/developing-with-sdp/manage-api-keys#roles) include all of them. An `api_readonly` key can run steps 2, 4, and 5, but can't create counterparties or batches.

Two more settings on the key can block the payment:

- **Wallet access.** If the key is limited to selected wallets, the source wallet must be one of them, and its binding must include `payments:write` to create the batch and `payments:read` to estimate and read it.
- **Allowed operations.** If the key carries a non-empty [allowed operations](/docs/developing-with-sdp/manage-api-keys#allowed-operations) list, it must include the `payment` family or the `payment_transfer_batch_execute` type. Otherwise creating the batch returns `403 OPERATION_NOT_ALLOWED`. The estimate is not checked against this list.

```typescript title="sdp.ts"
const BASE_URL = "https://api.solana.com";
const API_KEY = process.env.SDP_API_KEY!; // sk_test_...
export const WALLET_ID = process.env.SDP_WALLET_ID!; // cwlt_...

export class SdpError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,
    message: string,
    readonly details?: Record<string, unknown>
  ) {
    super(`${status} ${code}: ${message}`);
  }
}

// Calls the SDP API and returns the `data` field of the success envelope.
export async function sdp<T>(
  method: "GET" | "POST",
  path: string,
  body?: unknown,
  headers: Record<string, string> = {}
): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, {
    method,
    headers: {
      Authorization: `Bearer ${API_KEY}`,
      ...(body === undefined ? {} : { "Content-Type": "application/json" }),
      ...headers,
    },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const json = await res.json();
  if (!res.ok) {
    throw new SdpError(res.status, json.error.code, json.error.message, json.error.details);
  }
  return json.data as T;
}
```

The TypeScript steps below build one script, `payout.ts`, that imports this helper. Each step's block continues the previous one.

## 1. Register the recipients as counterparties

A transfer batch pays counterparty accounts, not raw addresses. Each contractor needs a **counterparty**, the record of who they are, and a `crypto_wallet` **account** that holds the Solana address you pay.

`POST /v1/counterparties` creates the counterparty. `externalId` is your own reference, and it must be unique among the project's active counterparties. Then `POST /v1/counterparties/{counterpartyId}/accounts` adds the wallet account. `details.network` must be `"solana"` and `details.address` a base58 Solana wallet address.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
COUNTERPARTY_ID_1=$(curl -sS -X POST https://api.solana.com/v1/counterparties \
  -H "Authorization: Bearer $SDP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "entityType": "individual",
    "displayName": "Ana Lima",
    "externalId": "contractor_0042"
  }' | jq -r '.data.counterparty.id')

ACCOUNT_ID_1=$(curl -sS -X POST "https://api.solana.com/v1/counterparties/$COUNTERPARTY_ID_1/accounts" \
  -H "Authorization: Bearer $SDP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "accountKind": "crypto_wallet",
    "label": "USDC payout wallet",
    "details": {
      "network": "solana",
      "address": "ASSxhogtgxhRTRaXtAdjXMCTd4uq3QGrDMyt4XiJmBRT"
    }
  }' | jq -r '.data.account.id')
```

## 2. Estimate the batch

`POST /v1/payments/transfer-batches/estimate` takes the same body as the real batch. It runs the same checks: your key's access to the wallet, the token, every counterparty account, and every amount. Then it works out how SDP would split the recipients into Solana transactions. It doesn't sign or submit anything.

Each recipient names its `counterpartyAccountId` and an `amount` in token units. `counterpartyId` is optional; if you send it, it must own the account. `externalId` on the batch and on each recipient is for your own correlation and doesn't deduplicate anything.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
BATCH_BODY=$(jq -n \
  --arg wallet "$SDP_WALLET_ID" \
  --arg cp1 "$COUNTERPARTY_ID_1" --arg acct1 "$ACCOUNT_ID_1" \
  --arg cp2 "$COUNTERPARTY_ID_2" --arg acct2 "$ACCOUNT_ID_2" \
  '{
    externalId: "contractors_2026_10",
    sourceCustodyWalletId: $wallet,
    token: "USDC",
    recipients: [
      { externalId: "contractor_0042", counterpartyId: $cp1, counterpartyAccountId: $acct1, amount: "1200.00" },
      { externalId: "contractor_0043", counterpartyId: $cp2, counterpartyAccountId: $acct2, amount: "850.50" }
    ]
  }')

curl -sS -X POST https://api.solana.com/v1/payments/transfer-batches/estimate \
  -H "Authorization: Bearer $SDP_API_KEY" \
  -H "Content-Type: application/json" \
  -d "$BATCH_BODY"
```

- `transactionCount` is `1`: by default SDP puts up to 20 recipients in one Solana transaction. Set `options.maxRecipientsPerTransaction` (1 to 64) to change that.
- `tokenAccountRentLamports` is the rent for recipient USDC token accounts that don't exist yet. Here neither contractor has one, so it covers two accounts.
- `sponsored: true` means SDP's fee payer pays these fees, not your wallet.

A clean estimate means the request passed validation. It doesn't check the wallet's USDC balance: a shortfall shows up when SDP simulates the transaction in the next step.

## 3. Create the batch

Send the same body to `POST /v1/payments/transfer-batches` with an `Idempotency-Key` header. Mint one key per payout run and store it with the run before you send, so a retry can reuse it.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
IDEMPOTENCY_KEY="contractors-2026-10-run-1"

BATCH_ID=$(curl -sS -X POST https://api.solana.com/v1/payments/transfer-batches \
  -H "Authorization: Bearer $SDP_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $IDEMPOTENCY_KEY" \
  -d "$BATCH_BODY" | jq -r '.data.batch.id')
```
</Tab>
<Tab value="TypeScript">

<Callout type="warn">
If the request times out, send it again with the same `Idempotency-Key` and the same body. SDP returns the original batch with its current state and submits nothing new. A new key, or no key, creates a second batch and pays everyone twice. The same key with a different body, or a different source wallet, returns `409 CONFLICT`. See [Idempotency](/docs/developing-with-sdp/idempotency).
</Callout>

## 4. Poll the batch until it settles

`GET /v1/payments/transfer-batches/{batchId}` returns the same shape as the create response. Poll it until `batch.status` is no longer `processing`. Every 15 to 30 seconds is a reasonable pace for a background job; see [Polling cadence](/docs/payments/accept-verification#polling-cadence).

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
curl -sS "https://api.solana.com/v1/payments/transfer-batches/$BATCH_ID" \
  -H "Authorization: Bearer $SDP_API_KEY" | jq '.data.batch.status'
```
</Tab>
<Tab value="TypeScript">
```typescript title="payout.ts (continued)"
async function waitForBatch(batchId: string, maxAttempts = 40): Promise<BatchDetail> {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    const detail = await sdp<BatchDetail>("GET", `/v1/payments/transfer-batches/${batchId}`);
    if (detail.batch.status !== "processing") return detail;
    await new Promise((resolve) => setTimeout(resolve, 15_000));
  }
  throw new Error(`Batch ${batchId} is still processing; keep polling, don't resend it`);
}

const settled = await waitForBatch(created.batch.id);
const failed = settled.recipients.filter((r) => r.status === "failed");
// Pay `failed` rows again in a new batch with a new Idempotency-Key.
```
</Tab>
</Tabs>

The batch ends in one of three statuses:

| `batch.status` | Meaning | What to do |
| --- | --- | --- |
| `confirmed` | Every recipient is `confirmed`. | Nothing. Everyone was paid. |
| `partially_failed` | Some recipients are `confirmed` and some `failed`. | Pay only the `failed` rows again. |
| `failed` | No recipient was paid. | Read each recipient's `error`, fix the cause, and pay them again. |

A batch can't be retried in place. Pay `failed` recipients in a new batch with a new `Idempotency-Key`. Never resend recipients that are `pending`, `processing`, or `confirmed`: a recipient stays `processing` while SDP finds out whether its transaction reached the network. See [Payouts and disbursements](/docs/payments/send-payouts#track-recipients) for every recipient and batch status.

## 5. Find the payments in the transaction history

`GET /v1/transactions` lists your project's payments and issuance transactions in one feed, newest first. A transfer batch appears as one `batch_pay` row per Solana transaction, not one row per recipient. Filter on the module, the kind, and the source wallet:

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
curl -sS "https://api.solana.com/v1/transactions?module=payments&kind=batch_pay&custodyWalletId=$SDP_WALLET_ID&limit=20" \
  -H "Authorization: Bearer $SDP_API_KEY"
```
</Tab>

```json title="Response"
    "nextCursor": null
  },
  "meta": { "requestId": "req_...", "timestamp": "2026-10-12T14:05:00.000Z" }
}
```

How to read the row:

- `moduleId` is the transfer ID that the batch's recipient rows carry as `transferId`. To fetch one row directly, use `search` with the full ID: `GET /v1/transactions?search=xfr_bea210fb-6b39-4edf-a0b0-4769cc7a4c78`.
- `amount` is the total paid in that one transaction. `counterpartyId` is `null` because the transaction paid two recipients; it is set only when a transaction pays a single recipient. Use the batch's recipient rows for per-recipient amounts.
- `status: "succeeded"` covers both `confirmed` and `finalized`. Wait for `moduleStatus` to reach `finalized` before irreversible side effects, such as posting to your general ledger. See [Finality on Solana](/docs/payments/accept-verification#finality-on-solana).

The list is metered at 60 requests per minute per API key. For pagination, search rules, and a reconciliation worker, see [Transaction history](/docs/payments/transactions).

## Errors you're likely to hit

Errors use the standard envelope: `error.code`, `error.message`, optional `error.details`, and `meta.requestId`.

| Status | `error.code` | When | What to do |
| --- | --- | --- | --- |
| `400` | `BAD_REQUEST` | The body fails validation: an unknown field, an amount with more decimal places than the token has, more than 500 recipients, or an account address that isn't base58. | Fix the request. `error.message` describes each problem and the field it is in. |
| `400` | `BAD_REQUEST` | `Source wallet has no token account for this mint`: the source wallet has never held USDC. | Fund the wallet with USDC first. |
| `403` | `INSUFFICIENT_PERMISSIONS` | The key lacks a permission from the [table above](#an-api-key-with-the-right-access), for example an `api_readonly` key creating a batch. | Use a key with the permissions. |
| `403` | `OPERATION_NOT_ALLOWED` | The key's allowed operations don't include `payment`. Only creating the batch is checked. | Add `payment` to the key's list, or use another key. |
| `403` | `FORBIDDEN` | The key is limited to selected wallets and the source wallet isn't one of them, or its binding lacks the permission. | Bind the wallet to the key, or use a key that can reach it. |
| `404` | `NOT_FOUND` | The `sourceCustodyWalletId` isn't a wallet in this project, a `counterpartyAccountId` doesn't exist in the project, or a `counterpartyId` doesn't own the account. | Check the IDs. Counterparty accounts belong to one project. |
| `409` | `CONFLICT` | The `Idempotency-Key` was already used with a different body or source wallet, or a counterparty `externalId` is already taken. | Resend the original body with that key, or mint a new key for a new payout run. For `externalId`, use the counterparty you already created. |
| `429` | `RATE_LIMITED` | `GET /v1/transactions` is over its metered quota. | Wait the number of seconds in the `Retry-After` header. |

A refused operation returns this body, and SDP records nothing:

```json title="Response"
{
  "error": {
    "code": "OPERATION_NOT_ALLOWED",
    "message": "This API key may not perform payment_transfer_batch_execute",
    "details": {
      "operationType": "payment_transfer_batch_execute",
      "operationFamily": "payment"
    }
  },
  "meta": { "requestId": "req_..." }
}
```

The key's list is checked before the body is validated, so this error can appear even when the body is invalid. To change the list, update the key with `PATCH /v1/api-keys/{keyId}`, using a key with `api-keys:write` such as an `api_admin` key. See [Allowed operations](/docs/developing-with-sdp/manage-api-keys#allowed-operations).

A batch can also come back `200` with `batch.status: "failed"` right away. That means SDP simulated a transaction before sending it and the simulation failed, for example because the wallet doesn't hold enough USDC. Nothing was sent, and each recipient's `error` gives the reason. Top up the wallet and pay the recipients in a new batch with a new `Idempotency-Key`.
