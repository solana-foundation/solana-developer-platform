This tutorial issues a regulated stablecoin on Solana: a product a Federal Reserve examiner could read and a bank's compliance committee could sign against. That takes more than deploying a token. You need institutional custody, integrated compliance and operational reversibility from day one. The [GENIUS Act](https://www.gibsondunn.com/the-genius-act-a-new-era-of-stablecoin-regulation/) treats those capabilities as preconditions, not features.

## 1. What this work demands

**Custody is not your laptop.** A federally chartered custodian, such as Anchorage Digital Bank, holds the signing keys for the mint, freeze and permanent-delegate authorities. The engineer at the issuer doesn't.

**Compliance is integrated from day one.** You screen every transfer destination before the transfer is built, and every freeze ties back to a court order, sanctions notice or compliance ticket. Screening runs on the same API as mint and burn.

**Operational reversibility is the product.** Freeze, seize and force burn are the capabilities the GENIUS Act requires before launch, and your compliance officer will check for them. Section 5 covers each.

**The reader is institutional.** This tutorial assumes you're a developer at a financial institution or fintech, building under a compliance officer's oversight. She'll see your decisions in product review.

## 2. Prerequisites

You need an SDP organization, a custody wallet, and two API keys: one for routine operations and one for compliance operations.

### 1. Account and organization

Sign up at [platform.solana.com](https://platform.solana.com) with email, Google or GitHub, and create your organization when the dashboard asks. It comes with a sandbox project (devnet) and a production project (mainnet). Work in the sandbox until Section 8.

### 2. Custody wallet

In production, a US institutional issuer holds its keys with a federally chartered custodian such as [Anchorage Digital Bank](https://www.anchorage.com/platform/stablecoin-issuance), one of SDP's custody providers. In the sandbox, [create a wallet](/docs/guides/setup-wallets) with SDP's Privy account instead. The API is the same; only the wallet record's `provider` differs.

SDP's fee sponsor pays the network fees for the issuance calls in this tutorial, and for transfers from a Privy wallet, so the sandbox wallet needs no SOL.

### 3. API keys: the two-key pattern

In the sandbox project, open **API keys** and create two keys ([Manage API keys](/docs/developing-with-sdp/manage-api-keys)):

- **Developer key**: Read, Manage and Execute on Issuance, Execute on Transfers, and Read on Wallets. It creates, deploys, mints, burns and transfers.
- **Admin key**: the Developer key's grants plus Enforce on Issuance and Execute on Compliance. It screens, freezes, seizes and force-burns.

The dashboard starts a key that holds an Execute grant on **Selected wallets**: select your custody wallet there, or choose **All wallets**. Only an organization admin can grant Enforce, because you can grant only actions you hold. An API key can't create keys.

<Callout type="warn">
The full key is shown only once. Store it in your secrets manager right away; SDP doesn't show it again.
</Callout>

### 4. Wire up your client and verify

The API base URL is `https://api.solana.com`. Wire two HTTP clients, one per key, with a thin wrapper around `fetch`:

```javascript title="sdp-client.js"
const BASE = "https://api.solana.com";

class SdpClient {
  constructor(apiKey, baseUrl = BASE) {
    this.apiKey = apiKey;
    this.baseUrl = baseUrl;
  }

  async request(method, path, body, { idempotencyKey } = {}) {
    const headers = {
      Authorization: `Bearer ${this.apiKey}`,
      "Content-Type": "application/json",
    };
    if (idempotencyKey) headers["Idempotency-Key"] = idempotencyKey;

    const res = await fetch(`${this.baseUrl}${path}`, {
      method,
      headers,
      body: body ? JSON.stringify(body) : undefined,
    });
    const payload = await res.json();
    if (!res.ok) {
      const error = new Error(payload.error.message);
      error.code = payload.error.code;
      error.status = res.status;
      throw error;
    }
    return payload;
  }

  get(path) { return this.request("GET", path); }
  post(path, body, opts) { return this.request("POST", path, body, opts); }
}

const sdp = new SdpClient(process.env.SDP_API_KEY);
const sdpAdmin = new SdpClient(process.env.SDP_ADMIN_API_KEY);
const idempotencyKey = (op) => `${op}-${crypto.randomUUID()}`;
```

Use `sdp` for routine operations and `sdpAdmin` for compliance operations. Every call that signs and sends takes an `Idempotency-Key`: a retry with the same key replays the original response instead of running twice. Create one key per logical operation, before the first attempt, and reuse it for every retry of that call.

Confirm the setup by finding a custody wallet that can sign:

```javascript title="list-wallets.js"
const { data } = await sdp.get("/v1/wallets");
const custodyWallet = data.wallets.find(
  (wallet) => wallet.status === "active" && wallet.isRuntimeExecutionAllowed
);
if (!custodyWallet) throw new Error("No active custody wallet can execute");

const signingCustodyWalletId = custodyWallet.id;
const custodyAddress = custodyWallet.publicKey;
```

`signingCustodyWalletId` is the SDP wallet record `id` (`cwlt_…`) that issuance requests take. It's not the provider's `walletId` or the Solana `publicKey`. `custodyAddress` is the public key, used only where an onchain address is needed. If no wallet is returned, finish your custody setup first.

## 3. Design the token

Before any API call, decide three things: the template, the compliance posture the token deploys with, and who holds its authorities. Your compliance officer reviews this design; the API calls in Section 4 follow from it.

### 1. Pick the template

SDP offers three **Tokenization Templates**, each a fixed set of [Token-2022](https://solana.com/docs/tokens/extensions) extensions for one institutional product shape:

- **`stablecoin`**: 6 decimals; `permanentDelegate` and `pausable` required; a blocklist by default. The right template for a regulated dollar.
- **`tokenized-security`**: 8 decimals; the same extensions plus an optional `scaledUiAmount`; an allowlist by default, with new accounts frozen. The right template for a regulated security.
- **`custom`**: 9 decimals and no required extensions. Use it only when neither template fits.

This tutorial uses `stablecoin`. Its required extensions give a US permitted payment stablecoin issuer the capabilities Section 5 uses. [Tokenization Templates](/docs/reference/issuance-token-types) has the details.

### 2. Set the compliance posture

Four fields on token creation set the posture you deploy with:

- **`isFreezable`**: `true` (the default). With `false`, the token deploys with no freeze authority, and freezing becomes impossible.
- **`isMintable`**: `true` (the default), so you can mint as new fiat reserves arrive at the custody bank.
- **`requiresAllowlist`**: leave it off for a payment stablecoin. The institutional pattern is screen before transfer, not gate by allowlist, and the token keeps its blocklist.
- **`maxSupply`**: an optional cap in UI units (a decimal string), useful for a pilot with a hard ceiling. Omit it for no cap.

### 3. Plan the authorities

A regulated stablecoin has four onchain authorities. At deploy, SDP gives all four to your custody wallet unless you assign others with `authorityCustodyWalletIds`:

- **`mint`**: creates new supply.
- **`freeze`**: freezes and unfreezes token accounts.
- **`permanentDelegate`**: moves or burns any holder's tokens without their signature, the capability the GENIUS Act requires for lawful orders.
- **`metadata`**: updates onchain metadata.

The **pause authority** belongs to the `pausable` extension and defaults to the mint authority. Move or revoke any authority later with `POST /v1/issuance/tokens/{tokenId}/authority`.

### 4. Capture the design as a config

Section 4 takes one input, the design above as an object. For the Treasury Pilot USD example used throughout:

```javascript title="token-config.js"
const tokenConfig = {
  template: "stablecoin",
  name: "Treasury Pilot USD",
  symbol: "TPUSD",
  decimals: 6,
  signingCustodyWalletId,
  description: "GENIUS-compliant treasury pilot stablecoin.",
  maxSupply: "100000000",
  isFreezable: true,
  isMintable: true,
};
```

## 4. Create and deploy

Two calls with the Developer key take the design onchain: one creates the record, one deploys it.

### 1. Create the token record

The first call writes the token to SDP's database. Nothing happens on Solana yet.

```javascript title="create-token.js"
const created = await sdp.post("/v1/issuance/tokens", tokenConfig);
const tokenId = created.data.token.id;
```

The `201` response returns the token with `status: "pending"` and `mintAddress: null`. Keep its `tok_…` id for the deploy call.

### 2. Deploy onchain

The deploy call creates the Token-2022 mint, signed by your custody wallet, and records the onchain addresses on the token:

```javascript title="deploy-token.js"
const deployKey = idempotencyKey("deploy");
const deployed = await sdp.post(
  `/v1/issuance/tokens/${tokenId}/deploy`,
  { signingCustodyWalletId },
  { idempotencyKey: deployKey }
);
const mintAddress = deployed.data.token.mintAddress;
```

A successful response carries the token with `status: "active"` and its `mintAddress`:

```json title="response.json"
{
  "data": {
    "token": {
      "id": "tok_e152fd38-...",
      "status": "active",
      "signingCustodyWalletId": "cwlt_123",
      "mintAddress": "6V5bTuMsmXyhdY2Hj6VWQZsuacugACBmPqNtQgGtar8L",
      "mintAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "freezeAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "metadataAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "extensions": {
        "defaultAccountState": "initialized",
        "permanentDelegate": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X"
      },
      "deployedAt": "2026-05-18T14:50:43.329Z"
    }
  }
}
```

`mintAuthority`, `freezeAuthority` and `metadataAuthority` are the public key of the custody wallet you deployed with. The permanent delegate appears in `extensions.permanentDelegate`, not as a top-level authority. From now on `signingCustodyWalletId` only records who deployed: each authority-gated call is checked against its live onchain authority, and a standard burn signs with its source wallet.

<Callout type="warn">
If a deploy fails before the mint lands, the token returns to `pending`. Retry with a new `Idempotency-Key`: the same key never deploys twice. If the mint lands but setting its metadata URI fails, SDP records the mint and returns `400 TRANSACTION_FAILED` with `details.mintAddress`. Don't redeploy.
</Callout>

### 3. Confirm the deploy

Check that the onchain state matches the record:

```javascript title="confirm-deploy.js"
const { data } = await sdp.get(`/v1/issuance/tokens/${tokenId}`);
console.log(`Status: ${data.token.status}`);
console.log(`Mint:   ${data.token.mintAddress}`);
```

A working deploy prints:

```text title="Output"
Status: active
Mint:   6V5bTuMsmXyhdY2Hj6VWQZsuacugACBmPqNtQgGtar8L
```

## 5. Configure compliance controls

Every other section is engineering. This one is the regulatory backbone.

Section 4(a)(5) of the GENIUS Act treats a permitted payment stablecoin issuer as a financial institution for purposes of the Bank Secrecy Act. The Act also requires "[the technological capability to comply with all lawful orders to seize, freeze, burn or prevent the transfer of outstanding stablecoins](https://www.skadden.com/insights/publications/2025/07/us-establishes-first-federal-regulatory-framework)."

The endpoints below map onto that phrase in order: screening first, freeze to block one account, seize to recover tokens, force burn as the final remedy. They use the Admin key and the `signingCustodyWalletId` from Section 2. SDP checks that the wallet holds the live freeze or permanent-delegate authority before signing.

Freeze, seize and force burn act on a holder's tokens, so they apply once tokens circulate (Section 6). Section 7 puts the freeze to a live test.

### Screen before you move

Screen every transfer destination and every allowlist entry before your application acts on it:

```javascript title="screen-address.js"
async function screenDestination(address) {
  const { data } = await sdpAdmin.post("/v1/compliance/address-screenings", {
    address,
    network: "solana",
    intent: "transfer_destination",
  });

  for (const provider of data.screening.providers) {
    if (provider.status !== "ok" || provider.riskScore > THRESHOLD) {
      throw new TransferBlocked(provider);
    }
  }
}
```

For an allowlist candidate, send `intent: "wallet_address_addition"` instead. One call checks every configured provider (Range, Elliptic, TRM and Chainalysis) and returns one result each. Write your policy against `providers[]`, not one provider, and fail closed: treat any status but `ok` (`pending`, `unavailable` or `error`) as a block, so one provider's outage can't wave a transfer through. `riskScore` can be `null`; decide how your policy treats that.

### Freeze when one account needs to stop

Freezing stops one holder's account without touching any other. Token-2022 enforces it onchain; SDP signs with the freeze authority.

```javascript title="freeze-account.js"
const holderFreezeKey = idempotencyKey("freeze");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/freeze`,
  {
    signingCustodyWalletId,
    accountAddress: holderAddress,
    reason: "Court order #2026-IL-0142",
  },
  { idempotencyKey: holderFreezeKey }
);
```

Pass the holder's wallet address. SDP finds the holder's [associated token account](https://solana.com/docs/tokens/basics/create-token-account) for TPUSD and freezes it, so transfers into or out of it fail onchain, not at SDP's gateway. Section 7 shows the error a frozen account returns.

### Seize for compliance recovery

Seize moves tokens out of a holder's account without their signature, through the **permanent delegate**: the Token-2022 extension that lets a named authority transfer or burn any holder's tokens. Use it for a court-ordered transfer or a sanctions matter where you must recover specific tokens to a controlled wallet.

```javascript title="seize-tokens.js"
const seizeKey = idempotencyKey("seize");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/seize`,
  {
    signingCustodyWalletId,
    seize: {
      source: holderAddress,
      destination: custodyAddress,
      amount: "50000.00",
      memo: "OFAC matter 2026-04-018",
    },
  },
  { idempotencyKey: seizeKey }
);
```

The memo stays on the transaction record. It's how your compliance officer matches the action, months later, to the court order or sanctions notice that authorized it.

### Force-burn as the final remedy

Force burn destroys tokens in a holder's account, with the same authority as seize. Reach for it only when the tokens can't be recovered to a controlled wallet, for example from a self-custodied address whose key you can't obtain.

```javascript title="force-burn.js"
const forceBurnKey = idempotencyKey("force-burn");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/force-burn`,
  {
    signingCustodyWalletId,
    forceBurn: {
      source: holderAddress,
      amount: "12000.00",
      memo: "regulator-ordered burn 2026-04-021",
    },
  },
  { idempotencyKey: forceBurnKey }
);
```

### Separation of duties

Freeze, seize and force burn need `issuance.enforce`, and screening needs `compliance.execute`, so only the Admin key from Section 2 can run them. Routine issuance can't escalate into a compliance action without a deliberate credential change. Every call also lands in SDP's audit log, which is the record a regulator will eventually ask for.

## 6. Mint the first tokens

Minting puts new supply into circulation. For a regulated stablecoin, every mint matches a reserve event: dollars arriving at the custody bank, attested by the reserve custodian and recorded against an issuance ticket. What you put in the memo is what your compliance officer reconciles against the reserve report.

### 1. Send the mint call

Minting needs `issuance.execute`, which the Developer key holds:

```javascript title="mint-tokens.js"
const mintKey = idempotencyKey("mint");
const minted = await sdp.post(
  `/v1/issuance/tokens/${tokenId}/mint`,
  {
    signingCustodyWalletId,
    mint: {
      destination: custodyAddress,
      amount: "1000000",
      memo: "Reserve mint Q2-2026, reference: ANB-RESV-2026-04-091",
    },
  },
  { idempotencyKey: mintKey }
);
```

Four field rules:

- **`signingCustodyWalletId`** must hold the current mint authority. SDP never falls back to the deployment wallet.
- **`destination`** is a Solana base58 address: your custody wallet for issuer-held supply, or a client's wallet for later mints.
- **`amount`** is a decimal string in UI units, not a number or a BigInt. `"1000000"` mints one million TPUSD at 6 decimals. A mint past `maxSupply` fails with `400 MAX_SUPPLY_EXCEEDED`.
- **`memo`** takes up to 100 characters and stays on the transaction record: the reference your compliance officer uses to reconcile the mint against the reserve custodian's monthly report.

### 2. Read the response

A successful mint returns the transaction record and the token account that received the tokens:

```json title="response.json"
{
  "data": {
    "transaction": {
      "id": "ttx_88240bf5-...",
      "type": "mint",
      "status": "confirmed",
      "signature": "51XZb4Tqm1G4LmSPUwnLrxENWmmhW9UE15LhxrwMrS6vKL4avFzKBBBcPNEQuiMEVgxWRgbdjJERo6K4taQEM9XG",
      "params": {
        "destination": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
        "amount": "1000000",
        "memo": "Reserve mint Q2-2026, reference: ANB-RESV-2026-04-091",
        "tokenAccount": "NLcEWVJ8oiHdbf6xuSLSAfKfJ1Gqcw4ksYHnkCyEy3t"
      }
    },
    "tokenAccount": "NLcEWVJ8oiHdbf6xuSLSAfKfJ1Gqcw4ksYHnkCyEy3t"
  }
}
```

`tokenAccount` is the destination's associated token account. SDP creates it on the first mint to that destination and reuses it after.

### 3. Tie mints to reserve attestations

<Callout type="info">
The GENIUS Act requires a permitted payment stablecoin issuer to publish a monthly attestation of reserve composition, signed by a registered public accounting firm, with separate CEO/CFO certification. The mint memo closes the engineering side of that obligation.
</Callout>

Every mint memo should carry at least a reserve reference that maps to one reserve event in the custodian's records. Two minimal patterns:

- **Single-deposit mint**: `"ANB-RESV-2026-04-091"`, the deposit reference the custody bank assigned when the reserves arrived.
- **Batched mint against a reserve commitment**: `"Q2-2026 commitment tranche 3 of 6"`, one scheduled release of a pre-arranged commitment.

A memo that doesn't reconcile to a reserve record doesn't work. The compliance officer needs a one-to-one mapping, and the auditor signing the report depends on it.

### 4. Confirm the supply

```javascript title="confirm-supply.js"
const { data } = await sdp.get(`/v1/issuance/tokens/${tokenId}`);
console.log(`Total supply: ${data.token.totalSupply}`);
```

Prints:

```text title="Output"
Total supply: 1000000
```

## 7. Test a transfer and a compliance action

Section 5's controls only matter if they enforce. Here you move tokens between two wallets, then freeze the destination and watch the next transfer fail. Token-2022 enforces the block onchain, not SDP's gateway.

### 1. The clean transfer

Transfers use `POST /v1/payments/transfers`, which needs `transfers.execute` (the Developer key has it). Screen the destination first with Section 5's `screenDestination`:

```javascript title="transfer-tokens.js"
await screenDestination(destinationAddress);

const transfer = await sdp.post(
  "/v1/payments/transfers",
  {
    sourceCustodyWalletId: signingCustodyWalletId,
    destination: destinationAddress,
    token: mintAddress,
    amount: "100",
    memo: "Treasury Pilot internal transfer #042",
  },
  { idempotencyKey: idempotencyKey("transfer") }
);
```

Three field rules:

- **`sourceCustodyWalletId`** is the SDP wallet `id` (`cwlt_…`) from `GET /v1/wallets`, not its public key or provider `walletId`.
- **`token`** is the mint address from Section 4's deploy response, not the SDP token id (`tok_…`).
- **`destination`** is any valid Solana address; SDP doesn't need to know it.

A successful response includes the onchain signature once the transaction confirms:

```json title="response.json"
{
  "data": {
    "transfer": {
      "id": "xfr_f570debc-...",
      "type": "transfer",
      "direction": "outbound",
      "status": "confirmed",
      "custodyWalletId": "cwlt_123",
      "providerWalletId": "privy_jfxdbsq4bg6dxzsd7imgon3j",
      "signature": "ekNe4HK67AXptsx6krYATZd5xYeq8wYQShmN9oHUdAipVJVFELGwiLhdJNCAbyN2TPv9SwzBTNz6igoAfWTdCYP",
      "source": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "destination": "2H2w3hSxAPTybuTL7LkhPbyk6bWYi94x2J4aqBhhyJL2",
      "token": "6V5bTuMsmXyhdY2Hj6VWQZsuacugACBmPqNtQgGtar8L",
      "amount": "100",
      "memo": "Treasury Pilot internal transfer #042"
    }
  }
}
```

### 2. Freeze the destination

Freeze the destination's TPUSD account with the Admin key; the Developer key lacks `issuance.enforce`:

```javascript title="freeze-destination.js"
const transferFreezeKey = idempotencyKey("freeze");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/freeze`,
  {
    signingCustodyWalletId,
    accountAddress: destinationAddress,
    reason: "Compliance hold pending OFAC review 2026-04-019",
  },
  { idempotencyKey: transferFreezeKey }
);
```

SDP records the frozen account in its audit trail and applies the Token-2022 freeze to the destination's associated token account. You can verify it on Solana Explorer:

![Freeze transaction on Solana Explorer in devnet, showing the Token-2022 FreezeAccount instruction applied to the destination's associated token account.](/issue-a-regulated-stablecoin/03-freeze-on-chain-explorer.png)

### 3. Attempt the transfer again

Run the same transfer. This time it fails:

```javascript title="transfer-blocked.js"
try {
  await sdp.post(
    "/v1/payments/transfers",
    {
      sourceCustodyWalletId: signingCustodyWalletId,
      destination: destinationAddress,
      token: mintAddress,
      amount: "100",
      memo: "Compliance test, expecting block",
    },
    { idempotencyKey: idempotencyKey("blocked-transfer") }
  );
} catch (error) {
  if (error.code === "ACCOUNT_FROZEN") {
    // A compliance verdict: log it to the compliance system and don't retry.
    await reportToCompliance(error);
  } else {
    // Anything else: apply your retry policy.
    throw error;
  }
}
```

SDP answers `400 ACCOUNT_FROZEN`. Its message carries the program's own error, `custom program error: 0x11`: Token-2022's `AccountFrozen` (decimal 17). The program refused the transaction, not SDP's gateway. SDP records the transfer as failed, and a retry with the same `Idempotency-Key` returns the same error, so treat it as a verdict. After the account is unfrozen, send a new key.

### 4. Clean up

In production, unfreeze only after the compliance review resolves. In the sandbox you can unfreeze now:

```javascript title="unfreeze-account.js"
await sdpAdmin.post(`/v1/issuance/tokens/${tokenId}/unfreeze`, {
  signingCustodyWalletId,
  accountAddress: destinationAddress,
});
```

With the freeze cleared, the destination can receive transfers again.

## 8. Production transition checklist

Moving from sandbox to production keys is not a flag flip. It's the moment your compliance officer signs against the runbook your team has built: a few things change mechanically, and a longer list is what your institution attests to.

### 1. What changes mechanically

- **API keys**: create new Developer and Admin keys in your production project, as in Section 2.
- **Custody**: production uses your custodian's wallets (Anchorage Digital Bank for most US institutional issuers). The sandbox Privy wallet doesn't carry over.
- **Network**: production projects run on mainnet; the sandbox runs on devnet.
- **Screening providers**: confirm the production provider mix matches your compliance policy. Screen a known address and check that each provider returns `status: "ok"` before live traffic.
- **Idempotency keys**: derive them from the operation, for example `mint-${reserveDepositReference}`, rather than at random, so your runbook can resend without minting twice.

### 2. What your compliance officer signs off on

Before a production key sees real traffic, the compliance officer needs evidence that the posture from Section 1 is operational, not aspirational. The minimum sign-off list:

- **GENIUS Section 4(a)(5) capabilities demonstrated**: screening, freeze, seize and force burn each exercised in the sandbox, with the response in the audit trail.
- **BSA/AML program documented**: a written risk-based policy with internal controls, ongoing customer due diligence, independent testing, and a named US-located AML/CFT compliance officer (proposed 31 CFR § 1033.210 under the FinCEN/OFAC implementing rules).
- **Sanctions program ready**: OFAC screening configured and tested, the technical capability to block transactions, and a secondary-market screening procedure.
- **Reserve attestation cadence agreed**: a registered public accounting firm engaged, a monthly examination schedule signed, and the CEO/CFO certification process defined.
- **Audit trail reviewed**: SDP's audit entries checked for completeness, and the Section 6 mint memos reconciled to reserve references in the custody bank's records.
- **Incident response runbook**: the playbook for a freeze, seize or force-burn order. Who signs in with which credential when a court order arrives, how long the chain of custody runs, and where the documentation lands.

### 3. The cutover

Once the sign-off is in, the cutover is small. Create the production keys, store them with your other live secrets, and update your runtime environment. Run the Section 2 wallet check against production to confirm the wallets are bound. Your first production mint should match a real fiat reserve event at your custody bank.
