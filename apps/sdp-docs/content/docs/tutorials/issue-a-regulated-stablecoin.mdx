This tutorial shows you how to issue a regulated stablecoin on Solana. The result is a token that a
bank's compliance committee and a federal examiner can review.

Issuing a regulated stablecoin is not the same as deploying a token. It requires institutional
custody, integrated compliance, and reversible operations from the first day. The
[GENIUS Act](https://www.gibsondunn.com/the-genius-act-a-new-era-of-stablecoin-regulation/) treats
those capabilities as preconditions, not as features.

The authors ran every code sample in this tutorial against the SDP sandbox in September 2026. The
request and response shapes below are what the API returned.

## 1. What a regulated stablecoin requires

This tutorial assumes that you are a developer at a financial institution or a fintech, and that
you work under a compliance officer's review. That officer sees the decisions you make here.

Three conditions shape every step that follows.

**A federally chartered custodian holds the signing keys.** A regulated stablecoin is not held on
an engineer's laptop. For a US issuer operating under the GENIUS Act framework, the custodian is
usually Anchorage Digital Bank or an equivalent federally chartered crypto bank. The custodian
holds the keys for the mint, freeze, and permanent-delegate authorities.

**Compliance is integrated from the first day.** SDP screens every transfer destination before it
builds the transfer. Every frozen account ties back to a court order, a sanctions notice, or an
internal compliance ticket. The screening endpoints sit in the same API as the mint and burn
endpoints.

**Freeze, seize, and force-burn are required capabilities.** The GENIUS Act requires you to have
them ready before launch. They exist in the SDP API because the regulation requires them, and your
compliance officer checks for them. Section 5 covers each one in detail.

## 2. Prerequisites

You need the following before you start. Expect about thirty minutes if you have none of them
today.

- An SDP account and an organization.
- A configured custody provider.
- Two project-scoped API keys. One is for routine operations. One is for compliance operations.
- A funded devnet wallet.

### Account and organization

Sign up at [platform.solana.com](https://platform.solana.com) with email, Google, or GitHub. Create
your organization when the dashboard prompts you.

SDP provisions a matching organization on its side through a [Clerk](https://clerk.com) webhook.
The dashboard's onboarding cards clear once that sync lands.

### Custody provider

An institutional issuer in the US pipeline configures
[Anchorage Digital Bank](https://www.anchorage.com/platform/stablecoin-issuance) as the custodian.
Anchorage is not entitled by default, so an administrator must have access granted to your
organization first. The Anchorage onboarding team then provisions the signing wallets and binds
them to your SDP organization.

If you work on the self-serve sandbox without an Anchorage relationship, SDP provisions Privy
wallets for development access instead. The API is identical. Only the `provider` field on the
wallet record differs.

### Configure your client and verify the setup

Configure two HTTP clients, one per project-scoped key, with a thin wrapper around `fetch`.

Every state-mutating execute endpoint in SDP supports an `Idempotency-Key` HTTP header. Those
endpoints are deploy, mint, burn, seize, force-burn, and authority. A retry with the same key
replays the original response. A retry with a different key is a new request. The header is what
makes network-level retries safe under partial failure, so the client below sends it.

```javascript title="sdp-client.js"
const BASE = "https://api.solana.com";

class SdpClient {
  constructor(apiKey, baseUrl = BASE) {
    this.apiKey = apiKey;
    this.baseUrl = baseUrl;
  }

  async request(method, path, body, { idempotencyKey } = {}) {
    const headers = {
      Authorization: `Bearer ${this.apiKey}`,
      "Content-Type": "application/json",
    };
    if (idempotencyKey) headers["Idempotency-Key"] = idempotencyKey;

    const res = await fetch(`${this.baseUrl}${path}`, {
      method,
      headers,
      body: body ? JSON.stringify(body) : undefined,
    });
    const payload = await res.json();
    if (!res.ok) throw new Error(`${payload.error.code}: ${payload.error.message}`);
    return payload;
  }

  get(path) { return this.request("GET", path); }
  post(path, body, opts) { return this.request("POST", path, body, opts); }
}

const sdp = new SdpClient(process.env.SDP_API_KEY);
const sdpAdmin = new SdpClient(process.env.SDP_ADMIN_API_KEY);
const idempotencyKey = (op) => `${op}-${crypto.randomUUID()}`;
```

Use `sdp` for routine operations: create, mint, and burn. Use `sdpAdmin` for compliance operations:
screening, freeze, seize, and force-burn.

Generate one idempotency key per logical operation, not per retry. Create the key once before the
first attempt. Store it in a variable, and reuse that same value for every retry of the same call.

Now confirm the setup. List the wallets bound to your project:

```javascript title="list-wallets.js"
const { data } = await sdp.get("/v1/wallets");
const custodyWallet = data.wallets.find(
  (wallet) => wallet.status === "active" && wallet.isRuntimeExecutionAllowed
);
if (!custodyWallet) throw new Error("No active custody wallet can execute");

const signingCustodyWalletId = custodyWallet.id;
const custodyAddress = custodyWallet.publicKey;
console.log(`Custody wallets configured: ${data.wallets.length}`);
console.log(`Deployment wallet: ${signingCustodyWalletId}`);
```

A working setup prints:

```text title="Output"
Custody wallets configured: 2
Deployment wallet: cwlt_123
```

If the response includes an active wallet with `isRuntimeExecutionAllowed: true`, your custody is
bound. You are ready to deploy a token.

If the response returns no wallets, your custody provider has not finished provisioning. For the
Anchorage pipeline, contact your onboarding lead. For the self-serve sandbox, wait a minute and run
the call again. Privy's first wallet provision can lag the SDP organization creation by a few
seconds.

Keep both values. `signingCustodyWalletId` is the SDP wallet record `id` (`cwlt_*`) that issuance
requests use. It is not the provider-specific `walletId`, and it is not the Solana `publicKey`.
`custodyAddress` is that public key. Use it only where an onchain address is required.

## 3. Design the token

Before any API call, decide three things: which template to start from, what compliance posture the
token deploys with, and which authorities the custodian holds. Your compliance officer reviews this
design. The API calls in Section 4 are the mechanical follow-through.

### Pick the template

A **Tokenization Template** prescribes a fixed set of
[Token-2022](https://solana.com/docs/tokens/extensions) extensions for one class of institutional
product. Call `GET /v1/issuance/templates` to list the templates available to your project and the
defaults each one applies.

Three of those templates matter here:

- **`stablecoin`**. 6 decimals by default. Required extensions: `permanentDelegate` and `pausable`.
  The **Token Access Control** allowlist is off. Use this template for a regulated dollar.
- **`tokenized-security`**. 8 decimals. Required extensions: `permanentDelegate` and `pausable`.
  The `scaledUiAmount` extension is available on this template, but it is opt-in rather than
  required. The Token Access Control allowlist is on, and accounts open frozen. Use this template
  for a regulated security.
- **`custom`**. 9 decimals. No required extensions. Use this template only when neither template
  above fits.

This tutorial uses `stablecoin`. Its required extensions are what a US permitted payment stablecoin
issuer needs to satisfy the technological-capability mandate in the GENIUS Act. Section 5 covers
that mandate.

### Set the compliance posture

Four fields on token creation determine the posture you deploy with. Three of them are booleans.
The fourth, `maxSupply`, is an optional decimal string.

- **`isFreezable`**. Set it to `true`. If it is `false` at create time, the token deploys with no
  freeze authority, and you cannot freeze an account afterward.
- **`isMintable`**. Set it to `true` for an active stablecoin. You mint as new fiat reserves arrive
  at the custody bank.
- **`requiresAllowlist`**. Turns on the allowlist mode of Token Access Control. Only listed
  addresses can then receive the token. Leave it off for a payment stablecoin. The institutional
  pattern is to screen before each transfer, not to gate by allowlist. The `tokenized-security`
  template turns this on automatically.
- **`maxSupply`**. An optional supply cap, written as a decimal string in display units. Use it for
  a pilot program with a hard ceiling. Omit it for uncapped supply.

### Plan the authorities

A regulated stablecoin has five onchain authorities. Each one is a distinct role.

- **`mint`**. Authorizes new supply.
- **`freeze`**. Freezes and unfreezes one token account.
- **`permanentDelegate`**. Moves or burns any holder's tokens without their signature. This is the
  technological capability that the GENIUS Act requires for lawful orders.
- **`metadata`**. Updates the token's onchain metadata.
- **The pause authority**. Pauses and resumes all transfers. It lives on the `pausable` extension
  configuration rather than on the mint.

At deploy, SDP sets the first four authorities to your custody signer. SDP sets the pause authority
to the `mint` authority unless you set it explicitly.

You can delegate or revoke any authority later with
`POST /v1/issuance/tokens/{tokenId}/authority`. Leaving every authority with the custodian is the
institutional baseline.

### Capture the design as a config

Section 4 takes one input: a configuration object that holds the design choices above. This is the
Treasury Pilot USD example that the rest of the tutorial uses.

```javascript title="token-config.js"
const tokenConfig = {
  template: "stablecoin",
  name: "Treasury Pilot USD",
  symbol: "TPUSD",
  decimals: 6,
  signingCustodyWalletId,
  description: "GENIUS-compliant treasury pilot stablecoin.",
  maxSupply: "100000000",
  isFreezable: true,
  isMintable: true,
};
```

Your design is captured. You are ready to make the first state-mutating call.

## 4. Create and deploy the token

Two API calls take the design from an object literal to a deployed stablecoin on Solana. The first
call creates the record. The second call deploys it onchain. Both run from the Developer key
(`sdp`).

### Create the token record

The first call writes the token's metadata to SDP's database. Nothing happens on Solana yet. The
token starts at `status: "pending"` with no `mintAddress`.

```javascript title="create-token.js"
const created = await sdp.post("/v1/issuance/tokens", tokenConfig);
const tokenId = created.data.token.id;
```

A successful response:

```json title="response.json"
{
  "data": {
    "token": {
      "id": "tok_e152fd38-...",
      "template": "stablecoin",
      "symbol": "TPUSD",
      "decimals": 6,
      "status": "pending",
      "signingCustodyWalletId": "cwlt_123",
      "mintAddress": null,
      "isFreezable": true,
      "isMintable": true,
      "requiresAllowlist": false,
      "maxSupply": "100000000"
    }
  }
}
```

Save the `tok_*` ID. The deploy call uses it.

### Deploy the token onchain

The deploy call submits a Token-2022 mint creation transaction to Solana through the custody
signer. SDP then updates the token record with the resulting onchain addresses.

```javascript title="deploy-token.js"
const deployKey = idempotencyKey("deploy");
const deployed = await sdp.post(
  `/v1/issuance/tokens/${tokenId}/deploy`,
  { signingCustodyWalletId },
  { idempotencyKey: deployKey }
);
const mintAddress = deployed.data.token.mintAddress;
```

A successful response carries the deployed token record. The record has `status: "active"` and a
populated onchain `mintAddress`.

```json title="response.json"
{
  "data": {
    "token": {
      "id": "tok_e152fd38-...",
      "status": "active",
      "signingCustodyWalletId": "cwlt_123",
      "mintAddress": "6V5bTuMsmXyhdY2Hj6VWQZsuacugACBmPqNtQgGtar8L",
      "mintAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "freezeAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "metadataAuthority": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "extensions": {
        "defaultAccountState": "initialized",
        "permanentDelegate": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X"
      },
      "deployedAt": "2026-05-18T14:50:43.329Z"
    }
  }
}
```

The `mintAuthority`, `freezeAuthority`, and `metadataAuthority` all resolve to the public key of
the `signingCustodyWalletId` you supplied. SDP sets the `permanentDelegate` at the same time. It
appears on the token record's `extensions.permanentDelegate` field rather than as a top-level
authority.

After deployment, the token's `signingCustodyWalletId` records historical attribution. It is not a
preferred signer, and it is not a fallback. SDP checks an authority-gated operation against the
live onchain authority, and a standard burn uses its own source wallet.

<Callout type="warn">
Deploy can return a bare `500 INTERNAL_ERROR` with no `details` field. The most common cause on
devnet is an unfunded custody wallet. Section 2 covers funding it from the browser faucet. Any
other downstream Solana RPC failure also appears this way.

Fund the custody wallet from the faucet. Then call `/deploy` again with the same `Idempotency-Key`
to replay the prior result, or with a fresh key to make a new attempt. SDP treats different keys as
different requests.
</Callout>

### Confirm the deploy

Confirm that the onchain state matches the record before you move to Section 5.

```javascript title="confirm-deploy.js"
const { data } = await sdp.get(`/v1/issuance/tokens/${tokenId}`);

```

## 5. Configure compliance controls

This section covers the controls that the regulation requires.

Section 4(a)(5) of the GENIUS Act treats a permitted payment stablecoin issuer as a financial
institution for the purposes of the Bank Secrecy Act. That sentence is what makes everything below
load-bearing.

The Act also requires you to have "[the technological capability to comply with all lawful orders to seize, freeze, burn or prevent the transfer of outstanding stablecoins](https://www.skadden.com/insights/publications/2025/07/us-establishes-first-federal-regulatory-framework)."
The endpoints in this section map onto that phrase, in the order you meet them. Screening comes
first. Freeze blocks one account. Seize recovers tokens. Force-burn is the final remedy.

The issuance selectors below reuse the `signingCustodyWalletId` from Section 2. SDP verifies that
this wallet controls the live freeze or permanent-delegate authority before it signs.

### Screen before you move funds

Screen every transfer destination and every allowlist entry before your application acts on it.
Screening takes one API call.

```javascript title="screen-address.js"
const response = await sdpAdmin.post("/v1/compliance/address-screenings", {
  address: destinationAddress,
  network: "solana",
  intent: "transfer_destination",
});

for (const provider of response.data.screening.providers) {
  if (provider.status === "error" || provider.riskScore > THRESHOLD) {
    throw new TransferBlocked(provider);
  }
}
```

SDP integrates with four screening providers: Range, Elliptic, TRM, and Chainalysis. SDP enables no
compliance provider by default, so an administrator configures the providers for your organization
first.

One call then fans out to every configured provider and returns one array entry per provider. Write
your code against that array rather than against a named provider. Iterate over `providers[]`. Fail
closed on any `status: "error"` and on any threshold breach.

A single provider can be unavailable for credential reasons or rate-limit reasons. A fail-closed
policy keeps you defensible when one feed degrades.

On the sandbox response that this tutorial cites, Range and Elliptic return numeric scores. TRM
returns a healthy status without scoring a fresh address. Chainalysis returns an upstream
credential error. Treat each provider's verdict as one signal. Your policy must not depend on a
single provider's availability.

### Freeze one account

A freeze halts one holder's account and touches no other holder. The freeze is onchain, and the
Token-2022 program enforces it. SDP signs the freeze instruction with the freeze authority that was
set at deploy.

```javascript title="freeze-account.js"
const holderFreezeKey = idempotencyKey("freeze");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/freeze`,
  {
    signingCustodyWalletId,
    accountAddress: holderAddress,
    reason: "Court order #2026-IL-0142",
  },
  { idempotencyKey: holderFreezeKey }
);
```

Pass the holder's wallet address. SDP derives the
[Associated Token Account](https://solana.com/docs/tokens/basics/create-token-account) that holds
that holder's TPUSD balance, and freezes it. Once the account is frozen, transfers to it and from
it fail at the program level, not at SDP's gateway.

Section 7 runs this block live and shows the error that the frozen account returns.

### Seize tokens for compliance recovery

A seize moves tokens out of a holder's account without their signature. It uses the **permanent
delegate** authority that was set at deploy.

The permanent delegate is a Token-2022 extension. It grants a named authority the right to transfer
or burn any holder's tokens, whatever the holder signs. This is the technological capability that
the GENIUS Act requires you to have ready for lawful orders. The institutional use case is a
court-ordered transfer, or a sanctions matter where you must recover specific tokens to a
controlled wallet.

```javascript title="seize-tokens.js"
const seizeKey = idempotencyKey("seize");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/seize`,
  {
    signingCustodyWalletId,
    seize: {
      source: holderAddress,
      destination: custodyAddress,
      amount: "50000.00",
      memo: "OFAC matter 2026-04-018",
    },
  },
  { idempotencyKey: seizeKey }
);
```

SDP stores the memo on the transaction record. The memo is the audit attribution that your
compliance officer reads months later, when they reconcile the action against the court order or
the sanctions notice that authorized it.

### Force-burn as the final remedy

A force-burn destroys tokens in a holder's account. It uses the same authority as a seize, with a
different effect. Use it only when you cannot recover the tokens to a controlled wallet. One
example is a self-custodied address whose key you cannot obtain.

```javascript title="force-burn.js"
const forceBurnKey = idempotencyKey("force-burn");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/force-burn`,
  {
    signingCustodyWalletId,
    forceBurn: {
      source: holderAddress,
      amount: "12000.00",
      memo: "regulator-ordered burn 2026-04-021",
    },
  },
  { idempotencyKey: forceBurnKey }
);
```

### Keep the two keys separate

Every endpoint in this section requires the `tokens:admin` permission. Keep two project-scoped API
keys:

- **Developer key**. Routine create, mint, and burn calls.
- **Admin key**. Screen, freeze, seize, and force-burn.

A compliance officer reviewing this design sees a clean separation. Routine issuance cannot
escalate into a compliance action without a deliberate credential change.

Every call writes an entry through SDP's audit service. That trail is the artifact a regulator asks
for, and it is not optional.

## 6. Mint the first tokens

Minting is how new supply enters circulation. For a regulated stablecoin, every mint corresponds to
a fiat reserve event: dollars arrive at the custody bank, the reserve custodian attests to them,
and SDP records the mint against an issuance ticket.

The mint call is small. What you put in the memo field is what your compliance officer reconciles
against the reserve report.

### Send the mint call

Minting requires the `tokens:write` permission, so the Developer key (`sdp`) is the right
credential.

```javascript title="mint-tokens.js"
const mintKey = idempotencyKey("mint");
const minted = await sdp.post(
  `/v1/issuance/tokens/${tokenId}/mint`,
  {
    signingCustodyWalletId,
    mint: {
      destination: custodyAddress,
      amount: "1000000",
      memo: "Reserve mint Q2-2026, reference: ANB-RESV-2026-04-091",
    },
  },
  { idempotencyKey: mintKey }
);
```

Four field rules matter here:

- **`signingCustodyWalletId`** is the SDP wallet `id` from Section 2. SDP verifies that this wallet
  controls the current mint authority. SDP does not fall back to the historical deployment wallet.
- **`destination`** is a Solana base58 address. For the initial pattern where the issuer holds the
  supply, this is your custody wallet's public key. For later mints to client wallets, it is the
  recipient's wallet.
- **`amount`** is a decimal string in display units, after decimals are applied. Do not pass a
  number, and do not pass a BigInt. `"1000000"` mints one million TPUSD, because the token has 6
  decimals.
- **`memo`** is up to 100 characters. SDP stores it on the transaction record. This is the
  institutional audit attribution. Your compliance officer uses it months later to reconcile the
  mint against the reserve custodian's monthly report.

### Read the response

A successful mint returns the transaction record and the token account that received the tokens.

```json title="response.json"
{
  "data": {
    "transaction": {
      "id": "ttx_88240bf5-...",
      "type": "mint",
      "status": "confirmed",
      "signature": "51XZb4Tqm1G4LmSPUwnLrxENWmmhW9UE15LhxrwMrS6vKL4avFzKBBBcPNEQuiMEVgxWRgbdjJERo6K4taQEM9XG",
      "params": {
        "destination": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
        "amount": "1000000",
        "memo": "Reserve mint Q2-2026, reference: ANB-RESV-2026-04-091",
        "tokenAccount": "NLcEWVJ8oiHdbf6xuSLSAfKfJ1Gqcw4ksYHnkCyEy3t"
      }
    },
    "tokenAccount": "NLcEWVJ8oiHdbf6xuSLSAfKfJ1Gqcw4ksYHnkCyEy3t"
  }
}
```

The `tokenAccount` is the Associated Token Account that holds the newly minted tokens. SDP creates
it on the first mint to that destination if it does not already exist. Later mints to the same
destination reuse it.

### Tie the mint to the reserve attestation

<Callout type="info">
The GENIUS Act requires a permitted payment stablecoin issuer to publish a monthly public
attestation of reserve composition. A registered public accounting firm signs that attestation, and
the CEO and CFO certify it separately. The mint memo closes the loop on the engineering side of
that obligation.
</Callout>

Every mint memo carries at minimum a reserve reference number. That number maps to one reserve
event in the custodian's records. Two patterns meet the minimum:

- **Single-deposit mint**: `"ANB-RESV-2026-04-091"`. This is the deposit reference that the custody
  bank assigned when it received the fiat reserves.
- **Batched mint against a reserve commitment**: `"Q2-2026 commitment tranche 3 of 6"`. This is a
  pre-arranged reserve commitment, broken into scheduled releases.

Do not write a mint memo that cannot be matched to a reserve record. The compliance officer reading
the attestation report needs a one-to-one mapping, and the auditor signing the report depends on
it.

### Confirm the supply

```javascript title="confirm-supply.js"
const { data } = await sdp.get(`/v1/issuance/tokens/${tokenId}`);
console.log(`Total supply: ${data.token.totalSupply}`);
```

Prints:

```text title="Output"

```

## 7. Test a transfer and a compliance action

The compliance controls in Section 5 matter only if they enforce. This section moves tokens between
two wallets, then tests the freeze authority live.

### Send a clean transfer

Transfers run on the `/v1/payments/transfers` endpoints, which are separate from the issuance
endpoints that Section 4 used. The call requires the `payments:write` and `wallets:read`
permissions. The Developer key (`sdp`) carries both.

```javascript title="transfer-tokens.js"
const sourceCustodyWalletId = signingCustodyWalletId;

const screening = await sdpAdmin.post("/v1/compliance/address-screenings", {
  address: destinationAddress,
  network: "solana",
  intent: "transfer_destination",
});

for (const provider of screening.data.screening.providers) {
  if (provider.status === "error" || provider.riskScore > THRESHOLD) {
    throw new TransferBlocked(provider);
  }
}

const transfer = await sdp.post(
  "/v1/payments/transfers",
  {
    sourceCustodyWalletId,
    destination: destinationAddress,
    token: mintAddress,
    amount: "100",
    memo: "Treasury Pilot internal transfer #042",
  },
  { idempotencyKey: idempotencyKey("transfer") }
);
```

Three field rules matter here:

- **`sourceCustodyWalletId`** is the SDP wallet `id` (`cwlt_*`) that `GET /v1/wallets` returns. It
  is not the wallet's public key, and it is not the provider-specific `walletId`.
- **`token`** is the onchain mint address from the deploy response in Section 4. It is not the SDP
  token ID (`tok_*`).
- **`destination`** is any valid Solana base58 address. It does not have to be a wallet that SDP
  knows about.

A successful response includes the onchain signature once the transaction confirms.

```json title="response.json"
{
  "data": {
    "transfer": {
      "id": "xfr_f570debc-...",
      "type": "transfer",
      "direction": "outbound",
      "status": "confirmed",
      "custodyWalletId": "cwlt_123",
      "providerWalletId": "privy_jfxdbsq4bg6dxzsd7imgon3j",
      "signature": "ekNe4HK67AXptsx6krYATZd5xYeq8wYQShmN9oHUdAipVJVFELGwiLhdJNCAbyN2TPv9SwzBTNz6igoAfWTdCYP",
      "source": "ASy986dzvVqHHV2Ftfe9ZKshKZhEEQwuAoPoKMc64A9X",
      "destination": "2H2w3hSxAPTybuTL7LkhPbyk6bWYi94x2J4aqBhhyJL2",
      "token": "6V5bTuMsmXyhdY2Hj6VWQZsuacugACBmPqNtQgGtar8L",
      "amount": "100",
      "memo": "Treasury Pilot internal transfer #042"
    }
  }
}
```

### Freeze the destination

Freeze the destination's TPUSD account with the Admin key. Freeze requires `tokens:admin`, which
the Developer key does not carry.

```javascript title="freeze-destination.js"
const transferFreezeKey = idempotencyKey("freeze");
await sdpAdmin.post(
  `/v1/issuance/tokens/${tokenId}/freeze`,
  {
    signingCustodyWalletId,
    accountAddress: destinationAddress,
    reason: "Compliance hold pending OFAC review 2026-04-019",
  },
  { idempotencyKey: transferFreezeKey }
);
```

The freeze records a frozen account in SDP's audit trail. It also applies the Token-2022 freeze
instruction to the destination's Associated Token Account onchain. You can verify the onchain side
on Solana Explorer.

### Attempt the transfer again

Run the same transfer call. This time it fails.

```javascript title="transfer-blocked.js"
try {
  await sdp.post(
    "/v1/payments/transfers",
    {
      sourceCustodyWalletId,
      destination: destinationAddress,
      token: mintAddress,
      amount: "100",
      memo: "Compliance test, expecting block",
    },
    { idempotencyKey: idempotencyKey("blocked-transfer") }
  );
} catch (error) {
  // handle the onchain block (see the error-handling section below)
}
```

SDP returns this error envelope, with HTTP status 502:

```json title="response.json"
{
  "error": {
    "code": "SOLANA_RPC_ERROR",
    "message": "Failed to sign and send transaction: RPC Error -32000: Invalid transaction: Transaction simulation failed: Error processing Instruction 1: custom program error: 0x11"
  }
}
```

This is the one error pattern to learn from this tutorial, and it is the reason the envelope reads
the way it does.

The outer code, `SOLANA_RPC_ERROR`, names the family of failure. It tells you that an upstream call
failed. It is not the compliance verdict. The reason lives in the wrapped message:
`custom program error: 0x11`. That is Token-2022's `AccountFrozen` signal, decimal 17. The
Token-2022 program enforced the block onchain. SDP's gateway did not.

Treat `0x11` as a compliance verdict, not as a failure you can retry. The same rule applies
whenever SDP wraps a downstream Solana RPC error: the outer code is the family of failure, and the
wrapped code is the actual reason.

### Parse the wrapped error

Write your error handler against the wrapped onchain code rather than against the outer SDP code.

```javascript title="parse-error.js"
function isOnChainCompliance(error) {
  return error.message?.includes("custom program error: 0x11");
}

try {
  // transfer attempt
} catch (error) {
  if (isOnChainCompliance(error)) {
    // log to the compliance system, do not retry
    return reportToCompliance(error);
  }
  // anything else: treat as a transient RPC failure and apply your retry policy
  throw error;
}
```

### Clean up

In production, you unfreeze only after the underlying compliance review resolves. In the sandbox,
you can unfreeze immediately.

```javascript title="unfreeze-account.js"
await sdpAdmin.post(`/v1/issuance/tokens/${tokenId}/unfreeze`, {
  signingCustodyWalletId,
  accountAddress: destinationAddress,
});
```

The freeze is cleared, so the destination can receive transfers again. Section 8 covers the
production transition. It lists what changes between `sk_test_` and `sk_live_`, and which checks
your compliance officer signs against before this same code runs on mainnet.

## 8. Production transition checklist

The work between `sk_test_` and `sk_live_` is not a flag change. It is the moment your compliance
officer signs against the runbook your engineering team has built since Section 2.

Going to production changes six artifacts mechanically. It also adds a longer list of items that
your institution attests to.

### What changes mechanically

Your sandbox setup rests on six artifacts. Each one swaps for a production equivalent.

- **API keys**. Replace your project-scoped Developer and Admin keys with `sk_live_` keys minted
  from your production project. Use the bootstrap pattern from Section 2 with a fresh Admin key.
  Select the `default-production` project from `GET /v1/projects` instead of `default-sandbox`, and
  mint fresh project-scoped keys under it.
- **Custody provider**. In production, `provider` names your federally chartered custodian. For
  most US institutional issuers that is Anchorage Digital Bank, bound to your organization through
  the Anchorage onboarding flow. The Privy sandbox wallets do not carry over.
- **Solana cluster**. Mainnet replaces devnet. Your custody bank funds the custody address as part
  of its standard operational support. You do not use a faucet.
- **API base URL**. `https://api.solana.com` is the base URL in production and in sandbox. It does
  not change.
- **Screening providers**. Confirm that the production provider mix matches your compliance team's
  policy. Run `POST /v1/compliance/address-screenings` against a known address before live traffic.
  Confirm that every provider your policy depends on returns `status: "ok"`, and that your handler
  fails closed for any provider that does not.
- **Idempotency-Key strategy**. In production, generate idempotency keys deterministically per
  operation, for example `mint-${reserveDepositReference}`. Do not generate a random key per
  attempt. A deterministic key lets your runbook resend a call safely without minting twice.

### What your compliance officer signs off on

Before any `sk_live_` key sees real traffic, your compliance officer needs evidence that the
posture from Section 1 is operational rather than aspirational. This is the minimum sign-off list.

- **GENIUS Section 4(a)(5) capabilities demonstrated**. Screening, freeze, seize, and force-burn
  each exercised in the sandbox, with a captured response in the audit trail.
- **BSA/AML program documented**. A written risk-based policy with internal controls, ongoing
  customer due diligence, and independent testing. A US-located AML/CFT compliance officer named,
  under proposed 31 CFR § 1033.210 in the FinCEN and OFAC implementing rules.
- **Sanctions program ready**. An OFAC screening provider configured and tested, the technical
  capability to block transactions in place, and a defined secondary-market screening procedure.
- **Reserve attestation cadence agreed**. A registered public accounting firm engaged, a monthly
  examination schedule signed, and a defined CEO and CFO certification process.
- **Audit trail review**. SDP's audit-service entries reviewed for completeness. The mint memos
  from Section 6 reconcile to reserve references in the custody bank's records.
- **Incident response runbook**. The operational playbook for a freeze, seize, or force-burn order.
  It states what happens when a court order arrives, who signs in with which credential, how long
  the chain of custody runs, and where the documentation lands.

### The cutover

When the sign-off is in, the cutover itself is small.

1. Repeat the bootstrap from Section 2 with `environment: "production"`.
2. Mint your production keys.
3. Store the keys with your other live secrets.
4. Update your runtime environment.
5. Run the wallet verification call from Section 2 against the production API base, to confirm that
   the wallets are bound.

Your first production mint corresponds to a real fiat reserve event at your custody bank.

## 9. What to read next

You have a deployed regulated stablecoin, the compliance controls configured, and a production
transition checklist that your compliance officer can sign against. That is the issuance side of
the institutional product.

Two adjacent problems build on it, and SDP does not yet publish a tutorial for either one.

**Tokenizing a treasury fund.** A tokenized money market fund or treasury bond product uses the
`tokenized-security` template. Its compliance posture differs from the stablecoin pattern in three
ways: the allowlist is on by default, accounts open frozen, and the `scaledUiAmount` extension is
available for accrued yield. Most of the Section 5 controls work identically. The differences sit
in the design and deploy steps in Sections 3 and 4. See
[Token templates](/docs/reference/issuance-token-types) for the template defaults, and
[Tokenize an asset](/docs/tokens/tokenize-an-asset) for the decision between token models.

**Running enterprise stablecoin payments.** Institutional payment flows pick up after Section 7.
They cover bulk transfers, scheduled payments, onramp and offramp integration with custody bank
settlement, and the policy-engine patterns that gate transfers at scale. See
[Payments](/docs/payments) for the transfer endpoints and
[Wallet policies](/docs/wallet-operations/policies) for the policy engine.
