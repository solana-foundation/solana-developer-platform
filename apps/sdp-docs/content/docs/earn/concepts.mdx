Earn builds transactions, and your customer's wallet signs them.

## Key terms

| Term | Meaning |
| --- | --- |
| Strategy | A yield source: a lending market, a vault, or a yield-bearing token. Each takes one deposit token. |
| Position | One wallet's holding in one strategy, counted in shares. Withdrawals spend shares, not dollars. |
| Movement | SDP's record of one deposit or withdrawal, from submit to finality. |
| Withdrawal request | SDP's record of a withdrawal that pays out later. |
| External wallet | A wallet SDP holds no key for, such as your customer's. `ownerAddress` names it. |

## Who signs

1. Your backend asks SDP to **build** an unsigned transaction.
2. Your customer's wallet **signs** it, without changing or broadcasting it.
3. Your backend **submits** the signed transaction.
4. SDP verifies it, records a movement, broadcasts it, and tracks it.

The only signers are the customer's wallet and, when you name one, your
[fee payer](/docs/earn/integration-details#fees-and-sponsorship). SDP never
signs.

## Where funds go

SDP never holds your customer's keys or funds. Every step is onchain, so you
can check it:

| Step | What happens | How to check |
| --- | --- | --- |
| Deposit | The deposit token leaves the wallet for the strategy, and its shares (`shareMint`) arrive in the same wallet. | The movement's `signature`, in any explorer. |
| Hold | The shares sit in a token account the wallet owns. | The wallet's `shareMint` balance, from any RPC node. |
| Withdraw | The strategy takes the shares back and pays the deposit token to the same wallet. | The withdrawal's `signature`. |

A sandbox deposit of 10 USDC changed three balances and no others: the
wallet's USDC fell by 10, the vault's rose by 10, and the wallet received 10
shares.

- **The strategy holds the deposits,** pooled with its other depositors. Its
  custody, liquidity, and withdrawal risks apply.
- **A token strategy has no vault.** The deposit swaps into the yield-bearing
  token, and that token is the position.
- **A position's value is read live** from the strategy. SDP's movements
  record only what it submitted.

<Callout type="warn">
Never send tokens to a strategy's `providerReference`. It identifies the
instrument, not a deposit address. Deposit only through a transaction SDP
builds.
</Callout>

## One integration, many customers

One API key serves every customer. SDP records positions and movements for
each wallet, inside your project.

| Question | Answer |
| --- | --- |
| How do I add a customer? | Send their wallet as `ownerAddress` when you build. There is no registration call. |
| How are customers kept apart? | Each position, movement, and withdrawal request belongs to one wallet, and each read takes `ownerAddress`. |
| How do I report per customer? | Read [positions, movements, and earnings](/docs/earn/balances) per wallet, and the [position summary](/docs/earn/balances#position-totals) for totals. |
| Who links customers to wallets? | Your backend. The key can read every wallet in its project, so check that the signed-in customer owns the wallet. |
| Can I separate lines of business? | Use one project for each. A key cannot reach another project's positions. |

Keep the key on your backend.
[Rate limits](/docs/reference/conventions/rate-limits) apply per key, not per
wallet.

## What it costs

| Cost | Paid to | Who pays |
| --- | --- | --- |
| Network fee and account rent | The Solana network | The customer's wallet, or your [`feePayer`](/docs/earn/integration-details#fees-and-sponsorship). |
| Strategy fees | The strategy's provider | The provider sets and collects them. `riskMetadata` lists the rates it reports, such as `managementFeeBps` and `performanceFeeBps`. |
| SDP fee | Nobody | No transaction SDP builds contains an instruction that pays SDP. |

## What the wallet must support

Earn issues no token of its own: the position is the strategy's share or
yield-bearing token. Any wallet that signs a Solana transaction unchanged
works, whether browser, embedded, MPC, or custody.

| The wallet or its policy must | Why |
| --- | --- |
| Sign a transaction it did not build, unchanged | SDP refuses a changed transaction. |
| Leave broadcasting to SDP | SDP records the movement first, then broadcasts. |
| Allow the programs a build calls | The strategy's program, the Associated Token Account program, and the Memo program, which tags the build ID. Decode a build to list them: IDs can differ between devnet and mainnet. |
| Hold the strategy's token | An SPL Token or Token-2022 mint, which can carry a transfer hook or an issuer freeze authority. SDP simulates each build, so it already includes the accounts a hook needs. |
| Create accounts on a first deposit | The share account, and for some strategies a record for the wallet. See [rent](/docs/earn/integration-details#fees-and-sponsorship). |

## How a movement settles

| Status | Meaning |
| --- | --- |
| `requested` | SDP recorded the signed transaction and has not seen it onchain yet. |
| `submitted` | SDP broadcast the transaction. |
| `confirmed` | The network confirmed it. Final for display only when settlement is `atomic`. |
| `finalized` | The transaction is final. |
| `failed` | It did not land. `failureReason` says why. |

A movement's `settlement` decides when funds have really moved:

- **`atomic`**: one transaction does it all. You may show it as done at
  `confirmed` while SDP tracks it to `finalized`.
- **`provider_order`**: the transaction places an order that the provider
  completes later. The movement stays `confirmed` until then, and only
  `finalized` means it is done.

A solver queue or operator redemption also pays out later. Track it as a
[withdrawal request](/docs/earn/withdrawals#track-a-request), and credit funds
only when the payout arrives.

## Sandbox and production

Your API key's project decides the network: sandbox runs on devnet with test
tokens, production on mainnet with real funds. Strategy IDs differ between
them. See [Go to mainnet](/docs/guides/go-to-mainnet).
