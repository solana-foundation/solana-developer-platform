module: earn
title: Deposit funds
description: Prepare and review strategy deposits, then follow signing and settlement.
---

Send `POST /v1/earn/deposit` with `strategyId`, a source and token amount.
With your SDP API key, use `source: { "ownerAddress": "<owner-public-key>" }` for
any compatible Solana wallet. No SDP wallet registration or provider connection
is required. Amounts use a mint and decimal-string `value` in that token's units.

## Review before submission

Preparation returns `202` with a durable operation, economic terms and its next
action. It quotes, plans and simulates without starting wallet signing or
broadcasting. Show the estimate, enforceable minimum and fees.
Unknown fees are not zero fees.

For `sign_transaction`, use your wallet integration to sign the exact advertised
transaction. Its owner must match the prepared `ownerAddress`; any required fee
payer must co-sign. Keep the message unchanged and encode the signed transaction
as base64.
Call `POST /v1/operations/{operationId}/submit` with the current action ID and
version and `signedTransaction`. Submission authorizes and queues
that exact transaction; it does not prepare another action.

If you already have a wallet connected in SDP, `source: { "walletId": "..." }`
is an optional alternative. For its `submit` action, send the action ID/version
without signed bytes. The worker requests signing through the configured wallet
provider; there is no separate API flow.

Funding with another supported token combines the swap and deposit into one
transaction. If they cannot fit together after a compact-route retry, preparation
refuses before signing. Fund the strategy's deposit token and retry; SDP never
returns a standalone funding swap.

The worker coordinates signing and broadcast. Poll
`GET /v1/operations/{operationId}` and display its next action. For
`sign_in_provider`, show the signing instructions and handoff URL when present.
A queued or submitted operation has not yet established delivery.

After submit acceptance, refresh and cancellation are unavailable. Track the
operation until its outcome is known. A definitive failure requires a new
deposit request and idempotency key; an uncertain outcome does not permit one.

Persist an `Idempotency-Key` before each mutation. Recover uncertain responses
by reading the operation and retrying the same body with its original key.
