## Next actions

Every operation says what to do next in `nextAction`:

| `nextAction.type` | What to do |
| --- | --- |
| `sign_transaction` | Have the owner, and any `feePayer`, sign `transaction` unchanged. Call `/submit` with `signedTransaction` and the current `actionId` and `version`. |
| `select_option` | Choose an `id` from `terms.options` and call `/refresh` with it as `optionId`. Review the new transaction. |
| `wait` | Keep polling. `reason` says what SDP is waiting for. |
| `null` | Nothing left to do: the operation is final. |

These calls live under `/v1/operations/{operationId}`. Only `/submit` lets SDP
send anything; there is no separate approval step. `actionId` and `version`
name the exact transaction you were shown: each refresh issues a new pair, and
submitting an old pair returns `409`.

Signing or broadcasting outside SDP does not update the operation. Send the
exact signed bytes to `/submit` for operation tracking, even if you already
broadcast them yourself.

## Refresh and cancel

Both work only while an operation waits for a route choice (`select_option`),
before SDP hands you a transaction to sign:

- **Refresh** picks a withdrawal route and prepares its transaction. It never
  signs, sends or cancels anything, and the chosen route stays fixed.
- **Cancel** abandons the operation while `canCancel` is `true`, and needs the
  `earn.manage` grant. Read `canCancel`; don't infer it from `status` or time.

After SDP accepts a `/submit`, both return `409 CONFLICT` with `details.reason`
`operation_already_submitted`, even if the operation later fails. Track it to
the end instead.

SDP can't take back a transaction it handed you to sign, because you could still
sign and broadcast it yourself. Once an operation shows `sign_transaction`,
refresh and cancel return `409` with `details.reason`
`wallet_transaction_outcome_unknown`. If the customer declines to sign, close
the prompt: nothing executes and no SDP call is needed. SDP can't revoke a
signature or pull a broadcast transaction from Solana.

## Recover expired withdrawal escrow

A queued withdrawal that isn't filled before its deadline can leave its shares
in the provider's escrow. To get them back, prepare `POST /v1/earn/withdraw` for the
same tracked `positionId` with `amount: { "kind": "all" }`. When the provider
proves the recorded request still holds those expired shares, `terms.options`
offers **Recover expired escrowed shares** through `select_option`.

Select it with `/refresh`, review the new transaction, then sign and submit as
usual. Recovery returns the shares to the same owner, not the deposit token.
After SDP verifies the transaction and the provider's outcome, the result has
`settlementOutcome: "recovered"` with the returned share mint and amount.

Each review checks up to three recorded requests in creation order and offers
the first escrow that is still recoverable. Closed or no-longer-expired requests
are skipped. If all three are stale and more remain, the recovery option is
omitted while other available withdrawal routes remain usable. Preparation
returns `503 SERVICE_UNAVAILABLE` only if no route remains.

Recover one request per review, then prepare another withdrawal for the next.
The original operation is not reopened, and its `/cancel` stays unavailable.
Expiry alone, or a missing provider request, does not authorize recovery.

## Release a pending Hastra redemption

For a tracked Hastra position with a recorded pending operator redemption,
prepare the same `POST /v1/earn/withdraw` with `amount: { "kind": "all" }`.
SDP checks the current provider request and offers
**Release current pending redemption**
(`release_current_redemption`), even with no free PRIME or wYLDS balance.
Explicitly select it with `/refresh`, review the transaction, then sign and
submit as usual.

This closes whichever Hastra request is current **when the transaction
executes**, including a replacement created after review. It revokes Hastra's
burn delegation if still present and preserves unrelated delegates. Hastra's
instruction cannot target a historical request cycle or guarantee an unlocked
amount. Review that scope before signing.

Release does not mint PRIME or deliver USDC. After SDP verifies its cancellation
transaction, the result is `settlementOutcome: "recovered"` with
`settledAmount: null`. Read the position's `parIntermediate` for its current
wYLDS balance. Issuer freezes can still block release.

The historical redemption's financial record stays unchanged. Its operation
ends `failed` with `REDEMPTION_SUPERSEDED`, no settled amount and no settlement
outcome. That ends tracking without proving nonexecution or establishing a
historical payout. Do not automatically retry the original withdrawal. The new
release operation completes; it does not reopen the original or enable its
`/cancel`. An uncertain broadcast is not permission to build another release.

A release that never lands ends `failed` with `TRANSACTION_EXPIRED`. SDP
decides that only after the transaction's blockhash has expired and finalized
history misses it twice, at least 30 seconds apart, the second time on every
RPC endpoint SDP uses, with at least two distinct endpoints answering. A
single-endpoint pool keeps an uncertain outcome pending. Proven nonexecution
frees the redemption address, so you can prepare a new release.

## Retries and idempotency

Save a fresh `Idempotency-Key` with each request body before you send it. After
an uncertain response, such as a timeout or a `5xx`, resend the exact same body,
signed bytes included, with the same key: SDP returns the original response.
Don't rebuild a retry from a newer quote or balance.

To pick up work you already started, list `GET /v1/operations?ownerAddress=...`
and continue from its `nextAction` instead of preparing another deposit or
withdrawal.

Track several known operations in one request with
`GET /v1/operations?ownerAddress=...&operationIds=op_a,op_b&limit=100`.
`operationIds` accepts up to 100 comma-separated IDs. The same wallet visibility
and other filters apply; missing or inaccessible IDs are omitted. Keep the
owner filter for owner-address operations. Refresh recent user actions quickly,
then back off while a provider is settling. A status read never executes work.

Replaying a refresh with its original key returns the original response, even
after a later submit; it builds nothing new. Read
`GET /v1/operations/{operationId}` for the current state.

Once you submit, start over with a new key only after the operation is
`failed` with a definitive rejection or proven nonexecution. A
`REDEMPTION_SUPERSEDED` result ends tracking without that proof and must not
trigger an automatic retry.

A timeout, an expired blockhash, an unknown provider response or missing RPC
history doesn't prove a submitted transaction never ran: keep
tracking until SDP knows. A transaction you never submitted or sent can't land
once the network passes its `lastValidBlockHeight`, so you can prepare again.

When SDP stops before sending signed bytes, for example because the key lost
`earn.execute`, it keeps watching for them. Once their blockhash has expired
and every configured RPC endpoint misses the signature at a finalized read
floor, with at least two distinct endpoints answering, the operation ends
`failed` with `TRANSACTION_EXPIRED`. One endpoint alone leaves it pending.

If the vault exposure cap refuses a deposit before broadcast, SDP stops trying
to send it and reports `DEPOSIT_REFUSED` while watching the exposed bytes. The
refusal becomes final only when SDP proves they never executed. A deposit
observed on chain is still recorded even when current caps or an unreadable
exposure figure prevent new deposits.

## Fees and rates

| Cost | What you can know |
| --- | --- |
| Network fees and rent | The owner pays them, unless you set a separate `feePayer`, which must also sign. A full Kamino withdrawal leaves the empty share account open, so don't promise its rent back. |
| Provider costs | Management, performance, swap and redemption charges depend on the strategy and route. Show the provider's metadata and the reviewed estimate; a queue discount also lowers proceeds. |
| SDP pricing | Not part of the Earn response. Confirm SDP pricing separately, and don't read a missing field as zero. |

`terms.fees` lists known fees for the transaction: `null` means unavailable, not
free, and it is not an invoice for ongoing provider costs. `rate.value` is the
provider-reported APY, not a promise of returns after every cost, and Earn
doesn't normalize rates across providers into one comparable net yield.

## Permissioned tokens and transfer hooks

Earn supports specific provider instruments and their token programs.
WisdomTree fund tokens, for example, use Token-2022 with an issuer compliance
hook: Earn pins that program and supplies the hook's accounts in the
transaction. The signing wallet must allow every program and instruction in the
reviewed transaction.

This is not generic support for any transfer hook, gated mint or Token ACL
policy, and a listing doesn't prove an arbitrary token can be deposited or
moved. Issuer freezes, delegates and transfer restrictions can still affect
holdings and exits.

SDP's [tokenization tools](/docs/tokens/tokenize-an-asset) are a separate
module, with their own availability. Using Earn doesn't issue a token,
configure its access list or enroll an issuer policy.

## Provider eligibility

An SDP API key grants API access, not investment eligibility. For each customer
and wallet, confirm the issuer's rules on jurisdiction, investor qualification
or accreditation, KYC/AML, subscriptions and redemptions. They differ by
product, and Earn has no universal compliance approval or jurisdiction screen.

Where a provider supports an eligibility check, Earn runs it before building the
deposit. WisdomTree requires a customer mapping in the same project, an approved
wallet and access to the selected fund. Its onboarding (KYC/KYB, documents and
wallet registration) is a separate issuer workflow. Only an active business
customer can register a wallet; a retail application alone doesn't make a
wallet eligible.

For other providers, screen customers in your integration and confirm the
issuer's terms before you offer a strategy. Withdrawals get no new eligibility
gate, but issuer hooks, freezes, liquidity and redemption decisions can still
delay or block delivery.
