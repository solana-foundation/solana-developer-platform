title: Ramp providers
description: The seven ramp providers SDP integrates, what each one can do, how each is configured, and how to find out which ones your organization can use today.
---

SDP integrates seven ramp providers: MoonPay, Lightspark, BVNK, MoneyGram, Coinbase, Mural, and Stripe. Each is configured with its own credentials on the SDP API deployment, and each is gated per organization. The same `provider` string selects between them on every ramp endpoint.

<Callout type="warn">
Don't build against a provider table, including the one on this page. Which providers you can use depends on the corridor, on your organization's entitlements, and on the provider's own availability at the moment of the call. Ask the API: `GET /v1/payments/ramps/{onramp,offramp}/currency` returns a `providers` list per corridor and a `providerDetails` block per provider, and `POST .../estimate` returns a per-provider result where entries succeed or fail independently. See [Ramps](/docs/payments/ramps).
</Callout>

## What each provider does

Directions and counterparty types come from the API's support matrix; delivery modes come from how each provider's quote is built. Use this to decide where to start, then confirm with `currency`.

| Provider | On-ramp | Off-ramp | `deliveryMode` | Counterparty types | Sandbox `simulate` |
| --- | --- | --- | --- | --- | --- |
| MoonPay | yes | yes | `hosted` | individual | no |
| Lightspark | yes | yes | `manual_instructions` | individual, business | yes |
| BVNK | yes | yes | `manual_instructions` or `hosted` | individual (on-ramp); individual, business (off-ramp) | yes |
| MoneyGram | yes | yes | `session_widget` | individual | no |
| Coinbase | yes | no | `hosted` | individual | no |
| Mural | yes | no | `manual_instructions` | business | yes |
| Stripe | yes | no | `session_widget` | individual | no |

Corridors are narrower than directions. On `USD` to `usdc.solana`, six providers answer and MoonPay is not one of them; MoonPay's on-ramp corridors go to `sol.solana` and `pyusd.solana`. On `usdc.solana` to `USD`, three do: Lightspark, BVNK, and MoneyGram. Read `pairs` for the corridor you need rather than the direction columns above.

An off-ramp quote for Coinbase or Stripe returns `400` (`Coinbase Onramp does not support off-ramp.`, `Stripe off-ramp is not supported.`). Mural's off-ramp quote is not built yet and currently returns `500` with `Mural off-ramp quote is not implemented yet.`, though its off-ramp `estimate` works.

## Sandbox and production credentials

Every provider that supports both modes takes two credential sets, and the mode is chosen per request rather than at deploy time. The environment of the calling API key decides (sandbox keys start with `sk_test_`, production keys with `sk_live_`); dashboard and session callers get their project's environment. A request that resolves to a mode the provider has no credentials for returns `503` with `<provider> is not configured for <mode> mode.`

Configure both credential pairs for any provider you want to expose to test and live traffic on the same deployment. Coinbase and Stripe carry a single credential set; use their test-mode keys for sandbox. MoneyGram has sandbox credentials only.

## MoonPay

| Variable | Required | Notes |
| --- | --- | --- |
| `MOONPAY_API_KEY` | conditional | Production API key. |
| `MOONPAY_SECRET_KEY` | conditional | Production secret, used to sign on-ramp and off-ramp URLs. |
| `MOONPAY_SANDBOX_API_KEY` | conditional | Sandbox API key. |
| `MOONPAY_SANDBOX_SECRET_KEY` | conditional | Sandbox secret. |
| `MOONPAY_ONRAMP_URL` | no | Override the on-ramp host. |
| `MOONPAY_OFFRAMP_URL` | no | Override the off-ramp host. |
| `MOONPAY_WEBHOOK_KEY` | no | Verifies production webhook signatures. |
| `MOONPAY_SANDBOX_WEBHOOK_KEY` | no | Verifies sandbox webhook signatures. |

MoonPay maps token symbols internally (`USDC` to `usdc_sol`, `USDT` to `usdt_sol`), so you pass plain symbols on the request. The corridor matrix is discovered with the sandbox key and keeps only the assets MoonPay's sandbox flags as test-mode capable, which is why MoonPay appears on `sol.solana` and `pyusd.solana` corridors but not on `usdc.solana`. A production key inherits the same matrix.

Counterparties need no provider-side setup: requirements report `ready` in both directions. Quotes return `deliveryMode: "hosted"` with a signed `hostedUrl`; MoonPay geo-blocks the hosted page by the end user's location before any KYC step, so test it from a supported country. Settlement arrives through MoonPay's webhook, and on off-ramps that webhook supplies the deposit wallet the user has to fund.

## Lightspark

| Variable | Required | Notes |
| --- | --- | --- |
| `LIGHTSPARK_GRID_CLIENT_ID` | conditional | Production Grid API client identifier. |
| `LIGHTSPARK_GRID_CLIENT_SECRET` | conditional | Production Grid API client secret. |
| `LIGHTSPARK_GRID_SANDBOX_CLIENT_ID` | conditional | Sandbox Grid API client identifier. |
| `LIGHTSPARK_GRID_SANDBOX_CLIENT_SECRET` | conditional | Sandbox Grid API client secret. |
| `LIGHTSPARK_GRID_API_BASE_URL` | no | Override the Grid API host. |
| `LIGHTSPARK_GRID_WEBHOOK_PUBLIC_KEY` | no | Verifies production webhook signatures. |
| `LIGHTSPARK_GRID_SANDBOX_WEBHOOK_PUBLIC_KEY` | no | Verifies sandbox webhook signatures. |

Lightspark is integrated against the Grid API. A new counterparty first answers `collect_counterparty` in both directions: identity fields (name, date of birth, nationality, email, residential address, purpose of payment) that create the Grid customer. After that an on-ramp is `ready`. An off-ramp goes on to `collect_account`, where the fields depend on the destination country and rail rather than on the counterparty: a USD payout to the US asks for a rail (ACH, Wire, RTP, or FedNow) plus a routing number and an account number. The resulting payout account is reused on later requests for the same country and currency, and an off-ramp quote names it with `providerAccountId`. A quote for a counterparty that hasn't been provisioned returns `409`.

Quotes return `deliveryMode: "manual_instructions"` and carry `expiresAt`, about three minutes out. On-ramp instructions are bank funding details (`accountType: "USD_ACCOUNT"` with a `reference` the transfer must carry); off-ramp instructions are a `crypto_deposit` to a Solana address. Lightspark's sandbox caps stablecoin on-ramp requests at 10 USD per request and returns its own error above that.

## BVNK

| Variable | Required | Notes |
| --- | --- | --- |
| `BVNK_WALLET_ID` | conditional | Production BVNK-side wallet used for settlement. |
| `BVNK_HAWK_AUTH_ID` | conditional | Production Hawk auth id. |
| `BVNK_HAWK_SECRET_KEY` | conditional | Production Hawk secret key. |
| `BVNK_SANDBOX_WALLET_ID` | conditional | Sandbox BVNK wallet. |
| `BVNK_SANDBOX_HAWK_AUTH_ID` | conditional | Sandbox Hawk auth id. |
| `BVNK_SANDBOX_HAWK_SECRET_KEY` | conditional | Sandbox Hawk secret key. |
| `BVNK_API_BASE_URL` | no | Override the BVNK host. |
| `BVNK_SIGNING_HOST` | no | Host used when computing the Hawk signature. |
| `BVNK_WEBHOOK_SECRET` | no | Verifies production webhook signatures. |
| `BVNK_SANDBOX_WEBHOOK_SECRET` | no | Verifies sandbox webhook signatures. |

BVNK uses Hawk authentication. Bearer-token auth is not supported. `BVNK_WALLET_ID` configures BVNK's settlement wallet on the provider side and is unrelated to the `sourceWallet` and `destinationWallet` fields on a quote request.

BVNK is a travel-rule provider and needs party details (name, address) to create a customer. Requirements collect them: a new counterparty answers `collect_counterparty` with the identity fields, and submitting them creates the BVNK customer. From there requirements can report `customer_agreement_required` with agreements to show and accept (`agreementConsent: true` on the resubmit), `customer_verification_required` with a `verificationUrl` to send the customer to, and the `customer_verifying` and `customer_funding_account_provisioning` waits. Off-ramp requirements then ask for a bank account and routing number through `collect`. The off-ramp quote itself is the remaining gap: it rebuilds BVNK's party details from identity fields SDP no longer stores, so today it returns `400` with `BVNK offramp requires identity fields ... that are no longer stored; JIT collection is not wired yet` for every counterparty, including ones BVNK already knows.

BVNK can return either `deliveryMode: "manual_instructions"` (on on-ramp, a fiat virtual account for the customer to fund) or `deliveryMode: "hosted"`. Branch on the response.

## MoneyGram

| Variable | Required | Notes |
| --- | --- | --- |
| `MONEYGRAM_SANDBOX_PUBLIC_KEY` | conditional | Sandbox public key. |
| `MONEYGRAM_SANDBOX_SECRET_KEY` | conditional | Sandbox secret key. |

MoneyGram is sandbox-only in the SDP configuration surface today. No production credential pair exists, so a production request for MoneyGram returns `503` as not configured.

Counterparties need no provider-side setup. Quotes return `deliveryMode: "session_widget"` with a `sessionToken`, a `sessionId`, a `widgetUrl`, and an `expiresAt` one hour out. The widget URL has to sit on MoneyGram's approved host or the quote fails closed, and a widget event that arrives after the session token has expired is rejected.

MoneyGram does not send SDP a provider webhook, which is why no webhook secret appears above. The widget reports progress through the authenticated `POST /v1/payments/ramps/moneygram/events` route instead, and SDP treats those events as advisory: a MoneyGram transfer rests at `settling` until the cash side is confirmed.

## Coinbase

| Variable | Required | Notes |
| --- | --- | --- |
| `COINBASE_CDP_API_KEY_ID` | conditional | CDP API key identifier. |
| `COINBASE_CDP_API_KEY_SECRET` | conditional | CDP API key secret. |
| `COINBASE_CDP_WALLET_ID` | conditional | CDP wallet used for settlement. |
| `COINBASE_CDP_WALLET_SECRET` | conditional | Secret for that wallet. |
| `COINBASE_CDP_API_BASE_URL` | no | Override the CDP host. |
| `COINBASE_CDP_NETWORK` | no | Target network. |
| `COINBASE_CDP_ACCOUNT_NAMESPACE` | no | Namespace for provisioned accounts. |
| `COINBASE_CDP_RAMPS_WEBHOOK_SECRET` | no | Verifies webhook signatures. |

Coinbase is on-ramp only, for individual counterparties. Quotes accept an optional `domain` field, the browser origin host used to embed its Apple Pay payment link, and return `deliveryMode: "hosted"` with the order economics (`paymentSubtotal`, `paymentTotal`, `purchaseAmount`, `fees`) beside the URL.

Requirements report `ready` for a new counterparty, but the quote itself needs an email and phone number that SDP no longer stores, so a first-time quote returns `400` with `Coinbase onramp requires identity fields that are no longer stored; JIT collection is not wired yet`. Coinbase reports settlement through an inbound provider webhook and also accepts the authenticated `POST /v1/payments/ramps/coinbase/events` route.

## Mural

| Variable | Required | Notes |
| --- | --- | --- |
| `MURAL_PAY_API_KEY` | conditional | Production API key. |
| `MURAL_PAY_TRANSFER_API_KEY` | conditional | Production transfer API key, used for payout operations. |
| `MURAL_PAY_SANDBOX_API_KEY` | conditional | Sandbox API key. |
| `MURAL_PAY_SANDBOX_TRANSFER_API_KEY` | conditional | Sandbox transfer API key. |
| `MURAL_PAY_WEBHOOK_PUBLIC_KEY` | no | Verifies production webhook signatures. |
| `MURAL_PAY_SANDBOX_WEBHOOK_PUBLIC_KEY` | no | Verifies sandbox webhook signatures. |

Mural requires two keys per environment: a general API key and a separate transfer key. It serves business counterparties only, on-ramp only.

A Mural quote needs the counterparty's Mural organization and pay-in account provisioned first. Requirements walk through that: `onboarding_not_started`, then `terms_of_service_required` with a `termsOfServiceUrl`, then `customer_verification_required` with a `verificationUrl`, then `customer_verifying` and `funding_account_provisioning` until `ready`. First-time organization creation for a new counterparty currently fails at the same just-in-time identity seam as Coinbase: the requirements call returns `400` with `Mural organization creation requires identity fields that are no longer stored; JIT collection is not wired yet`, so a counterparty that has no Mural organization cannot leave `onboarding_not_started` today. Quotes return `deliveryMode: "manual_instructions"` built from the account's active pay-in method. Sandbox `simulate` accepts `USD`, `MXN`, `BRL`, and `ARS`.

## Stripe

| Variable | Required | Notes |
| --- | --- | --- |
| `STRIPE_SECRET_KEY` | conditional | Secret key. One key serves both modes; use a Stripe test-mode key for sandbox. |
| `STRIPE_PUBLISHABLE_KEY` | conditional | Publishable key, returned to the client on the quote for widget initialization. |
| `STRIPE_WEBHOOK_SECRET` | no | Verifies webhook signatures. |

Stripe is on-ramp only, for individual counterparties, and needs no provider-side counterparty setup. Quotes return `deliveryMode: "session_widget"` with a `clientSecret`, a `sessionId`, and the `publishableKey` to mount Stripe's crypto on-ramp session. Stripe's redirect destinations are validated against an approved host list on the way back; a redirect to anything else fails closed.

## Provider gating

Populating a provider's credentials is not sufficient on its own. Every ramp call checks the organization's entitlements, and a request for a provider the organization is not entitled to returns `403`. On `estimate`, where SDP fans out to every provider on the corridor, that provider comes back as `status: "error"` inside the 200 instead. To change entitlements for a deployment, see [Provider onboarding](/docs/reference/provider-onboarding).

Self-hosted deployments do not need every provider. Configure the ones you have credentials for and leave the rest unset. An unset provider still appears in `pairs`, because the corridor matrix is static, but any request that names it returns `503` and its `estimate` entry reads `status: "error"`.
