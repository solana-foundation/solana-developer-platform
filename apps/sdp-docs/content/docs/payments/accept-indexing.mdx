title: Indexing and reconciliation
description: List inbound transfers, paginate them, deduplicate them, and reconcile them against your ledger.
---

`GET /v1/payments/transfers` is the main endpoint for reconciliation. By default it returns
paginated, persisted transfer records across your organization's custody wallets.

It filters on direction, status, token, exact `custodyWalletId`, and date range. Use it to mirror
SDP transfers locally, to match an inbound payment to an order, and to drive a delta-polling
worker.

To include recent onchain observations for one exact wallet, set `custodyWalletId` and
`includeObserved=true`.

## Listing inbound transfers

This is the smallest inbound-only request.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
curl "https://api.solana.com/v1/payments/transfers?direction=inbound&pageSize=50" \
  -H "Authorization: Bearer sk_test_..."
```
</Tab>
<Tab value="TypeScript">
```typescript title="list-inbound-transfers.ts"
const url = new URL("https://api.solana.com/v1/payments/transfers");
url.searchParams.set("direction", "inbound");
url.searchParams.set("pageSize", "50");

const res = await fetch(url, {
  headers: { Authorization: "Bearer sk_test_..." },
});
const { data, meta } = await res.json();
// data: Transfer[]
// meta: { total, page, pageSize, hasMore, requestId }
```
</Tab>
</Tabs>

### Query parameters

| Parameter | Type | Notes |
| --- | --- | --- |
| `direction` | `inbound` \| `outbound` | The common filter. `inbound` means payments to wallets you control. |
| `status` | `pending` \| `processing` \| `confirmed` \| `finalized` \| `failed` | Scope the list to a single state. |
| `custodyWalletId` | string | An exact SDP wallet ID. `GET /v1/wallets` returns it as `id`. |
| `includeObserved` | boolean | Default `false`. When `true`, SDP adds recent onchain activity for the exact `custodyWalletId`. You cannot use it without that filter. A synthetic observed row has `custodyWalletId: null`. |
| `token` | string | Filter by token symbol or by onchain mint address. SDP matches it exactly against the stored `token` value on the transfer. |
| `from`, `to` | ISO 8601 datetime | A time-window filter on `createdAt`. Pass an ISO 8601 timestamp, such as `2026-05-14T00:00:00Z`. The trailing `Z` means UTC. |
| `page` | integer | Default `1`. |
| `pageSize` | integer | Default `20`, maximum `100`. |

## Deduplication

A transfer has two natural keys for this.

1. **`Transfer.id`** is SDP-internal and immutable. It is present on every transfer, including a
   `pending` one that has no signature yet. Use it as your local primary key.
2. **`Transfer.signature`** is the onchain signature. SDP sets it once it has built the transaction
   and observed it onchain. That is usually at `confirmed` or `finalized`, but treat the presence
   of the value as the trigger rather than the status. A `processing` record, and even a `pending`
   record, can still have a null signature. The column is `UNIQUE` across the SDP transfers table
   wherever it is set, so two records cannot share a signature. Use it when you need to
   deduplicate across several data sources, such as SDP plus a parallel chain indexer, and only
   once `signature` is present.

In practice: store transfers in your reconciliation table keyed by the SDP `Transfer.id`, and
assert that `signature` is unique once it is populated.

## Reconciling an order

SDP does not populate `Transfer.memo` for a customer-initiated inbound transfer, because SDP does
not extract memo-program instructions into that field. The inbound record also carries no reference
field.

The reliable correlation key on the record is therefore the inbound transfer's `destination`. Match
it against an order whose pre-issued receiving address is that same `destination`.

The typical inbound match cycle runs like this.

1. **Read** recent persisted inbound transfers for the token you care about:
   ```text title="Request"
   GET /v1/payments/transfers
     ?direction=inbound
     &token=<mint or SOL>
     &from=<since last reconciled>
     &to=<now>
     &pageSize=100
   ```
2. **For each transfer**, look up an open order keyed by the transfer's `destination`, with
   `findOrderByDestination(tr.destination)`.
3. **If it matches**, check that the amount and the token match the values on the order row. Then
   mark the order paid, record the SDP `Transfer.id`, and dispatch the downstream side effects,
   such as an email, a shipment, or a ledger entry.
4. **If it does not match**, leave the transfer for the next pass. It can be an early arrival for
   an order you have not staged yet. Flag it for manual review after a grace window.

If you need correlation by memo or by Solana Pay `reference`, for example in a single-wallet flow
where many orders share one destination address, read the onchain transaction through Solana RPC
using the transfer's `signature`.

## Solana Pay reference accounts (roadmap)

SDP does not attach a Solana Pay reference pubkey onchain, and an inbound transfer record does not
expose a reference field today. That leaves two realistic correlation options.

- **Per-order destination addresses.** Pre-issue a fresh receiving wallet for each order and match
  on `Transfer.destination`. This is the recommended pattern. See
  [Reconciling an order](#reconciling-an-order) above.
- **Onchain reads through Solana RPC**, keyed off the transfer's `signature`. Use these to recover
  the memo-program instruction or the Solana Pay `reference` that the transfer record does not
  carry.

## A delta-poll worker

This reconciliation worker wakes on a tick and asks what is new since the last tick.

<Tabs items={["TypeScript"]}>
<Tab value="TypeScript">
```typescript title="reconcile-tick.ts"
const OVERLAP_MS = 5_000; // re-query the last 5s on each tick to catch boundary arrivals

async function reconcileTick(state: WorkerState) {
  // Nudge `from` backwards by the overlap window; `alreadySeen` dedupes the
  // resulting duplicates. Always advance the high-water mark to `to` regardless,
  // otherwise the window grows without bound.
  const fromMs = state.lastSeenIso
    ? Date.parse(state.lastSeenIso) - OVERLAP_MS
    : Date.now() - 60_000;
  const from = new Date(fromMs).toISOString();
  const to = new Date().toISOString();

  // This lists persisted records. To discover additional recent chain activity,
  // run the same window per exact wallet with custodyWalletId + includeObserved.
  for await (const tr of listInbound({ from, to })) {
    if (await alreadySeen(tr.id)) continue;

    // Match by destination — the on-record correlation key for inbound transfers.
    // `tr.memo` is omitted (undefined) for customer-initiated inbound payments.
    const order = await findOrderByDestination(tr.destination);
    if (!order) {
      await persistUnmatched(tr);
      continue;
    }

    if (tr.status === "finalized") {
      await markOrderPaid(order, tr);
    }
    await persistSeen(tr.id, tr.status);
  }

  state.lastSeenIso = to;
}
```
</Tab>
</Tabs>

Notes:

- The overlap window, 5 seconds above, re-queries the trailing edge of the last tick. It catches a
  transfer that arrives at the boundary, and `alreadySeen` collapses the duplicates that result.
- The high-water mark advances to `to` on every pass, even though `from` rolls back. Otherwise the
  query window grows without bound.
- Always re-fetch a transfer to upgrade its status. A transfer seen as `confirmed` on one tick
  appears as `finalized` on a later tick.
- Use `pageSize=100` and the async iterator pattern to handle a large window. See
  [Payouts and disbursements](/docs/payments/send-payouts).
