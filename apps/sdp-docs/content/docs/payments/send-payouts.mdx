A payout run is a batch of outbound transfers. Marketplace seller payouts, payroll, affiliate
disbursements, and royalty distributions are all payout runs.

Use `POST /v1/payments/transfer-batches` when every recipient is a registered counterparty
account. For arbitrary Solana addresses, call `POST /v1/payments/transfers` once per recipient, and
reconcile the transfer IDs that it returns.

## Native transfer batches

One request creates a durable batch. SDP splits the recipients into Solana transactions, and
returns the batch record, the recipient records, and the transfer records.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfer-batches \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: payroll-2026-05-14" \
  -d '{
    "externalId": "payroll_2026-05-14",
    "sourceCustodyWalletId": "cwlt_123",
    "token": "9aBCd...4eEf",
    "recipients": [
      {
        "externalId": "row_4837",
        "counterpartyId": "cp_4837",
        "counterpartyAccountId": "cpa_4837",
        "amount": "150.00"
      }
    ]
  }'
```

Reuse the same `Idempotency-Key` when you retry that exact request. Call
`GET /v1/payments/transfer-batches/{batchId}` to inspect the recipient outcomes and the chunk
outcomes. `externalId` is a correlation field. It is not an idempotency key.

The rest of this page covers the per-recipient alternative, for destinations that are not
registered counterparty accounts.

## Designing a payout run

A typical run works like this.

1. **Resolve the recipients** in your application. List or stream the rows to be paid. Each row
   carries a destination address and an amount.
2. **Pick a batch identifier** that you control, such as
   `payout_2026-05-14_marketplace_sellers`.
3. **Iterate.** For each recipient, call `POST /v1/payments/transfers` with the destination, the
   amount, the token, and a memo. Encode the batch ID and a per-row identifier in the memo, as in
   `payout_2026-05-14_marketplace_sellers/row_4837`.
4. **Capture** the returned `Transfer.id` and `Transfer.status`. Persist the SDP transfer ID next
   to the recipient row, so that you can poll the status again later.
5. **Reconcile.** Once you have submitted the whole batch, call
   `GET /v1/payments/transfers?direction=outbound&from=…&to=…`. Confirm that every row in your
   application has a matching `finalized` transfer.

Send the transfers one at a time, or with modest concurrency of 4 to 8 in flight. High concurrency
raises the chance of priority-fee contention and blockhash expiry, and it adds little throughput.

## Dedup and retries

Two layers protect you against a double spend if a worker dies part-way through a run.

1. **Idempotency keys.** Generate one stable `Idempotency-Key` for each recipient row, and reuse
   it for retries. An identical request for the same exact source wallet returns the original
   transfer. If you reuse the key for a different request, the API returns `409`.
2. **Application mapping.** Persist the SDP transfer ID for each recipient row before you move to
   the next row. On restart, replay the row with the same idempotency key, or skip any row that
   already has a `Transfer.id`.

The onchain `signature` is unique across SDP transfers once SDP sets it. Use it as a
cross-indexer integrity check, not as the retry mechanism.

A fresh idempotency key creates a new transfer intent, even when the payload is otherwise
identical.

```typescript title="payout-recipient.ts"
async function payoutRecipient(row: PayoutRow): Promise<string> {
  if (row.transferId) return row.transferId; // already submitted

  const response = await fetch(
    "https://api.solana.com/v1/payments/transfers",
    {
      method: "POST",
      headers: {
        "Authorization": "Bearer sk_test_...",
        "Content-Type": "application/json",
        "Idempotency-Key": row.idempotencyKey,
      },
      body: JSON.stringify({
        sourceCustodyWalletId: row.sourceCustodyWalletId,
        destination: row.destination,
        token: row.token,
        amount: row.amount,
        memo: `${row.batchId}/row_${row.id}`,
      }),
    }
  );

  const { data } = await response.json();
  // The transfer record is under data.transfer (standard SDP success envelope).
  await row.persistTransferId(data.transfer.id); // persist BEFORE returning
  return data.transfer.id;
}
```

## Reconciling a run

After the loop finishes, list every outbound transfer in the time window of the run. Then tally
the list against your recipient table.

<Tab value="curl">
```bash title="Terminal"
curl "https://api.solana.com/v1/payments/transfers?direction=outbound&from=2026-05-14T00:00:00Z&to=2026-05-14T23:59:59Z&pageSize=100" \
  -H "Authorization: Bearer sk_test_..."
```
</Tab>
<Tab value="TypeScript">
```typescript title="list-outbound-transfers.ts"
async function* listOutboundTransfers(from: string, to: string) {
  let page = 1;
  while (true) {
    const url = new URL("https://api.solana.com/v1/payments/transfers");
    url.searchParams.set("direction", "outbound");
    url.searchParams.set("from", from);
    url.searchParams.set("to", to);
    url.searchParams.set("page", String(page));
    url.searchParams.set("pageSize", "100");

    const res = await fetch(url, {
      headers: { Authorization: "Bearer sk_test_..." },
    });
    const { data, meta } = await res.json();
    yield* data;
    if (!meta.hasMore) return;
    page += 1;
  }
}
```

Scope the result to the batch by filtering on `memo.startsWith(batchId)`, or on whatever
convention you chose. Then cross-reference each recipient row by its SDP `Transfer.id`.

## Failure modes

Expect to handle these per-transfer outcomes.

- **`failed`.** SDP built and submitted the transaction, and the network rejected it. Common
  causes are insufficient funds, a frozen account, and an expired blockhash. The `error` field on
  the transfer record explains what reached the chain. The recipient was not paid. You can retry
  by submitting a new transfer.
- **`pending` past the expected confirmation window.** This is usually a backend or RPC problem.
  Poll `GET /v1/payments/transfers/{id}` again rather than submitting again. Create a new transfer
  only if the status settles to `failed`.
- **A worker crash part-way through the run.** Resume with each row's original `Idempotency-Key`.
  Persist the returned `Transfer.id` before you advance to the next row.
- **The source wallet runs out of SOL for fees.** Submissions start to fail with fee-related
  errors. This does not happen when SDP is configured to sponsor fees. Otherwise, top up the SOL
  balance of the source wallet before you continue.
