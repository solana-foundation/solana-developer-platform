---
title: Payouts and disbursements
description: Pay many counterparties from one custody wallet with a transfer batch, track each recipient, and fall back to single transfers when a batch doesn't fit.
---

A payout run sends one token from one custody wallet to many recipients: marketplace seller payouts, payroll, affiliate or royalty disbursements. In SDP you run it as a **transfer batch**. One request validates every recipient, packs the recipients into Solana transactions, submits them, and gives you a status for each recipient.

Batches pay **counterparty accounts**, not raw addresses. If a recipient isn't a registered counterparty account, or you need something a batch doesn't support, send single transfers instead. See [When to use single transfers](#when-to-use-single-transfers).

To pay the same counterparty a fixed amount on a schedule, use [Recurring payments](/docs/payments/recurring-payments).

## Prerequisites

- A custody wallet to pay from, with a custody signer configured so SDP can sign and submit. You pass its SDP Wallet `id` (`cwlt_…`, from `GET /v1/wallets`) as `sourceCustodyWalletId`.
- Enough of the token in that wallet. To check, call `GET /v1/payments/wallets/{walletId}/balances` with the wallet's provider `walletId` (for example `privy_wallet_123`), not its `cwlt_…` id. See [Wallet balances](/docs/wallet-operations/balances).
- One counterparty account per recipient, with `accountKind: "crypto_wallet"` and `details.network: "solana"`. Create accounts with `POST /v1/counterparties/{counterpartyId}/accounts`.
- An API key with `payments:write`, `wallets:read` and `counterparties:read`, whose `payments:write` wallet scope includes the source wallet. The estimate endpoint needs `payments:read` in place of `payments:write`.

## How a batch runs

1. SDP checks the request: your key's access to the source wallet, the token, every counterparty account, and every amount.
2. SDP evaluates the batch against the source wallet's policy. See [Wallet policy](#wallet-policy).
3. SDP packs the recipients into Solana transactions, called chunks. Each chunk holds up to `options.maxRecipientsPerTransaction` recipients (default 20, maximum 64), and fewer if the transaction would exceed Solana's size limit.
4. Unless you set `options.preflight` to `false`, SDP simulates each chunk first. A chunk that fails simulation isn't sent, and its recipients are marked `failed`.
5. SDP signs every chunk with the source wallet and submits them concurrently. SDP's fee payer pays the network fees and the rent for any recipient token account that has to be created.
6. SDP responds without waiting for confirmation. Its background reconciliation settles each chunk, and the batch status follows.

Each chunk is one Solana transaction, so the recipients in a chunk succeed or fail together. Chunks are independent: one failed chunk doesn't stop the others. If every recipient must succeed or fail on its own, set `options.maxRecipientsPerTransaction` to `1`.

## Limits and validation

| Field | Rule | When it's broken |
| --- | --- | --- |
| `recipients` | 1 to 500 per batch | `400` |
| `recipients[].counterpartyAccountId` | Must belong to the project, be a `crypto_wallet` account on `solana`, and hold a valid address | `404` if not found, `400` otherwise |
| `recipients[].counterpartyId` | Optional. If you send it, it must own the account | `404` |
| `recipients[].amount` | Positive decimal string in UI units, with no more decimal places than the token has | `400` |
| `token` | `SOL`, a well-known symbol such as `USDC`, or an SPL mint address. One token per batch | `400` |
| `externalId`, `recipients[].externalId` | Up to 256 characters. A correlation field, not an idempotency key | `400` |
| `options.maxRecipientsPerTransaction` | Integer from 1 to 64. Default 20 | `400` |
| Request body | Unknown fields are rejected | `400` |

A single recipient that can't fit in one Solana transaction also returns `400`.

## Estimate a batch

`POST /v1/payments/transfer-batches/estimate` takes the same body as a real batch. It runs the same validation and chunking without signing or submitting anything, and returns how many transactions the batch needs and what it costs:

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/transfer-batches/estimate \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "sourceCustodyWalletId": "cwlt_123",
    "token": "USDC",
    "recipients": [
      { "counterpartyAccountId": "counterparty_account_4837", "amount": "150.00" },
      { "counterpartyAccountId": "counterparty_account_4838", "amount": "75.50" }
    ]
  }'
```

```json title="response.json"
{
  "data": {
    "estimate": {
      "recipientCount": 2,
      "transactionCount": 1,
      "estimatedFees": {
        "networkFeeLamports": "5000",
        "priorityFeeLamports": "0",
        "tokenAccountRentLamports": "2039280",
        "sponsored": true
      }
    }
  },
  "meta": { "requestId": "req_...", "timestamp": "2026-05-14T09:00:00.000Z" }
}
```

`tokenAccountRentLamports` covers recipient token accounts that don't exist yet. `sponsored` tells you whether SDP pays these fees. The estimate doesn't evaluate wallet policy, so a batch that estimates cleanly can still be denied or held.

### Retries and idempotency

Mint one `Idempotency-Key` per payout run and reuse it on every retry of that exact request. An identical request with the same key returns the original batch with its current state and doesn't submit anything again. The same key with a different request returns `409`. A new key, or no key, creates a new batch even if the body is identical.

Keys are scoped to the project. `externalId` is for your own correlation and doesn't deduplicate anything. See [Idempotency](/docs/developing-with-sdp/idempotency).

## Wallet policy

SDP evaluates every batch against the source wallet's policy before it signs anything. The batch is one wallet operation of type `payment_transfer_batch_execute`:

- The operation's amount is the batch total, so amount rules apply to the total.
- Each recipient is also evaluated as a leg with its own amount and destination, so destination and amount rules check every recipient.

If the decision isn't `allow`, SDP creates no batch and submits nothing:

| Status | `error.code` | Meaning |
| --- | --- | --- |
| `403` | `FORBIDDEN` | The policy denied the batch. |
| `202` | `SIGNING_PENDING` | The policy requires approval. |

A policy `403` or `202` carries `error.details` with `walletOperationId`, `policyEvaluationId`, `decision`, `reasonCode`, `reason`, `requiresApproval` and `approvalRequestId`:

```json title="response.json"
{
  "error": {
    "code": "SIGNING_PENDING",
    "message": "Wallet operation requires policy approval",
    "details": {
      "walletOperationId": "wop_...",
      "policyEvaluationId": "peval_...",
      "decision": "approval_required",
      "reasonCode": "wallet_policy_match",
      "reason": "Payment matched approval policy.",
      "requiresApproval": true,
      "approvalRequestId": "appr_..."
    }
  }
}
```

A held batch waits on its approval request. Someone other than the requester approves or rejects it with `POST /v1/wallets/approval-requests/{approvalRequestId}/approve` or `/reject`. On approval, SDP runs the stored request itself, so don't resubmit while it's pending. Track it with `GET /v1/wallets/approval-requests/{approvalRequestId}`: `operation.status` moves to `executing`, then `completed` or `failed`, and `operation.executionError` explains a failure.

If you sent an `Idempotency-Key`, the approved batch carries it. Once it has run, repeating the original request with the same key returns the batch. You can also find it with `GET /v1/payments/transfer-batches?externalId=…`.

See [Wallet policies](/docs/wallet-operations/policies) for rule kinds and operation types.

## Track recipients

Poll `GET /v1/payments/transfer-batches/{batchId}` until `batch.status` is no longer `processing`. The response has the same shape as the create response.

<Tab value="curl">
```bash title="Terminal"
curl https://api.solana.com/v1/payments/transfer-batches/xbatch_abc123 \
  -H "Authorization: Bearer sk_test_..."
```
</Tab>
<Tab value="TypeScript">
```typescript title="wait-for-batch.ts"
async function waitForBatch(batchId: string) {
  while (true) {
    const res = await fetch(
      `https://api.solana.com/v1/payments/transfer-batches/${batchId}`,
      { headers: { Authorization: "Bearer sk_test_..." } }
    );
    const { data } = await res.json();
    if (data.batch.status !== "processing") return data;
    await new Promise((resolve) => setTimeout(resolve, 15_000));
  }
}

const { batch, recipients } = await waitForBatch("xbatch_abc123");
const failed = recipients.filter((r) => r.status === "failed");
// Resubmit `failed` rows; leave everything else alone.
```
</Tab>
</Tabs>

See [Polling cadence](/docs/payments/accept-verification#polling-cadence) for how often to poll.

### Recipient statuses

| Status | Meaning |
| --- | --- |
| `pending` | Not yet assigned to a chunk. |
| `processing` | Assigned to a chunk that SDP is sending or has sent, and waiting for settlement. `transferId` points to the chunk's transfer. |
| `confirmed` | Its chunk settled on-chain. The recipient was paid. |
| `failed` | Its chunk failed simulation, couldn't be sent, or failed on-chain. `error` gives the reason. The recipient wasn't paid. |

### Batch statuses

| Status | Meaning |
| --- | --- |
| `processing` | At least one recipient is still `pending` or `processing`. |
| `confirmed` | Every recipient is `confirmed`. |
| `partially_failed` | Nothing is in flight; some recipients are `confirmed` and some `failed`. |
| `failed` | Nothing is in flight and no recipient was paid. |

If SDP can't tell whether a chunk reached the network, the chunk and its recipients stay `processing` while reconciliation finds out. Don't pay those recipients again.

### Chunk transfers

Each chunk is a payment transfer with `type: "transfer_batch"` and `kind: "batch_pay"`. Several recipients can share one `transferId`, and the transfer's `amount` is the chunk total, so use the recipient rows for per-recipient amounts and destinations. To list chunk transfers across batches, call `GET /v1/payments/transfers?type=transfer_batch`. A transfer's `signature` identifies the chunk's on-chain transaction.

To find past batches, use `GET /v1/payments/transfer-batches`, filtered by `sourceCustodyWalletId`, `token`, `status` or `externalId`, with `page` and `pageSize` (up to 100). It returns batch summaries without recipient rows and only covers wallets your key can read.

### Paying failed recipients again

A batch can't be retried in place. To pay the recipients that ended `failed`, send them in a new batch with a new `Idempotency-Key`, or as single transfers. Never resend recipients that are `pending`, `processing` or `confirmed`.

## When to use single transfers

Use `POST /v1/payments/transfers`, one call per recipient, when:

- **The recipient isn't a counterparty account.** Batches only pay `crypto_wallet` counterparty accounts. Single transfers take any Solana wallet address as `destination`. Alternatively, register the recipient as a counterparty account first.
- **You need a memo on each payment.** Single transfers accept `memo`. Batch requests have no memo field.
- **You're retrying a few failed recipients** and a second batch isn't worth it.

Batches also need one source wallet and one token. Split a run that mixes either into several batches, or one batch per 500 recipients.

The rest of this page covers running payouts as single transfers.

### Designing a run of single transfers

1. **Resolve recipients** in your application: the rows to pay, each with destination address and amount.
2. **Pick a run identifier** you control, for example `payout_2026-05-14_marketplace_sellers`.
3. **Send one transfer per row** with `POST /v1/payments/transfers`. Put the run ID and a row ID in `memo`, for example `payout_2026-05-14_marketplace_sellers/row_4837`.
4. **Store** the returned `transfer.id` and `transfer.status` against the row before moving on, so you can poll it later.
5. **Reconcile** once every row is sent, by listing outbound transfers for the window. See [Reconciling a run](#reconciling-a-run).

## Dedup and retries

Two layers protect you against paying a row twice if a worker dies mid-run:

1. **Idempotency keys.** Generate one stable `Idempotency-Key` per recipient row and reuse it on retries. An identical request for the same source wallet returns the original transfer. Reusing the key for a different request returns `409`.
2. **Your own mapping.** Store the SDP transfer ID for each row before moving to the next. On restart, resend with the same key, or skip rows that already have a transfer ID.

A fresh idempotency key creates a new transfer, even if the payload is identical. Once a transfer has an on-chain `signature`, that signature is unique across SDP transfers. Use it to cross-check against another indexer, not as the retry mechanism.

async function payoutRecipient(row: PayoutRow): Promise<string> {
  if (row.transferId) return row.transferId; // already submitted

  const response = await fetch(
    "https://api.solana.com/v1/payments/transfers",
    {
      method: "POST",
      headers: {
        "Authorization": "Bearer sk_test_...",
        "Content-Type": "application/json",
        "Idempotency-Key": row.idempotencyKey,
      },
      body: JSON.stringify({
        sourceCustodyWalletId: row.sourceCustodyWalletId,
        destination: row.destination,
        token: row.token,
        amount: row.amount,
        memo: `${row.batchId}/row_${row.id}`,
      }),
    }
  );

  const { data } = await response.json();
  // The transfer record is under data.transfer (standard SDP success envelope).
  await row.persistTransferId(data.transfer.id); // persist BEFORE returning
  return data.transfer.id;
}

## Reconciling a run

After the loop finishes, list outbound transfers in the run's time window and tally them against your recipient table:

<Tab value="curl">
```bash title="Terminal"
curl "https://api.solana.com/v1/payments/transfers?direction=outbound&from=2026-05-14T00:00:00Z&to=2026-05-14T23:59:59Z&pageSize=100" \
  -H "Authorization: Bearer sk_test_..."
```
</Tab>
<Tab value="TypeScript">
```typescript title="list-outbound-transfers.ts"
async function* listOutboundTransfers(from: string, to: string) {
  let page = 1;
  while (true) {
    const url = new URL("https://api.solana.com/v1/payments/transfers");
    url.searchParams.set("direction", "outbound");
    url.searchParams.set("from", from);
    url.searchParams.set("to", to);
    url.searchParams.set("page", String(page));
    url.searchParams.set("pageSize", "100");

    const res = await fetch(url, {
      headers: { Authorization: "Bearer sk_test_..." },
    });
    const { data, meta } = await res.json();
    yield* data;
    if (!meta.hasMore) return;
    page += 1;
  }
}
```
</Tab>
</Tabs>

Filter the results on `memo.startsWith(runId)`, or whatever convention you chose, to scope them to the run. Match each recipient row by SDP transfer ID, and treat `confirmed` or `finalized` as paid.

### Failure modes

- **`failed`**: the transfer didn't go through, and `error` says why. The recipient wasn't paid. To retry, submit a new transfer with a new idempotency key.
- **`processing` for longer than you expect**: a `200` can return a `processing` transfer that already has a signature while SDP is still reconciling it. Poll `GET /v1/payments/transfers/{transferId}` instead of resubmitting. Only send a new transfer once the status is `failed`.
- **The worker crashes mid-run**: resume with each row's original `Idempotency-Key`, and store the returned transfer ID before moving on.
