SDP does not provide a hosted checkout product. To accept a payment, you publish a Solana address
that you control. SDP detects the inbound transfer and returns it in the transfer list.

This page covers that pattern. [Verifying a payment](/docs/payments/accept-verification) and
[Indexing and reconciliation](/docs/payments/accept-indexing) cover the details.

## Receiving-address convention

The receiving address is a custody wallet you control. Choose one of two scopes.

**One wallet per order.** This is the recommended scope for accept flows. Create a fresh custody
wallet, or a sub-account, for each order or for each customer. The destination address is then your
correlation key. The `destination` field on the inbound transfer maps one-to-one to your order row,
so you do not depend on a memo field or a reference field.

**One wallet per merchant scope.** For a marketplace, create one custody wallet per seller. For
treasury operations, create one per ledger account. This scope is reasonable when you do not need
correlation, as in treasury and settlement work, or when each merchant takes a single fixed-amount
payment.

The address you publish is the onchain `address` of the custody wallet. Fetch it with
[`GET /v1/wallets/{walletId}`](/docs/reference/api/wallets). Add `?includeBalance=false` when you
need only the wallet metadata. That skips a balance RPC call and a pricing lookup.

Senders use that address as the destination of a normal SPL token transfer. SDP indexes the inbound
transfer and returns it from [`GET /v1/payments/transfers`](/docs/payments/accept-indexing) with
`direction=inbound`.

**Correlation caveats.** SDP does not populate `Transfer.memo` for a customer-initiated inbound
transfer. SDP does not extract Solana memo-program instructions into the record, and the inbound
record carries no reference field either.

The `memo` field is optional in the schema rather than nullable. SDP therefore omits it from the
response instead of returning `null`. SDP populates `memo` only for a transfer that SDP itself
initiated, whether outbound or internal.

The reliable correlation key on the record is the inbound transfer's `destination`. That is the
reason for the per-order receiving address above. If you need correlation by memo or by reference,
for example for a Solana Pay URL that carries an order pubkey, read the onchain transaction through
Solana RPC using the transfer's `signature`.

## Integration options

A customer can land a payment on the address you control in two ways.

1. **Direct address share.** You display the address, the expected token, and the expected amount
   in your own screens. The customer's wallet sends the transfer. This works with any Solana wallet
   and any client, because SDP picks the transfer up from the chain. Use it for B2B settlement,
   treasury operations, and crypto-native flows.
2. **Solana Pay request.** For consumer checkout, give the customer a
   [Solana Pay](https://solana.com/docs/payments/accept-payments/solana-pay) URL or QR code. It
   carries the destination, the amount, and a per-order `reference` pubkey. The customer's wallet
   builds the transfer and attaches the `reference` account onchain. You then match the transfer
   back to the order by reading the transaction through Solana RPC, because neither the `reference`
   nor a wallet-set memo reaches the SDP `Transfer` record. See the
   [correlation caveats](#receiving-address-convention) above. SDP does not host a Solana Pay
   endpoint today, and SDP does not attach a Solana Pay reference onchain. See
   [Solana Pay reference accounts](/docs/payments/accept-indexing#solana-pay-reference-accounts-roadmap).
   For correlation inside SDP today, use a per-order destination address.

## What SDP gives you today

- **Indexed inbound transfers.** `GET /v1/payments/transfers?direction=inbound` returns the
  persisted transfers across your custody wallets. Filter by exact `custodyWalletId`. Add
  `includeObserved=true` to include recent chain observations for that wallet. See
  [Indexing and reconciliation](/docs/payments/accept-indexing).
- **Per-transfer status reads.** `GET /v1/payments/transfers/{id}` returns the lifecycle of one
  payment. See [Verifying a payment](/docs/payments/accept-verification).
- **Wallet balances.** `GET /v1/payments/wallets/{walletId}/balances` returns the current per-token
  balance on a receiving wallet. See [Wallet balances](/docs/wallet-operations/balances).
- **Address-based correlation.** The `destination` on the inbound transfer is the correlation key
  held on the record. Pair it with a per-order receiving address to map an inbound transfer to an
  order without a memo. See the [correlation caveats](#receiving-address-convention) above.

## What SDP does not give you yet

- **No checkout session and no payment intent object.** You do not pre-register an expected payment
  with the API. SDP recognizes an inbound transfer after the fact, and you match it on the
  `destination` held on the record. The token and the amount are available as extra checks. See the
  [correlation caveats](#receiving-address-convention) above.
- **No webhooks on settlement.** Observe a status change by polling
  `GET /v1/payments/transfers/{id}`, or by listing again with date filters. See the
  [polling cadence guidance](/docs/payments/accept-verification#polling-cadence).
- **No hosted Solana Pay URL endpoint.** To serve a Solana Pay URL or QR code, build it in your own
  client from the destination address, the token mint, the amount, and the reference pubkey.

## Worked example: a marketplace checkout

This is the smallest accept flow built on the per-order-address pattern.

1. At checkout, create a fresh custody wallet for the order, or claim one from a warm pool.
2. Stage a row in your `orders` table. Store that wallet's onchain address, the expected amount,
   and the token.
3. Show the customer the per-order custody wallet address, the token, and the amount. Build a
   Solana Pay URL from those fields if you want a QR code. No SDP endpoint is involved.
4. The customer's wallet submits the transfer.
5. Your reconciliation worker lists recent persisted inbound transfers on a schedule. To discover
   chain activity that SDP has not persisted yet, poll each receiving wallet with its exact
   `custodyWalletId` and `includeObserved=true`. Match each transfer's `destination` to an open
   order in your `orders` table.
6. When a transfer matches, mark the order paid and ship the goods. Use the transfer's `signature`
   to deduplicate if the worker runs again. The `signature` is `UNIQUE` on the transfer record once
   it is present.

This flow is deliberately low-level. SDP provides no session object. Treat the `orders` table as
your checkout state machine, and treat SDP as the settlement and status backend.
