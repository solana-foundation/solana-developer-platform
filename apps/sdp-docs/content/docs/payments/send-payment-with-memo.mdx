---
title: Payment with memo
description: Attach an order ID, an invoice number, or a customer reference to an SDP transfer.
---

The `memo` field on `POST /v1/payments/transfers` carries a UTF-8 string of your choice alongside
the onchain transfer. A memo can be up to 256 characters.

SDP stores the memo on the `Transfer` record, and returns it in list and read responses. Your
indexer can therefore map each transfer back to a row in your own product database.

## When to use a memo

Use a memo when you need a free-form correlation value that your backend already knows at request
time:

- **Order IDs and invoice IDs.** A value such as `order_2026-05-14_4837` ties the transfer to a
  checkout row.
- **Customer references.** Your internal customer or account identifiers, for support and
  reconciliation.
- **Run identifiers.** A payout-batch ID shared across many outbound transfers in one
  disbursement.

SDP stores the memo on its own record. SDP does not attach it as a Solana memo-program
instruction. If you need an onchain memo that a block explorer displays, handle that at the
transaction level. See the trade-offs section below.

SDP keeps the memo on the transfer record:

```json title="response.json"
{
  "id": "xfr_...",
  "memo": "order_2026-05-14_4837",
  "status": "finalized",
  "signature": "5xR1...",
  ...
}
```

A memo can be up to 256 characters. SDP accepts UTF-8. Trim or sanitize the value before you send
it if your downstream systems are stricter.

## Trade-offs against Solana Pay reference accounts

For accept flows, a **Solana Pay reference account** is an alternative way to correlate. You
generate a unique pubkey for each order and include it in the onchain transfer as a reference.

This has two advantages. The link has onchain provenance, so anyone can verify it without trusting
the SDP database. The payer can also build the transfer themselves from a Solana Pay URL.

SDP does not attach a Solana Pay reference onchain today, and SDP does not return one on an
inbound transfer record. Use `memo` for correlation inside SDP, or read the reference from the
transaction through Solana RPC. See [Accept payments](/docs/payments/accept-overview) and
[Indexing and reconciliation](/docs/payments/accept-indexing) for the inbound side.

As a rule: a memo is simpler when you initiate the transfer, as in a server-side payout or an
internal move. A reference is stronger when a third party initiates the transfer, as in a customer
checkout or a donation.

## Indexing implications

`GET /v1/payments/transfers` and `GET /v1/payments/transfers/{id}` both return the memo. Your
reconciliation worker can filter by date, direction, or token, and then match each row to your
order table by memo. See [Indexing and reconciliation](/docs/payments/accept-indexing) for the
query patterns.
