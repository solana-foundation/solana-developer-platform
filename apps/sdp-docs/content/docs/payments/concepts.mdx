---
title: How payments work on SDP
description: The wallets, tokens, signing, fees, and records behind an SDP payment.
---

An SDP payment moves value between two Solana accounts. A custody wallet sends tokens to a
destination address, and SDP records the transfer.

This page explains the parts that the rest of this section assumes: wallets, tokens, execution,
fees, and the transfer record.

## Custody wallets

Every SDP payment starts from a **custody wallet**. A custody wallet is a Solana wallet that SDP
manages for an organization, and optionally for one project inside it.

A custody provider holds the key and signs with it. SDP gives you one stable Solana address and
sends each signing request to the provider that holds the key. The wallet signs your outbound
transfers. It also reports balances and applies policies for the addresses you control.

Create your custody wallets before you send a payment. See
[Set up wallets](/docs/guides/setup-wallets).

A transfer request passes the SDP wallet `id` (`cwlt_…`) as `sourceCustodyWalletId`. The response
returns the same value as `custodyWalletId`, and keeps the provider's own identifier separately as
`providerWalletId`. The `destination` is always the recipient's Solana address.

Ramp quote endpoints use the same fields for every provider. An onramp quote takes
`destinationCustodyWalletId`. An offramp quote takes `sourceCustodyWalletId`. Both identify a
custody wallet you control, by the `id` that `GET /v1/wallets` returns.

SDP resolves provider-specific identifiers, such as a customer ID or a payout account ID, from the
counterparty's provider requirements. See [Ramps](/docs/payments/ramps).

## Tokens and token accounts

A payment transfers **SPL tokens**. These can be stablecoins, tokenized assets, or any other mint
your project supports.

On `POST /v1/payments/transfers`, the `token` field takes the **mint address**. For native SOL,
pass the string `SOL`. SDP does not resolve a symbol such as `USDC` when it receives the request.

On `GET /v1/payments/transfers`, the `token` filter matches the stored `Transfer.token` value
exactly. A transfer created through the API stores the mint you supplied, or `SOL`. A transfer that
SDP observed onchain can store a resolved symbol instead, such as `USDC`.

Filter with the same label that the response shows. You can also omit `token` and filter the
results in your own code.

Balance responses behave differently. They always try to resolve the symbol, and return it whenever
SDP knows the mint. A wallet that holds USDC therefore reports `USDC`, not the mint address.

**Every amount in a request is a decimal string in display units.** `"100.00"` means 100 tokens,
whatever the mint's decimal count is. This rule covers payment transfers and issuance operations
such as mint, burn, seize, and force-burn. SDP converts the value to the smallest unit when it
builds the transaction.

Wallet balance responses are the one exception. They return a raw `amount` in the smallest unit and
a `uiAmount` as a decimal string, so you can use whichever one you need.

## Transfer execution

SDP executes an outbound wallet transfer when you call `POST /v1/payments/transfers`. SDP builds
the transaction, signs it with the source wallet's custody key, and submits it to the configured
Solana cluster. SDP then records the transfer and tracks its status.

The rest of this section assumes that SDP submits the transfer from a custody wallet you control.

## Fees and sponsorship

The fee payer of a transaction pays the Solana fee in SOL. On a wallet transfer, the source custody
wallet is the fee payer by default.

You can configure SDP to sponsor the fee instead. An end-user wallet then does not need a SOL
balance.

## The transfer data model

Every transfer creates a `Transfer` record, whether it succeeds or fails. These are the fields that
matter in most flows.

| Field | Meaning |
| --- | --- |
| `id` | SDP-internal transfer identifier (use this in API URLs). |
| `status` | Wallet transfers: `processing`, `confirmed`, `finalized`, `failed`. Ramp transfers: `pending`, `awaiting_payment`, `settling`, `completed`, `canceled`, `expired`, `failed`. See [Verifying a payment](/docs/payments/accept-verification). |
| `direction` | `inbound` (someone paid you) or `outbound` (you paid someone). |
| `source`, `destination` | Solana addresses. |
| `token`, `amount` | What moved, and how much. `amount` is a decimal string in display units, for example `"100.00"`. |
| `memo` | Optional UTF-8 string, up to 256 chars. See [Payment with memo](/docs/payments/send-payment-with-memo). |
| `signature` | The Solana transaction signature, set once the transfer is confirmed. It is unique across SDP, so use it as the deduplication key. |
| `slot`, `blockTime`, `fee` | Settlement details from the network, filled in as the transaction lands. |
| `error` | Set when the transfer fails. The rest of the record shows what reached the network. |
| `risk` | Risk score metadata. Present only when a risk provider is configured. |

An outbound wallet transfer starts at `processing`, then moves to `confirmed` and then
`finalized`. An inbound transfer that SDP finds onchain appears at `confirmed`. A ramp transfer can
start at `pending` while the provider completes its own steps.

See [Verifying a payment](/docs/payments/accept-verification#status-lifecycle) for the full state
table.

## What SDP does and does not give you

SDP gives you what you need to send, track, and reconcile payments at the level of a single
transfer:

- Status polling.
- Filtered transfer lists.
- Balances per wallet.
- Replay of a request through the `Idempotency-Key` header, per wallet.
- A unique `signature` once the network confirms the transaction. See
  [Basic payment](/docs/payments/send-basic-payment#deduplication).

SDP does not give you commerce objects such as a checkout session or an invoice. The
[Accept payments](/docs/payments/accept-overview) section shows how to build those on top of the
transfer record.
