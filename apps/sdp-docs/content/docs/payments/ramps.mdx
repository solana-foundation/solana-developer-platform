---
title: Ramps
description: Fiat on-ramps and off-ramps. Let a customer buy crypto with fiat, or cash out from a wallet you custody, through one set of endpoints.
---

A ramp is a fiat-to-crypto or crypto-to-fiat conversion run by a provider (MoonPay, Lightspark, BVNK, MoneyGram, Coinbase, Mural, or Stripe). SDP puts all seven behind the same endpoints, so your integration reads one contract and branches on the response rather than on the provider name.

The flow is the same in both directions:

1. Discover which fiat currencies pair with which Solana rails, and which providers serve each pair.
2. Price the conversion with `estimate`. It commits you to nothing.
3. Make sure the counterparty (the person or business on the other side) has cleared the provider's requirements.
4. Request a quote. This creates the ramp, creates a transfer record, and returns what the provider needs from the end user.
5. Track the transfer until it settles.

Two things trip people up. `estimate` and `quote` are separate calls, and no call does both. And every quote needs a counterparty that the provider has accepted; a wallet alone is not enough.

This page assumes you have an API key with `payments:read` and `payments:write`, and at least one custody wallet from `GET /v1/wallets`. For per-provider configuration and credentials, see [Ramp providers](/docs/payments/ramps-providers).

## Discover available corridors

A corridor is a fiat currency paired with a Solana rail, for example `USD` to `usdc.solana`. Not every combination exists, and the providers that serve a corridor vary by corridor.

```bash
curl "https://api.solana.com/v1/payments/ramps/onramp/currency?source=USD&dest=usdc.solana" \
  -H "Authorization: Bearer sk_test_..."
```

```json
{
  "data": {
    "currencies": {
      "sources": ["USD"],
      "destinations": ["usdc.solana"]
    },
    "pairs": [
      {
        "source": "USD",
        "dest": "usdc.solana",
        "providers": ["lightspark", "bvnk", "moneygram", "coinbase", "mural", "stripe"]
      }
    ],
    "providerDetails": {
      "lightspark": {
        "currencies": { "USD": { "min": "1", "max": "10000" } },
        "countrySupport": { "coverage": "unreported" },
        "entityTypes": ["business", "individual"]
      },
      "mural": {
        "currencies": { "USD": { "min": null, "max": null } },
        "countrySupport": { "coverage": "by-country", "countries": { "US": ["USD"] } },
        "entityTypes": ["business"]
      }
    },
    "supportHash": "d253b18a629c6403c4617cc256ea9a530d013569c4a2c04364a6edd264ecbc0f"
  }
}
```

The response has four parts. `pairs` is the one to read: each entry is a real corridor with the providers that serve it. `currencies` lists the sources and destinations that appear in `pairs` after your filters are applied. `providerDetails` gives each provider's amount bounds, country coverage, and the counterparty entity types it accepts for this direction. `supportHash` identifies the support matrix the API is running, which is useful when you cache the result.

<Callout type="warn">
Read `pairs`, not the cross product of `sources` and `destinations`. Most combinations of the two arrays are not corridors. `USD` pairs with `usdc.solana` through six providers and with `sol.solana` through four, and those two lists overlap only partly.
</Callout>

All three query parameters are optional. On the on-ramp endpoint `source` is a fiat code and `dest` is a rail. On `GET /v1/payments/ramps/offramp/currency` the direction flips: `source` is the rail and `dest` is the fiat code. `provider` narrows either one to a single provider.

## Price the conversion

`estimate` needs no counterparty and creates nothing. It asks every provider that serves the corridor and returns each answer separately.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash
curl -X POST https://api.solana.com/v1/payments/ramps/onramp/estimate \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "assetRail": "usdc.solana",
    "fiatCurrency": "USD",
    "fiatAmount": "100.00"
  }'
```
</Tab>

```json
{
  "data": {
    "estimates": [
      {
        "provider": "moneygram",
        "status": "ok",
        "estimate": {
          "provider": "moneygram",
          "direction": "onramp",
          "fiatCurrency": "USD",

          "cryptoAmount": "100.000000",
          "exchangeRate": "1",

        }
      },
      {
        "provider": "bvnk",
        "status": "error",
        "error": "BVNK request failed with status 404"
      }
    ]
  }

```

Each entry has one of three statuses. `ok` carries the estimate. `unsupported` means the provider serves the corridor but can't give an indicative price up front; you learn the rate at quote time. `error` carries the provider's error text; an organization that isn't entitled to a provider sees that provider as `error` here rather than as a top-level 403.

<Callout type="warn">
Treat `estimates` as a partial result. Filter to `status === "ok"` before comparing prices, and don't assume any particular provider will be present. A corridor that no provider serves returns `estimates: []` with HTTP 200, not an error.
</Callout>

`POST /v1/payments/ramps/offramp/estimate` takes the same shape with `cryptoAmount` in place of `fiatAmount`. `fiatCurrency` is required on both.

### Estimate request fields

| Field | Required | Notes |
| --- | --- | --- |
| `assetRail` | yes | The Solana rail, for example `usdc.solana`. One of `sol.solana`, `usdc.solana`, `usdt.solana`, `usdg.solana`, `pyusd.solana`. |
| `fiatCurrency` | yes | ISO 4217 code. |
| `fiatAmount` | on-ramp | Decimal string greater than zero. |
| `cryptoAmount` | off-ramp | Decimal string greater than zero. |

The quote step names the asset differently, as a bare token symbol (`USDC`, not `usdc.solana`). Take the part before the dot and upper-case it.

## Provision the counterparty

A quote is tied to a counterparty, the customer or business on the fiat side of the conversion. Create one if you haven't:

```bash
curl -X POST https://api.solana.com/v1/counterparties \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "entityType": "individual",
    "displayName": "Amara N. Okafor",
    "externalId": "CUST-2087"
  }'
```

That is the whole body. SDP does not store names, emails, dates of birth, or addresses on the counterparty; providers that need identity details collect them in their own flows. The response carries an `id` of the form `cpty_...`, which is what `counterpartyId` takes below.

Before a quote will succeed, the counterparty has to satisfy the provider's requirements for that corridor. Requirements depend on the provider, the direction, the token, and the currency, so all of those are part of the request. On-ramp requests also need the destination wallet, and a Lightspark off-ramp request can carry the `destinationCountry` the payout is going to.

```bash
curl "https://api.solana.com/v1/counterparties/$COUNTERPARTY_ID/requirements\
?provider=lightspark&direction=offramp&cryptoToken=USDC&fiatCurrency=USD" \
  -H "Authorization: Bearer sk_test_..."
```

Every response carries `provider`, `direction`, and a `status`. `ready` means quote now. Any other status says what to do next, and the rest of the response is shaped by it. The full list is in the table further down. A Lightspark off-ramp walks through most of the flow, so it is the worked example here: identity fields first, then a payout account.

### Step 1: identity fields

A counterparty the provider has never seen returns `collect_counterparty` with the fields the provider needs to create its customer record. Lightspark and BVNK both do this, in both directions, each with its own list. For an individual counterparty Lightspark asks for:

```json
{

    "direction": "offramp",
    "status": "collect_counterparty",
    "fields": [
      { "kind": "text", "key": "customer.fullName", "label": "Full name", "required": true, "maxLength": 256 },
      { "kind": "date", "key": "customer.birthDate", "label": "Date of birth", "required": true, "before": "2026-09-03" },
      { "kind": "country", "key": "customer.nationality", "label": "Nationality", "required": true },
      { "kind": "country", "key": "customer.region", "label": "Region", "required": true },
      {
        "kind": "text",
        "key": "customer.email",
        "label": "Email",
        "required": true,
        "maxLength": 320,
        "pattern": "^[^\\s@]+@[^\\s@]+\\.[^\\s@]+$",
        "placeholder": "name@example.com"
      },
      {
        "kind": "address",
        "key": "customer.address",
        "label": "Residential address",
        "required": true,
        "fields": [
          { "kind": "text", "key": "customer.address.line1", "label": "Address line 1", "required": true },
          { "kind": "text", "key": "customer.address.city", "label": "City", "required": true },
          { "kind": "text", "key": "customer.address.subdivisionCode", "label": "State / region", "required": false },
          { "kind": "text", "key": "customer.address.postalCode", "label": "Postal code", "required": true },
          { "kind": "country", "key": "customer.address.countryCode", "label": "Country", "required": true }
        ]
      },
      {
        "kind": "select",
        "key": "purposeOfPayment",
        "label": "Purpose of payment",
        "required": true,
        "options": [{ "value": "...", "label": "..." }]
      }
    ]
  }
}
```

Each field has a `kind` that tells you what to render and what to send back:

| `kind` | Render | Submit under the field's `key` |
| --- | --- | --- |
| `text` | A text input. `pattern`, `minLength`, `maxLength`, `placeholder`, and `mask` are hints the API also enforces. | The string. |
| `select` | The listed `options`. | One option's `value`. |
| `country` | A country picker. No options are sent. | An ISO 3166-1 alpha-2 code such as `US`. Anything else is rejected. |
| `date` | A date picker. `before` is the exclusive upper bound, so a birth date must fall before today. | `YYYY-MM-DD`. |
| `address` | Its nested `fields` as a group. | Each nested field separately, under its own dotted key. |

Submit what you collected to the same path. Values go in `collectedData`, keyed exactly as the field's `key`:

```bash
curl -X POST "https://api.solana.com/v1/counterparties/$COUNTERPARTY_ID/requirements" \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "lightspark",
    "direction": "offramp",
    "cryptoToken": "USDC",
    "fiatCurrency": "USD",
    "collectedData": {
      "customer.fullName": "Ada Lovelace",
      "customer.birthDate": "1990-12-10",
      "customer.nationality": "US",
      "customer.region": "US",
      "customer.email": "ada@example.com",
      "customer.address.line1": "1 Main St",
      "customer.address.city": "New York",
      "customer.address.subdivisionCode": "NY",
      "customer.address.postalCode": "10001",
      "customer.address.countryCode": "US",
      "purposeOfPayment": "..."
    }
  }'
```

A submission that leaves out a required field comes back as `collect_counterparty` again, listing only what is still missing. A complete one creates the provider-side customer and moves on: an on-ramp answers `ready`, an off-ramp answers `collect_account`.

### Step 2, off-ramp only: the payout account

`collect_account` carries a `payout` tree instead of a flat field list, because the bank fields depend on where the money is going:

```json
{
  "data": {
    "provider": "lightspark",
    "direction": "offramp",
    "status": "collect_account",
    "payout": {
      "countryRails": {
        "US": [
          { "value": "ACH", "label": "ACH" },
          { "value": "WIRE", "label": "Wire" },
          { "value": "RTP", "label": "RTP" },
          { "value": "FEDNOW", "label": "FedNow" }
        ]
      },
      "railFields": {
        "ACH": [
          { "kind": "text", "key": "bankAccount.accountNumber", "label": "Account number", "required": true, "minLength": 1, "maxLength": 34, "placeholder": "12345678" },
          {
            "kind": "select",
            "key": "bankAccount.bankAccountType",
            "label": "Account type",
            "required": false,
            "options": [{ "value": "CHECKING", "label": "Checking" }, { "value": "SAVINGS", "label": "Savings" }]
          },
          { "kind": "text", "key": "bankAccount.routingNumber", "label": "Routing number", "required": true, "pattern": "^[0-9]{9}$", "minLength": 9, "maxLength": 9, "placeholder": "021000021" }
        ]
      },
      "accounts": []
    }
  }
}
```

`countryRails` has one entry per country that can receive this currency, each listing the rails available there. `railFields` has the fields for every rail that appeared. `accounts` lists payout accounts this counterparty already has for the currency, empty on the first pass. The example is trimmed to the required ACH fields plus one optional one; the live tree carries the other rails and their optional fields too.

Let the user pick a country, then a rail from that country's list, then render `railFields[rail]`. Submit all three in one `collectedData`:

```bash
curl -X POST "https://api.solana.com/v1/counterparties/$COUNTERPARTY_ID/requirements" \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "lightspark",
    "direction": "offramp",
    "cryptoToken": "USDC",
    "fiatCurrency": "USD",
    "collectedData": {
      "destinationCountry": "US",
      "paymentRails": "ACH",
      "bankAccount.routingNumber": "021000021",
      "bankAccount.accountNumber": "000123456789"
    }
  }'
```

That creates the payout account with the provider and answers `ready` with its id:

```json
{
  "data": {
    "provider": "lightspark",
    "direction": "offramp",
    "status": "ready",
    "providerAccountId": "counterparty_provider_account_93809134-1b2c-4d5e-8f90-a1b2c3d4e5f6"
  }
}
```

Keep `providerAccountId`. The off-ramp quote takes it to pin the payout to that account, and it is how you tell accounts apart once a counterparty has more than one.

### Reusing a payout account

The account persists, so the next time you call the `GET` with the destination country on the query string, the API resolves it for you:

```bash
curl "https://api.solana.com/v1/counterparties/$COUNTERPARTY_ID/requirements\
?provider=lightspark&direction=offramp&cryptoToken=USDC&fiatCurrency=USD&destinationCountry=US" \
  -H "Authorization: Bearer sk_test_..."
```

A country with exactly one active account answers `ready` with that account's `providerAccountId`, plus the `payout` tree in case the user wants to send somewhere else. Inside the tree, `accounts` now lists what exists: `id`, `destinationCountry`, `paymentRail`, `status`, and where the provider reports them, `bankName` and `accountNumberLast4`. A country with no account answers `collect_account` as above. A country with two or more active accounts answers `400` until you choose one, which you do by submitting `providerAccountId` alongside `collectedData: { "destinationCountry": "US" }`; the `POST` verifies the account belongs to this counterparty and corridor and answers `ready`. Without `destinationCountry` the `GET` returns the tree and lets you pick.

Every provider account a counterparty holds, across providers, is listed at `GET /v1/counterparties/{counterpartyId}/provider-accounts`, filterable by `provider`, `fiatCurrency`, and `destinationCountry`. `destinationCountry` on a requirements `GET` is accepted for Lightspark off-ramps only; other providers reject it with `400`.

### Other providers

The `POST` body varies by provider. Lightspark and BVNK take `collectedData`; BVNK additionally takes `agreementConsent: true` once it has shown you its agreements. MoonPay, MoneyGram, Coinbase, and Stripe take only `provider` and `direction` and answer `ready` at once. Mural takes the corridor fields and no `collectedData`. Repeat the `GET` until `status` reads `ready`.

The statuses you will see:

| `status` | Providers | Meaning |
| --- | --- | --- |
| `ready` | all | Quote now. A Lightspark off-ramp also returns `providerAccountId`. |
| `collect_counterparty` | Lightspark, BVNK | Submit the identity `fields`. |
| `collect_account` | Lightspark off-ramp | Pick a country and rail from `payout` and submit that rail's fields. |
| `collect` | BVNK off-ramp | Submit the bank `fields` for the beneficiary. |
| `unsupported` | all | The provider won't serve this counterparty for this corridor. `reason` says why: a currency it can't pay out, or an entity type it doesn't take. |
| `onboarding_not_started` | Lightspark, Mural | The provider-side customer does not exist yet. For Mural, see the warning below. |
| `customer_agreement_required` | BVNK | Show the listed `agreements` (each has a `downloadUrl`, minted per response) and resubmit with `agreementConsent: true`. |
| `customer_pending_agreement_acceptance` | BVNK | Wait and poll again. |
| `customer_verification_required` | BVNK, Mural | Send the customer to `verificationUrl` to complete KYC. The link is minted per response. |
| `terms_of_service_required` | Mural | Send the customer to `termsOfServiceUrl`. |
| `customer_verifying`, `customer_funding_account_provisioning`, `funding_account_provisioning` | BVNK, Mural | Wait and poll again. |
| `customer_verification_failed`, `customer_funding_account_provisioning_failed` | BVNK, Mural | The provider rejected the customer or could not open the account. Polling will not change it; the provider-side status has to. |

Three seams still fail because SDP no longer stores the identity fields the provider wants at that moment, and just-in-time collection is not wired for that call. Each returns `400` with a message ending in `requires identity fields that are no longer stored; JIT collection is not wired yet`. A Coinbase on-ramp quote fails this way for a counterparty Coinbase has not seen, even after requirements reported `ready`; counterparties Coinbase already knows keep working. A Mural requirements call fails this way for a counterparty with no Mural organization yet, so `onboarding_not_started` cannot currently advance. A BVNK off-ramp quote fails this way for every counterparty today, because the party details BVNK wants on the quote are rebuilt from fields that are no longer stored; the BVNK on-ramp is not affected, since its identity fields now arrive through `collect_counterparty`.

## Request a quote

A quote creates the ramp with the provider and returns what the end user has to do next.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash
curl -X POST https://api.solana.com/v1/payments/ramps/onramp/quote \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "lightspark",
    "counterpartyId": "cpty_52f96f7f-4e90-47a3-a824-a38f62b86188",
    "destinationWallet": "privy_grfk86kwihjlny3d6zr3jxyv",
    "cryptoToken": "USDC",
    "fiatCurrency": "USD",
    "fiatAmount": "10.00",
    "rampsMemo": { "orderId": "ord_4821" }
  }'
```
</Tab>
<Tab value="TypeScript">
```typescript
const response = await fetch(
  "https://api.solana.com/v1/payments/ramps/onramp/quote",
  {
    method: "POST",

      Authorization: "Bearer sk_test_...",
      "Content-Type": "application/json",

      provider: "lightspark",
```

The response has two top-level keys under `data`: `quote`, the provider-shaped payment details, and `transferId`, the SDP transfer record created for this ramp. Keep both. `transferId` is how you find out whether the money arrived.

### Quote request fields

| Field | Required | Notes |
| --- | --- | --- |
| `provider` | yes | One of the providers in the corridor's `providers` list. SDP does not choose for you. |
| `counterpartyId` | yes | A `cpty_...` id whose requirements are `ready` for this provider and corridor. |
| `destinationWallet` | on-ramp | The `walletId` from `GET /v1/wallets` (for example `privy_...`) or that wallet's public key. It has to resolve to one of your wallets; an unrelated Solana address is rejected with `destinationWallet must reference an SDP wallet.` The `cwlt_...` custody wallet `id` is not accepted here. |
| `sourceWallet` | off-ramp | The wallet you are cashing out from. Same forms, same restriction. |
| `destinationCountry` | off-ramp, Lightspark | ISO 3166-1 alpha-2 code of the country the payout goes to. Required for Lightspark; it selects the payout account's corridor together with `fiatCurrency`. Other providers do not take it. |
| `providerAccountId` | off-ramp, Lightspark, optional | The payout account to settle to, from the requirements flow above or `GET /v1/counterparties/{counterpartyId}/provider-accounts`. Omitted, SDP uses the counterparty's single active account for the corridor; two or more active accounts return `400` naming the ambiguity, and none returns `409`. An id that belongs to another counterparty, another corridor, or an inactive account is rejected with `400`, never silently swapped. The account used is recorded on the transfer. |
| `cryptoToken` | yes | Token symbol, for example `USDC`. Passing the rail form (`usdc.solana`) is rejected with `Invalid ramp currency code` on `cryptoToken`. |
| `fiatCurrency` | on-ramp; in practice off-ramp too | Required on on-ramp. The off-ramp schema marks it optional, but Lightspark and BVNK reject an off-ramp quote without it, so treat it as required unless you have checked your provider. |
| `fiatAmount` | on-ramp | Decimal string greater than zero. |
| `cryptoAmount` | off-ramp | Decimal string greater than zero. |
| `rampsMemo` | no | Up to 20 string key-value pairs stored on the transfer for your own correlation. |
| `domain` | no | Coinbase only. The browser origin host for its Apple Pay payment link. |

SDP does not enforce provider amount bounds. The `min` and `max` in `providerDetails` are advisory, and an out-of-range amount fails at the provider with that provider's message. Lightspark's sandbox, for example, caps on-ramp requests at 10 USD and says so in its error.

### Idempotency works differently here

The `Idempotency-Key` header that protects `POST /v1/payments/transfers` is accepted on quote routes but ignored. Replay protection for ramps is the provider reference instead: if a provider hands back a quote or session reference SDP has already seen, the request returns the existing transfer when every field matches and `409` with `Provider quote/session reference is already bound to a different ramp transfer.` when any field differs. A Lightspark or MoneyGram reference past its expiry returns `409` with `Provider quote/session reference has expired; create a new quote.` Retrying a failed quote request is safe; retrying it with different amounts is not a retry.

## Handle the delivery mode

Every quote carries a `deliveryMode`. It tells you how the end user pays, and it determines which other fields are present. Branch on this field, not on the provider name: BVNK, for one, can return either of two modes.

### `manual_instructions`

The user moves money themselves from their own bank or wallet. `paymentInstructions` says where. Display it and wait for settlement.

The instruction differs by direction. An on-ramp quote tells the user where to send fiat. This is a Lightspark on-ramp quote for 10 USD:

```json
{
  "data": {
    "quote": {
      "id": "Quote:01a0581f-b6cf-5246-0000-f15a37c2912a",
      "provider": "lightspark",
      "status": "pending",
      "deliveryMode": "manual_instructions",
      "paymentInstructions": [
        {
          "provider": "lightspark",
          "accountOrWalletInfo": {
            "accountType": "USD_ACCOUNT",
            "accountNumber": "1111222233331111",
            "routingNumber": "021000021",
            "paymentRails": ["ACH", "WIRE", "RTP", "FEDNOW"],
            "reference": "539d61d1-f4f4-4754-bf11-48fac4d7e045"
          }
        }
      ],
      "totalSendingAmount": 1000,
      "sendingCurrency": { "code": "USD", "decimals": 2, "name": "US Dollar", "symbol": "$" },
      "totalReceivingAmount": 10000000,
      "receivingCurrency": { "code": "USDC", "decimals": 6, "name": "USD Coin", "symbol": "usdc" },
      "feesIncluded": 0,
      "feeCurrency": { "code": "USD", "decimals": 2, "name": "US Dollar", "symbol": "$" },
      "exchangeRate": 1,
      "expiresAt": "2026-08-31T14:04:08.559627Z"
    },
    "transferId": "xfr_69b4436f-877f-4528-a1e1-5755886ac426"
  }
}
```

Amounts on Lightspark quotes are integers in the currency's minor units: `totalSendingAmount: 1000` with `decimals: 2` is 10.00 USD, and `totalReceivingAmount: 10000000` with `decimals: 6` is 10 USDC. The `reference` is what the bank transfer has to carry for the provider to match it.

An off-ramp quote tells the user where to send crypto. The same provider, cashing out 1 USDC:

```json
{
  "data": {
    "quote": {
      "id": "Quote:01a05820-2a47-5246-0000-f7d55dcfb891",
      "provider": "lightspark",
      "status": "pending",
      "deliveryMode": "manual_instructions",
      "paymentInstructions": [
        {
          "provider": "lightspark",
          "kind": "crypto_deposit",
          "destinationAddress": "CtLDz9CE3XKQS18j3EaJnMhJuDhgJRLP9bqHrbkCN3s7",
          "cryptoCurrency": "USDC",
          "network": "SOLANA",
          "accountOrWalletInfo": {
            "accountType": "SOLANA_WALLET",
            "address": "CtLDz9CE3XKQS18j3EaJnMhJuDhgJRLP9bqHrbkCN3s7",
            "assetType": "USDC"
          }
        }
      ],
      "expiresAt": "2026-08-31T14:04:37.687850Z"
    },
    "transferId": "xfr_aa1eecf6-8d7f-46f5-be13-c7b0e3e82b5a"
  }

```

When `kind` is `crypto_deposit`, fund the ramp by sending `cryptoCurrency` to `destinationAddress` from the `sourceWallet` you quoted with, through `POST /v1/payments/transfers` like any other transfer. Do it before `expiresAt`; Lightspark's window is about three minutes. If the off-ramp transfer already carries a deposit instruction of its own (MoonPay sets one through its settlement events), pass the ramp's `transferId` in that transfer request and SDP records the on-chain send on the same transfer instead of creating a second one.

### `hosted`

The provider runs the whole payment journey on its own page. Send the user to `hostedUrl`.

```json
{
  "data": {
    "quote": {
      "id": "ramp_quote_589ffbef-2c4e-4a41-9c33-7a0e1b6f0d21",
      "provider": "moonpay",
      "status": "pending",
      "deliveryMode": "hosted",
      "hostedUrl": "https://buy-sandbox.moonpay.com/?apiKey=pk_test_...&currencyCode=sol&baseCurrencyAmount=30"
    },
    "transferId": "xfr_f335fd8c-91a2-4d6b-8e0f-3b7c2a5d1e90"
  }
}
```

Coinbase quotes use the same mode and add the order economics (`paymentSubtotal`, `paymentTotal`, `purchaseAmount`, `fees`) beside the URL.

### `session_widget`

The provider's widget is embedded in your own interface, authenticated by a short-lived credential. This is a MoneyGram on-ramp quote:

```json
{
  "data": {
    "quote": {
      "id": "a549daae-5300-4361-adfe-53c7650ef805",
      "provider": "moneygram",
      "status": "pending",
      "deliveryMode": "session_widget",
      "sessionToken": "eyJhbGciOiJIUzI1NiJ9...",
      "sessionId": "a549daae-5300-4361-adfe-53c7650ef805",
      "widgetUrl": "https://playground.xramps.moneygram.com/sdk/widget.html?mode=on-ramp",
      "expiresAt": "2026-08-31T15:01:39.000Z"
    },
    "transferId": "xfr_d6e46a12-d3ae-420e-90ea-557990074757"
  }
}
```

Stripe uses the same mode with `clientSecret`, `sessionId`, and `publishableKey` in place of the token and widget URL.

`sessionToken` and `clientSecret` are bearer credentials. Pass them to the widget and don't log or persist them. MoneyGram's session lasts one hour, which is the `expiresAt` on the quote.

Request the quote when the user is ready to pay rather than earlier in your flow. Lightspark and MoneyGram quotes carry `expiresAt`; the other providers' quotes don't expire on SDP's side, but their hosted sessions do on the provider's.

## Track the transfer

Every quote creates a transfer, and `data.transferId` names it. Poll it:

```bash
curl https://api.solana.com/v1/payments/transfers/xfr_69b4436f-877f-4528-a1e1-5755886ac426 \
  -H "Authorization: Bearer sk_test_..."
```

```json
{
  "data": {
    "transfer": {
      "id": "xfr_69b4436f-877f-4528-a1e1-5755886ac426",
      "type": "onramp",
      "direction": "inbound",
      "status": "awaiting_payment",
      "provider": "lightspark",
      "providerReference": "Quote:01a0581f-b6cf-5246-0000-f15a37c2912a",
      "deliveryMode": "manual_instructions",
      "fiatAmount": "10",
      "fiatCurrency": "USD",
      "token": "4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU",
      "amount": null,
      "signature": null,
      "counterpartyId": "cpty_52f96f7f-4e90-47a3-a824-a38f62b86188",
      "rampsMemo": { "orderId": "ord_4821" },
      "createdAt": "2026-08-31T14:01:08.412Z"
    }
  }
}
```

Read it like this:

- `type` is `onramp` or `offramp`; `direction` is `inbound` for on-ramps and `outbound` for off-ramps.
- `providerReference` equals the quote's `id`. It is the key for the cancel endpoint and for provider support tickets.
- `token` is the mint address, not the symbol. `amount` is the crypto amount and is `null` on an on-ramp until it settles; `fiatAmount` is what the user pays or receives.
- `signature` is set only when the ramp settles with an on-chain transaction. Providers that settle off-chain complete with `signature: null`, which is expected, not a failure.

A ramp transfer moves through these statuses:

| `status` | Meaning |
| --- | --- |
| `awaiting_payment` | Created. Waiting for the user to pay (manual instructions) or for the provider to report payment. |
| `pending`, `processing` | The provider has started the ramp but not yet taken payment. |
| `settling` | Payment received; the provider is delivering the other side. |
| `completed` | Done. `amount` (on-ramp) or `fiatAmount` (off-ramp) now reflects what the provider actually delivered. |
| `failed` | The provider reported failure. Terminal. |
| `expired` | The quote lapsed before payment. Not terminal: a late provider event can still move it. |
| `canceled` | You cancelled it. Terminal. |

To find ramp transfers in bulk, list with `category=ramp`, and add `provider` and `providerReference` to look one up by its quote id:

```bash
curl "https://api.solana.com/v1/payments/transfers?category=ramp&provider=lightspark&providerReference=Quote:01a0581f-b6cf-5246-0000-f15a37c2912a" \
  -H "Authorization: Bearer sk_test_..."
```

`providerReference` requires `provider` alongside it. Settlement events also reach the Workflow Builder as `onramp_settled` and `offramp_settled` triggers, which is how to get a webhook to your own system; the API has no ramp-specific webhook subscription. See [Index transfers](/docs/payments/accept-indexing) for pagination and the other filters.

## Cancel a ramp

Cancel a ramp the user abandoned, using the provider and the quote id:

```bash
curl -X POST https://api.solana.com/v1/payments/ramps/transfers/cancel \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "lightspark",
    "providerReference": "Quote:01a0581f-b6cf-5246-0000-f15a37c2912a"
  }'
```

The response is the transfer with `status: "canceled"`. Only `pending` and `awaiting_payment` transfers can be cancelled. Anything past that point, including an already-cancelled one, returns `400` with `Transfer can no longer be canceled (status: <status>).` Treat that as terminal, not as something to retry.

## In the dashboard

The same flow is available without code. In the dashboard, **Payments → Deposit → Deposit with fiat** runs an on-ramp and **Payments → Pay → Pay with fiat** runs an off-ramp. Each wizard walks the steps on this page in order: pick the counterparty, pick the currency pair, compare the live estimates (providers that don't serve the pair are listed as unavailable), clear any provider requirements, then request the quote. Hosted pages and widgets open inside the wizard, and manual instructions render as a funding panel; in sandbox, Lightspark's panel has a **Simulate** button that stands in for the bank transfer.

The wizard creates the same transfer record the API does. It appears under **Payments → Transactions** with the statuses in the table above, and you can cancel a pending one from there. Payments in the dashboard is enabled per organization, so if the section is missing from your sidebar, ask your SDP contact to turn it on. Each ramp provider can also be hidden from the wizards individually; a provider that is hidden there is still served by the API, so what the dashboard offers can be a subset of what the `currency` endpoints report.

## Test without moving money

Which provider environment a request hits is decided by the environment of the API key you call with (sandbox keys start with `sk_test_`, production keys with `sk_live_`), or by the project's environment for dashboard sessions. Sandbox and production share the same host. A provider that isn't configured for the resolved environment returns `503` with `<provider> is not configured for sandbox mode.`

`POST /v1/payments/ramps/sandbox/simulate` pushes a sandbox ramp through its provider-side states so you can exercise your settlement handling without a real payment. It works for Lightspark, BVNK, and Mural, and it returns `403` outside sandbox. The body is provider-specific. For Lightspark, pass the quote id:

```bash
curl -X POST https://api.solana.com/v1/payments/ramps/sandbox/simulate \
  -H "Authorization: Bearer sk_test_..." \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "lightspark",
    "payload": { "quoteId": "Quote:01a0581f-b6cf-5246-0000-f15a37c2912a" }
  }'
```

BVNK takes `{ "counterpartyId", "amount", "fiatCurrency", "cryptoToken", "destinationWallet" }` and Mural takes `{ "counterpartyId", "amount", "fiatCurrency" }` in `payload`. The response is the provider's own simulation record, passed through unchanged. Poll the transfer afterwards; it should reach `completed`.

MoonPay, MoneyGram, Coinbase, and Stripe have no simulate route. Test those through their sandbox widgets and hosted pages.

## Errors and limits

Errors come back as `{ "error": { "code", "message", "details"? }, "meta": { "requestId" } }`. The ones specific to ramps:

| HTTP | `code` | When |
| --- | --- | --- |
| 400 | `UNSUPPORTED_CORRIDOR` | The provider does not serve this fiat and rail pair. `details.supportedProviders` lists the ones that do. |
| 400 | `BAD_REQUEST` | Validation: the rail form in `cryptoToken`, a `destinationWallet` that isn't one of your wallets, a missing off-ramp `fiatCurrency`, or a first-time counterparty on BVNK or Coinbase. |
| 403 | `FORBIDDEN` | Your organization is not entitled to the provider, or you called `simulate` outside sandbox. |
| 404 | `NOT_FOUND` | Unknown `counterpartyId` or transfer. |
| 409 | `CONFLICT` | The counterparty is not provisioned for this provider and direction (Lightspark, Mural on-ramp, BVNK off-ramp), the provider reference is bound to a different transfer, or the quote has expired. |
| 429 | `RATE_LIMITED` | See the limits below. |
| 503 | `PROVIDER_NOT_CONFIGURED`, `PROVIDER_UNAVAILABLE` | The provider has no credentials for this environment, or returned something SDP could not use. |

Estimate and quote carry their own quotas:

| Endpoint | Per API key | Per organization |
| --- | --- | --- |
| `.../estimate` | 30 per minute | 120 per minute |
| `.../quote` | 20 per minute | 60 per minute |

The current allowance is returned on every response in `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`.
