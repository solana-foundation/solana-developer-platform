A **Ramp Quote** moves money between fiat and crypto through a ramp provider. SDP prices it with the provider when you ask, opens a **Payment Transfer** for it, and hands your customer to the provider's own flow (a hosted page or an embedded session) to complete it. SDP then tracks the provider's reports and verifies the crypto leg on chain.

Every quote names a **Counterparty**, the customer the provider runs KYC on, and a custody wallet you control. Provider configuration and capabilities are on [Ramp providers](/docs/payments/ramps-providers).

## Prerequisites

1. **A Counterparty.** Create one with `POST /v1/counterparties`.
2. **The provider's requirements met**, if it has any. Some providers need KYC or bank details collected against the counterparty before they price or accept a quote. Read `GET /v1/counterparties/{counterpartyId}/requirements` with the quote's `provider`, `direction`, `assetRail`, and `fiatCurrency`, plus `destinationCustodyWalletId` for an onramp. While `status` is `collect`, send what it lists with `POST` to the same path. Quote once it's `ready`.
3. **A custody wallet you control**, for the crypto leg: the onramp destination or the offramp source.

## Discovering corridors

`GET /v1/payments/ramps/onramp/currency` and `GET /v1/payments/ramps/offramp/currency` list the fiat and crypto pairs SDP supports, and the providers that cover each one. Which fiat currencies work depends on the provider and the asset, so check here rather than assume.

```bash title="Terminal"
curl "https://api.solana.com/v1/payments/ramps/onramp/currency?source=USD&dest=usdc.solana" \
  -H "Authorization: Bearer sf_..."
```

| Query param | Notes |
| --- | --- |
| `source` | Onramp: fiat currency (ISO code). Offramp: crypto rail (`usdc.solana`, `sol.solana`, …). |
| `dest` | Onramp: crypto rail. Offramp: fiat currency. |
| `provider` | Narrow to one provider. |

`pairs` lists the providers for each source and destination. `providerDetails` gives each provider's support for the direction: amount limits per currency, country coverage, and the entity types it accepts.

## Estimating a rate

`POST /v1/payments/ramps/onramp/estimate` and `POST /v1/payments/ramps/offramp/estimate` preview a rate without creating anything, and need no counterparty or wallet. SDP asks every provider on the corridor and returns one entry per provider in `estimates`. An onramp estimate takes `fiatAmount`; an offramp estimate takes `cryptoAmount`.

<Tabs items={["curl", "TypeScript"]}>
<Tab value="curl">
```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/ramps/onramp/estimate \
  -H "Authorization: Bearer sf_..." \
  -H "Content-Type: application/json" \
  -d '{
    "assetRail": "usdc.solana",
    "fiatCurrency": "USD",
    "fiatAmount": "100.00"
  }'
```
</Tab>

```typescript title="estimate-onramp.ts"

      fiatCurrency: "USD",
      fiatAmount: "100.00",

);
const { data } = await response.json();
// data.estimates: one entry per provider on the corridor
```

Each entry has a `status`:

- `ok`: `estimate` carries `fiatAmount`, `cryptoAmount`, `exchangeRate`, and `fees`, plus `totalFiatAmount` on an onramp. Show it to the customer before they commit to a quote.
- `unsupported`: the provider gives no estimate here. Its rate is known only at quote time.
- `error`: the provider call failed or was refused. An amount outside the provider's range carries `reason` (`amount_below_minimum` or `amount_above_maximum`) and the `limit`.

## Requesting a quote

`POST /v1/payments/ramps/onramp/quote` (fiat to crypto) and `POST /v1/payments/ramps/offramp/quote` (crypto to fiat) create the **Ramp Quote** with the provider you name. Unlike an estimate, a quote needs a counterparty and a wallet, and it opens a record at the provider. The request is the same for every provider: only `provider` changes. A pair the provider doesn't cover returns `400 UNSUPPORTED_CORRIDOR`, with the providers that do in `details.supportedProviders`.

    "provider": "moonpay",

### Request fields

| Field | Required | Notes |
| --- | --- | --- |
| `provider` | yes | A provider from the [capability matrix](/docs/payments/ramps-providers#capability-matrix). |
| `counterpartyId` | yes | An existing Counterparty. SDP resolves the provider's customer and payout records from it, so you don't send them. |
| `destinationCustodyWalletId` (onramp) / `sourceCustodyWalletId` (offramp) | yes | The `id` of a custody wallet you control, as `GET /v1/wallets` returns it. It must be in your API key's wallet scope. |
| `assetRail` | yes | SDP's crypto asset rail: `usdc.solana`, `usdt.solana`, `sol.solana`, and so on. |
| `fiatCurrency` | onramp: yes; offramp: no | Required on an onramp. On an offramp, the provider's default applies when you leave it out (see its page). |
| `fiatAmount` (onramp) / `cryptoAmount` (offramp) | yes | A decimal string greater than zero. |
| `rampsMemo` | no | Up to 20 key/value string pairs (keys up to 64 characters, values up to 256), stored on the transfer for your own reconciliation. |

### The response

The response holds `quote` and `transferId`, the **Payment Transfer** the quote opened. Follow the ramp with [`GET /v1/payments/transfers/{transferId}`](/docs/reference/api/payments/get-payment-transfer). `quote.status` is a snapshot from when the quote was created, and SDP doesn't update it. There's no endpoint to read a quote again.

`quote.deliveryMode` says how to hand the customer to the provider:

| Delivery mode | What to do |
| --- | --- |
| `hosted` | Redirect the customer to `quote.hostedUrl`. |
| `session_widget` | Mount the provider's session with `quote.clientSecret` and `quote.publishableKey`. |

Each provider's delivery mode is in the [capability matrix](/docs/payments/ramps-providers#capability-matrix). An onramp needs nothing more from you: the provider delivers to the wallet, and SDP completes the transfer once it verifies the delivery on chain.

## Funding an offramp

An offramp needs one more call, because you send the crypto. When the provider is ready for it, the transfer moves to `awaiting_payment` and carries `cryptoDeposit`, with the `destinationAddress` and `amount` to send.

Send exactly that with [`POST /v1/payments/transfers`](/docs/reference/api/payments/create-payment-transfer). Set `transferId` to the offramp's transfer, `sourceCustodyWalletId` to the quote's source wallet, `destination` and `amount` from `cryptoDeposit`, and `token` to the quoted asset (its symbol, such as `USDC`, or its mint). The call needs an `Idempotency-Key`, like any transfer, and your API key needs `transfers.execute`.

A deposit that doesn't match the instruction returns `400`, and one for a transfer no longer awaiting payment returns `409`. Sending the same deposit again, under any key, returns the transfer it already funded instead of sending twice.

## Canceling a quote

`POST /v1/payments/ramps/transfers/cancel` cancels the transfer behind a quote while it's still `pending` or `awaiting_payment`, before the customer has paid. Your API key needs `ramp_transfers.manage`.

```bash title="Terminal"
curl -X POST https://api.solana.com/v1/payments/ramps/transfers/cancel \
  -H "Authorization: Bearer sf_..." \
  -H "Content-Type: application/json" \
  -d '{ "transferId": "xfr_..." }'
```

A transfer in any other status returns `400` instead. If its status changes while you cancel, you get `409`. Canceling a canceled transfer returns it again.

## Transfer status

Each quote's **Payment Transfer** has its own lifecycle, apart from wallet transfers ([Verifying a payment](/docs/payments/accept-verification)):

| Status | Meaning |
| --- | --- |
| `pending` | The quote opened the transfer. The customer hasn't paid yet. |
| `awaiting_payment` | The provider is waiting for payment. On an offramp, `cryptoDeposit` says what to send. |
| `processing` | Offramp only: SDP is sending your crypto deposit. |
| `settling` | The provider is processing the ramp, or reported it settled and SDP is verifying it on chain. An offramp also waits here for the provider's payout once its deposit lands. |
| `completed` | Onramp: SDP verified on chain that the quoted asset reached the wallet. Offramp: SDP's deposit is finalized and the provider reported the fiat payout. |
| `canceled` | Canceled with `POST /v1/payments/ramps/transfers/cancel` before payment. |
| `expired` | The checkout lapsed unpaid: the provider expired it, or SDP did after no provider activity. |
| `failed` | The quote failed, the provider rejected or reversed the ramp, or the offramp deposit failed. `error` says why, when set. |

`completed`, `failed`, and `canceled` are final. An `expired` transfer comes back if the provider reports progress, for example when the customer completes an earlier checkout.

A provider's settlement report alone never completes a transfer: missing or mismatched chain evidence keeps it `settling` for review. On an offramp, the fiat payout stays the provider's report, because chain finality proves the crypto deposit, not the bank credit.

## Rate limits

Estimates and quotes have quotas of their own, counted per key (or signed-in member) and per organization. Onramp and offramp share each one. While SDP's counter store is unavailable, both refuse with `503` rather than run uncounted.

| Endpoint | Per key | Per organization |
| --- | --- | --- |
| `.../estimate` | 30 / minute | 120 / minute |
| `.../quote` | 20 / minute | 60 / minute |

## Choosing a provider

Always pass `provider`: SDP doesn't pick one for you. Choose by:

- **Availability:** the providers your organization can use. See [Provider gating](/docs/payments/ramps-providers#provider-gating).
- **Corridor:** currency, country, and entity type, from the currency endpoints above.
- **Environment:** your project's environment picks the provider's sandbox or production mode. See [Sandbox vs production selection](/docs/payments/ramps-providers#sandbox-vs-production-selection).
