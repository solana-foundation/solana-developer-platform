title: Treasury
description: Put your organization's own funds to work from a custody wallet, then track and withdraw them.
---

SDP builds each Treasury transaction, signs it through the wallet's custody
provider, and broadcasts it; the custody wallet holds the shares. To let
customers earn from their own wallets, use
[Embedded Yield](/docs/guides/embedded-yield) instead.

<Callout type="info">
Treasury runs in the dashboard and on internal routes. It is not part of the
partner API, which covers strategies and Embedded Yield.
</Callout>

## Set up the wallet

1. [Create a custody wallet](/docs/guides/setup-wallets) in your project.
   `GET /v1/wallets` returns its `id` (`cwlt_...`), which Earn calls
   `custodyWalletId`, and its `publicKey`.
2. In sandbox, send devnet USDC to that `publicKey` from the
   [Circle faucet](https://faucet.circle.com). Add devnet SOL only when the
   strategy's `feeSponsored` is false; otherwise SDP pays the fees and rent.
3. Give your API key `earn.execute`, `wallets.read` to look the wallet up,
   and wallet access that includes it. SDP checks that access again when it
   signs.

Confirm your organization's and the wallet's eligibility with the provider
for restricted strategies. SDP access authorizes API calls, not investment.

## Deposit

In the dashboard, open **Markets** > **Treasury**, choose a strategy and a
wallet, enter an amount, and review.

Through the API:

1. Choose a strategy from the [catalog](/docs/earn/strategies).
2. [Preview the deposit](/docs/reference/api/earn/create-earn-vault-deposit-preview)
   with `strategyId` and `amount`, and resolve every `blockingIssues` entry.
3. [Create the deposit](/docs/reference/api/earn/create-earn-vault-deposit)
   with `strategyId`, `custodyWalletId`, `amount`, and `minSharesOut` when
   the strategy's `depositSlippage` requires it. Compute the floor from the
   preview's `sharesOut` and `shareDecimals` with the strategy's
   `defaultToleranceBps`, as [Slippage floors](/docs/earn/integration-details#slippage-floors)
   shows.

Send a new random UUID as the `Idempotency-Key`, and save it with the request
body before you send. SDP writes Treasury idempotency keys into each
transaction's onchain memo, so never put customer or order data in one.

```json title="Response (trimmed)"
{
  "data": {
    "positionId": "earn_position_e6caf1cf-1165-4198-b2a9-c8ed258d17d1",
    "movementId": "earn_movement_fc981223-d5b1-4ae9-8356-3b30ea6655ae",
    "status": "submitted",
    "signature": "3cswdmoBwC8fk3sU6AdwvsDQz2MepBkMzURdS1XLzwrFYcPkVvPxCH7TjfgkRbn7nK4zJmKpKiRgiwjj6rzNgEBd",
    "replayed": false
  }
}
```

Save `movementId` and `positionId`. Never send tokens to a strategy's
`providerReference`: it identifies the instrument, not a deposit address.

## Track the deposit

| Task | Request | Stop at |
| --- | --- | --- |
| Track it | [`GET /v1/earn/vault-deposits/{movementId}`](/docs/reference/api/earn/get-earn-vault-deposit) returns `data.deposit`. | `confirmed` or `failed` |
| Check settlement | [`GET /v1/earn/movements?positionId=...`](/docs/reference/api/earn/list-earn-movements) lists the movement. | `finalized` or `failed` |
| Recover a lost response | Retry with the same idempotency key and body, or [list deposits](/docs/reference/api/earn/list-earn-vault-deposits) with `requestId` set to your `Idempotency-Key`, not the `meta.requestId` trace ID. | |

The deposit record keeps the older status names: `pending` means SDP recorded
the deposit but has not yet seen it on the network, which is not a failure,
and `confirmed` covers confirmation and finality. The movements feed tracks
the same deposit through `requested`, `submitted`, `confirmed`, and
`finalized`.

A retry with the same idempotency key and body returns the deposit in its
current state with `replayed: true`. The same idempotency key with a
different body returns `409 CONFLICT`.

After the deposit confirms, refresh
[`GET /v1/earn/vault-positions`](/docs/reference/api/earn/list-earn-vault-positions).
Pass `afterMovementIds` to require a read at or after those movements'
slots; `balanceReadContext` echoes the bound. Show the refreshed position,
never a requested amount added to an old balance. If live values come back
missing, show them as unavailable and read again.

## Withdraw to the same wallet

Read the position's live `withdrawableShares`, then:

| Step | Request | Body |
| --- | --- | --- |
| Choose a route | [`POST /v1/earn/vault-withdrawal-options`](/docs/reference/api/earn/get-earn-vault-withdrawal-options) | `positionId` |
| Preview | [`POST /v1/earn/vault-withdrawal-previews`](/docs/reference/api/earn/create-earn-vault-withdrawal-preview) | `positionId`, `shares` |
| Withdraw instantly | [`POST /v1/earn/vault-withdrawals`](/docs/reference/api/earn/create-earn-vault-withdrawal) | `positionId`, `shares`, and `minAmountOut` when `withdrawalSlippage` requires it |

`withdrawalSlippage` lives on the strategy: match the position's `provider`
and `providerReference` to the catalog, or keep the `strategy.id` from the
deposit response. Compute `minAmountOut` from the preview's `assetsOut` and
`assetDecimals`.

SDP builds and signs the withdrawal when you submit it, and the payout returns
to the same custody wallet. The response nests the record under
`data.withdrawal`. Use a new `Idempotency-Key` for each withdrawal and retry
an uncertain response with the same idempotency key and body.

Track it with [`GET /v1/earn/vault-withdrawals/{movementId}`](/docs/reference/api/earn/get-earn-vault-withdrawal)
until `finalized` or `failed`, or recover it by listing withdrawals with
`requestId`. Its `shares` is what you asked to withdraw; the payout is
`tokenAmount` on the [movements feed](/docs/reference/api/earn/list-earn-movements).

## Asynchronous withdrawals

When the live options offer a solver queue or an operator redemption, create
a withdrawal request. [Withdraw funds](/docs/earn/withdrawals#asynchronous-withdrawals)
explains each route's terms, timing, and statuses.

| Step | Request |
| --- | --- |
| Preview | [`POST /v1/earn/vault-queued-withdrawal-previews`](/docs/reference/api/earn/create-earn-vault-queued-withdrawal-preview) |
| Create | [`POST /v1/earn/vault-withdrawal-requests`](/docs/reference/api/earn/create-earn-vault-withdrawal-request), with an `Idempotency-Key` |
| Track | [`GET /v1/earn/vault-withdrawal-requests/{withdrawalRequestId}`](/docs/reference/api/earn/get-earn-vault-withdrawal-request) |
| Restore | [`GET /v1/earn/vault-withdrawal-requests?settled=false`](/docs/reference/api/earn/list-earn-vault-withdrawal-requests), every page |

Only `fulfilled`, `cancelled`, and `failed` are final, and only `fulfilled`
pays out. Keep tracking a `closedOrUnknown` request.

## Cancel a request

With `earn.manage`, call
[`POST /v1/earn/vault-withdrawal-requests/{withdrawalRequestId}/cancel`](/docs/reference/api/earn/cancel-earn-vault-withdrawal-request)
with a new `Idempotency-Key`. SDP builds and signs the cancellation.

Offer it for a solver queue request only at `expiredCancelable`. An operator
redemption can be canceled while `pending` if its live terms allow it. A
fulfillment can race the cancellation, so refresh first and keep tracking. A
canceled solver request returns the escrowed shares; a canceled operator
redemption leaves the intermediate token instead.
