Embedded Yield lets your customers earn from their own wallets inside your
app. Your backend calls SDP with your API key, your app asks the customer's
wallet to sign, and SDP verifies, broadcasts, and tracks every movement. SDP
never holds the customer's key.

New to Earn? Run the [Quickstart](/docs/earn/quickstart) first, then come
back to build the full integration.

## How the pieces fit

| Part | Does | Never |
| --- | --- | --- |
| Your backend | Holds the API key. Previews, builds, submits, and reads. Decides which customer may use which wallet. | Sends the API key to a browser or mobile app. |
| Your app | Shows quotes and status. Asks the customer's wallet to sign. | Broadcasts the transaction. |
| The customer's wallet | Signs the exact transaction SDP built. Owns the position and receives payouts. | Shares its private key. |
| SDP | Builds each transaction, verifies the signatures, records the movement, broadcasts it, and tracks it to finality. | Holds the customer's key or pools their funds. |

A deposit then runs: your backend builds, your app collects the signature,
your backend submits, and your app shows the result as your backend tracks
it.

## Authenticate on your backend

Create an API key in each project with the grants your integration uses:

| Grant | Allows |
| --- | --- |
| `earn.read` | Strategies, previews, positions, movements, earnings, and withdrawal requests. |
| `earn.execute` | Builds and submits for deposits, withdrawals, and withdrawal requests. Includes `earn.read`. |
| `earn.manage` | Building and submitting a withdrawal request cancellation. Includes `earn.read`. |

`earn.execute` and `earn.manage` do not include each other. The backend
module reads one `SDP_API_KEY`, so give that key every grant you call through
it. See [Manage API keys](/docs/developing-with-sdp/manage-api-keys).

Withdrawals and cancellations stay available after production access is
removed or new deposits are disabled. A suspended organization still cannot
authenticate, and Earn runs only on deployments whose release channel
includes it.

Your API key can read every customer wallet your project has recorded. Before
any request, check that the signed-in customer owns the `ownerAddress` you
send, for example by verifying a message the wallet signed when the customer
linked it. Custody-wallet scopes on the API key do not apply to customer wallets:
the customer's signature authorizes each transaction.

## Get the backend module

The dashboard generates a TypeScript module for a strategy with every call
this guide uses:

1. In the dashboard, open **Markets** > **Embedded Yield** > **Integrate**.
2. Choose a strategy. Only fundable strategies can be selected.
3. Click **Copy all code**, and save it as a server-only file such as
   `earn.ts`. Set `SDP_API_KEY` in your backend's environment.

The module holds the strategy ID and the API URL for the project you
generated it in, so generate it again for production. It needs Node.js 20.18
or later, and `@solana/kit` only for its fee sponsor signer.

| Task | Module function |
| --- | --- |
| List the catalog | `listEarnStrategies` |
| Quote a deposit | `previewEarnDeposit` |
| Build a deposit | `buildEarnDepositTransaction` |
| Collect signatures | `signEarnTransaction`, `createSponsorSigner` |
| Submit a deposit | `submitEarnDeposit` |
| Track a movement | `waitForEarnMovement`, `getEarnMovement` |
| Read balances | `listEarnPositions` (every page), `getEarnEarnings`, `listEarnMovements` (one page per call) |
| Withdraw instantly | `previewEarnWithdrawal`, `buildEarnWithdrawalTransaction`, `submitEarnWithdrawal` |
| Choose a route | `getEarnWithdrawalOptions` |
| Request a withdrawal | `previewEarnQueuedWithdrawal`, `previewEarnParRedemption`, `buildEarnQueuedWithdrawalRequest`, `buildEarnParRedemptionRequest`, `submitEarnWithdrawalRequest` |
| Track requests | `getEarnWithdrawalRequest`, `waitForEarnQueuedWithdrawal`, `listPendingEarnQueuedWithdrawals` |
| Cancel a request | `buildEarnWithdrawalRequestCancellation`, `submitEarnWithdrawalRequestCancellation` |

When SDP refuses a request, a module function throws an `EarnApiError` with
`status`, `code`, `details`, and `retryAfter`. Branch on those, never on the
message.

Prefer raw requests? Every function maps to one endpoint in
[Deposit funds](/docs/earn/deposits) and
[Withdraw funds](/docs/earn/withdrawals).

## Make a deposit

| Step | Module function | Endpoint |
| --- | --- | --- |
| 1. Quote | `previewEarnDeposit` | [`POST /v1/earn/vault-deposit-previews`](/docs/reference/api/earn/create-earn-vault-deposit-preview) |
| 2. Build | `buildEarnDepositTransaction` | [`POST /v1/earn/external-wallet/deposit-transactions`](/docs/reference/api/earn/create-earn-external-wallet-deposit-transaction) |
| 3. Sign | `signEarnTransaction` | In the customer's wallet |
| 4. Submit | `submitEarnDeposit` | [`POST /v1/earn/external-wallet/deposits`](/docs/reference/api/earn/create-earn-external-wallet-deposit) |
| 5. Track | `waitForEarnMovement` | [`GET /v1/earn/external-wallet/movements/{movementId}`](/docs/reference/api/earn/get-earn-external-wallet-movement) |

`buildEarnDepositTransaction` previews the deposit itself when the strategy
needs a floor; call `previewEarnDeposit` too when you want to show your
customer a quote first.

`signEarnTransaction(built, customerSigner, sponsorSigner?)` passes the
base64 transaction to your signer, checks that the signed message is
unchanged, and adds your sponsor's signature when the build named a
`feePayer`. `createSponsorSigner(secretKey, feePayerAddress)` makes that
sponsor signer from your fee payer's 64-byte secret key, the array a Solana
CLI keypair file holds. The Quickstart shows a
[customer signer for a browser wallet](/docs/earn/quickstart#sign-in-your-customers-wallet).

Three rules keep deposits safe:

- **Sign exactly what SDP built.** The wallet must not change or broadcast
  the transaction. SDP refuses a changed one with `400`.
- **Save before you submit.** Store the idempotency key with the signed
  transaction, then submit. After an uncertain response, retry with both
  unchanged; see [Retry safely](/docs/earn/integration-details#retry-safely).
- **Track to the end.** Save `movementId` and track it until `finalized` or
  `failed`.

## Show balances

Read positions for withdrawals, earnings for the totals your customer sees,
and movements for their history. [Balances and earnings](/docs/earn/balances)
covers every field. Two rules matter most:

- Show a missing live value as unavailable, never as zero.
- Read every page of a list. A short list hides money.

## Withdraw

1. Read the position's live `withdrawableShares` with `listEarnPositions`,
   then its routes with `getEarnWithdrawalOptions`.
2. For an instant withdrawal, preview, build, sign, submit, and track, as for
   a deposit.
3. For a solver queue or operator redemption, create a withdrawal request and
   track it to `fulfilled`, `cancelled`, or `failed`.
4. On startup, restore every open request with
   `listPendingEarnQueuedWithdrawals`.

| Step | Module function | Endpoint |
| --- | --- | --- |
| Choose a route | `getEarnWithdrawalOptions` | [`POST /v1/earn/external-wallet/withdrawal-options`](/docs/reference/api/earn/get-earn-external-wallet-withdrawal-options) |
| Withdraw instantly | `buildEarnWithdrawalTransaction`, `submitEarnWithdrawal` | [`POST /v1/earn/external-wallet/withdrawal-transactions`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal-transaction), [`POST /v1/earn/external-wallet/withdrawals`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal) |
| Preview a request | `previewEarnQueuedWithdrawal` | [`POST /v1/earn/external-wallet/queued-withdrawal-previews`](/docs/reference/api/earn/create-earn-external-wallet-queued-withdrawal-preview) |
| Build a request | `buildEarnQueuedWithdrawalRequest` | [`POST /v1/earn/external-wallet/withdrawal-request-transactions`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal-request-transaction) |
| Submit a request | `submitEarnWithdrawalRequest` | [`POST /v1/earn/external-wallet/withdrawal-requests`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal-request) |
| Track a request | `getEarnWithdrawalRequest` | [`GET /v1/earn/external-wallet/withdrawal-requests/{withdrawalRequestId}`](/docs/reference/api/earn/get-earn-external-wallet-withdrawal-request) |
| Cancel a request | `buildEarnWithdrawalRequestCancellation`, `submitEarnWithdrawalRequestCancellation` | [`POST /v1/earn/external-wallet/withdrawal-request-cancel-transactions`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal-request-cancel-transaction), [`POST /v1/earn/external-wallet/withdrawal-request-cancellations`](/docs/reference/api/earn/create-earn-external-wallet-withdrawal-request-cancellation) |

A withdrawal spends shares, not a dollar amount, and a request transaction
is not a payout. [Withdraw funds](/docs/earn/withdrawals) covers each route.

## WisdomTree customer verification (internal, pre-launch)

The backend Moderator onboarding flow uses an existing project-scoped
counterparty as the customer. All endpoints start with
`onboarding/wisdomtree`; reads take `earn.read` and writes take
`earn.execute` plus `Idempotency-Key`.

| Step | Endpoint |
| --- | --- |
| Read the live KYC/KYB form | `GET /v1/earn/onboarding/wisdomtree/forms/{entityType}` (`individual` or `business`) |
| Create KYC or save/submit KYB | `POST /v1/earn/onboarding/wisdomtree/{counterpartyId}` |
| Upload one business document | `POST /v1/earn/onboarding/wisdomtree/{counterpartyId}/documents` |
| Read verification/corrections | `GET /v1/earn/onboarding/wisdomtree/{counterpartyId}` |
| Answer one business correction | `POST /v1/earn/onboarding/wisdomtree/{counterpartyId}/corrections/{reasonId}` |
| Register an active child customer's Solana wallet | `POST /v1/earn/onboarding/wisdomtree/{counterpartyId}/wallets` |

Submit `{ application, documents? }` using the latest form's template and the
applicant's own agreement answers. Business intent is explicit (`draft` or
`submit`); individual KYC submits immediately and is US-only. Document uploads
accept base64 PDF/JPEG/PNG up to 20 MiB decoded and return SDP document IDs;
map those IDs under `documents` using the form's submission keys. Provider
GUIDs and blob paths cannot be supplied by callers.

A business's returned child organization is durably linked to the counterparty.
A retail person's GUID is separate and never turns the moderator into a child.
Only an `active`, still-assigned business child can register wallets on this
rail. Submission is not approval. After answering corrections, submit the same
business again. Unknown create outcomes require operator reconciliation; do
not create a second application. This backend workflow does not enable
WisdomTree surfacing or production deposits.

## Plume provider orders (internal integration)

Plume uses the same strategy catalogue, caller-signed deposit and withdrawal
transactions, positions and movement endpoints as other vault providers. The
provider is staged with money-in disabled pending deployment validation. No Plume
API key is required. Your wallet must pass Plume's Predicate v2 mint eligibility
check; a 403 from its builder means the wallet is not approved.

For a first mint with a separate fee payer, finalize the share token account setup:

1. `POST /v1/earn/provider-actions/external/preparation-transactions` with
   `strategyId`, `ownerAddress`, and optional `feePayer`.
2. Sign the returned action's `transaction` with the owner and optional fee payer.
3. `POST /v1/earn/provider-actions/external/preparations` with `actionId` and
   `signedTransaction`.
4. Poll `GET /v1/earn/provider-actions/{actionId}` until `finalized` or `not_required`, then use the
   normal deposit build and submit flow.

Every POST requires an `Idempotency-Key`. Preserve the key and identical payload
when retrying an uncertain request. The preparation action is durable and can outlive the browser session.
`not_required` means the live account already exists; no setup transaction or
signature is needed. An abandoned unsigned build can be rebuilt under a new key;
reuse its original key to recover an uncertain submit.

Plume mint transactions already contain protocol signatures. Sign the exact
message and preserve every existing signature. Do not replace its blockhash,
change its fee payer, append instructions, or compose a swap into it. Fund USDC
before building the mint. SDP accepts human-readable decimal amounts and converts
them to exact base-unit integers; no fractional base units are rounded.

The withdrawal build accepts optional `redemptionMode: "standard" | "instant"`.
Both modes settle across chains. `instant` uses the provider's available instant
liquidity; it does not mean same-transaction delivery. Neither mode requires a
later user-signed claim. A `confirmed` source movement still awaits delivery.
Poll until `finalized` and inspect `settlementOutcome: "delivered"`; SDP verifies
the destination Solana token credit before reporting fulfillment. A status-indexing
404 remains pending. Output-floor parameters are unsupported for these
cross-chain flows and are refused rather than silently ignored.

A pending standard redemption can be cancelled with
`POST /v1/earn/provider-actions/external/cancellation-transactions`, naming its
`movementId` and optional `feePayer`. Sign the returned transaction, submit it to
`POST /v1/earn/provider-actions/external/cancellations`, and poll the action id.

The cancellation uses the original order's composer. It sets Plume's aggregate
pending amount to zero for that wallet and vault, which can affect other pending
requests. Only a verified full share return closes the selected SDP movement;
partial or aggregated returns remain pending for recovery. A cancelled movement
reports `settlementOutcome: "cancelled"` and zero USDC payout. Already-delivered
USDC cannot be recalled.

These provider-action routes are registered in the internal OpenAPI document.
They remain outside the publishable Earn contract until a named security sign-off
promotes them; Earn itself remains unpublished until PRO-2038. Treasury uses the
custody equivalents, `POST /v1/earn/provider-actions/preparations` and
`POST /v1/earn/provider-actions/cancellations`, under the same project scope.

## Go live

- [ ] Get production access: request mainnet access and switch to your
      production project, as steps 1 and 2 of
      [Go to mainnet](/docs/guides/go-to-mainnet) show. Embedded Yield needs
      no custody provider or wallet funding.
- [ ] Create a production API key with your Earn grants, and regenerate the
      backend module in your production project. Strategy IDs differ per
      environment.
- [ ] Sign with your customer's wallet on `solana:mainnet`.
- [ ] Support deposit floors. Nearly every production deposit requires
      `minSharesOut`. The module sets it from a live preview when the
      strategy's `depositSlippage` asked for one at generation, so regenerate
      it if a build starts requiring a floor.
- [ ] Persist idempotency keys and signed transactions before you submit.
- [ ] Restore open work after every restart: keep tracking each saved
      `movementId` that is not `finalized` or `failed`, and restore open
      requests with `listPendingEarnQueuedWithdrawals`.
- [ ] Confirm investor and wallet eligibility for each strategy you offer;
      see [Strategies](/docs/earn/strategies#confirm-eligibility).
- [ ] Decide who pays fees, and if you sponsor them, bound and monitor your
      fee payer; see [Fees and sponsorship](/docs/earn/integration-details#fees-and-sponsorship).
