# sdp-helius-gateway

Stateless HTTP gateway over the Helius Rings ([zolana](https://github.com/helius-labs/zolana)) Rust
SDK. SDP owns operation state, policy, approvals, custody signing, fee sponsorship and RPC submission;
this service owns everything that touches zolana wire formats and holds nothing durable — no database,
no KMS key, no disk, no cursor.

Scope is the **default ring** only: instruction tags 11 (`DEPOSIT`), 12 (`TRANSACT`) and 13
(`MERGE_TRANSACT`).

Start with [`src/wire/`](src/wire/) — it is the contract, and it documents the invariants callers
depend on.

## Where key material comes from

Not from `sdp-api`. A separate **key authority** (`rings-key-auth`) generates both Rings secrets,
encrypts them into its own database, and is the only service that can decrypt them, under one hard
invariant: **no endpoint anywhere returns key material to its caller.**

For a key-bearing operation, `sdp-api` calls the key authority, which unwraps the material, **attaches
it to the request body, and forwards the request here.** The response travels back the same way.
Keyless operations go from `sdp-api` straight here.

Two consequences shape this crate:

- **There are two callers**, with different privileges — so there are two HMAC secrets, and each route
  is verified against its own caller's secret rather than against "either" (`src/config.rs`).
- **The request body is composed by two services.** `sdp-api` writes `preamble.owner` and the action;
  the key authority writes `preamble.keyMaterial`. Those halves come from different databases, and this
  gateway is the only component that sees both — which is why `KEY_OWNER_MISMATCH` exists in
  `src/error.rs`, and why the viewing-key index is carried as data rather than as array position
  (`IndexedViewingKey`).
- **The secrets are generated by code this repository does not review**, across a language boundary. So
  key widths are checked at the edge and fail as a typed `400` naming the field, rather than surfacing
  as an opaque conversion error inside a handler. `src/validate.rs` owns the four widths and the
  `Validate` trait; every request type implements it, so a new one cannot be added without deciding what
  its validation is.

## Status

`GET /health` is the only route wired up so far. It answers unauthenticated, because a liveness probe
carries no shared secret and requiring one would make an HMAC misconfiguration look like a dead
container instead of failing requests with a clear cause.

The full contract is already here as types in [`src/wire/`](src/wire/), ahead of the handlers that will
consume it. That ordering is deliberate: the contract is the thing SDP builds against and the thing
worth reviewing first, and `wire/mod.rs` carries a module-wide `allow(dead_code)` for exactly as long
as nothing reads it.

Eight endpoints are specified and land behind this one, five of which never see a secret:

| Endpoint | Caller | Key material |
| --- | --- | --- |
| `POST /v1/wallets/register` | `sdp-api` | no |
| `POST /v1/wallets/merging` | `sdp-api` | no |
| `POST /v1/operations/shield` | `sdp-api` | no |
| `POST /v1/transactions/assemble` | `sdp-api` | no |
| `POST /v1/nullifiers/status` | `sdp-api` | no |
| `POST /v1/wallets/sync` | `rings-key-auth` | yes |
| `POST /v1/operations/plan` | `rings-key-auth` | yes |
| `POST /v1/operations/prove` | `rings-key-auth` | yes |

Registration is keyless because a `ShieldedAddress` is built entirely from public halves — the owner's
Ed25519 pubkey, the 32-byte nullifier pubkey and the 33-byte compressed P256 viewing pubkey — so no
component in that path needs a secret, and under the invariant above none of them could have one.

Shield is a single call rather than plan → prove → assemble: a deposit spends no notes, so there is no
input set to pin and no prover to keep away from an expiring blockhash. It is also built entirely from
public address material — the recipient's `ShieldedAddress` is read from the on-chain user registry and
the view tag is `viewing_pubkey.x()` — so it is the second endpoint after `/assemble` that never sees a
secret.

`/v1/nullifiers/status` exists because reconciliation must ask the indexer whether a nullifier already
landed, and the gateway is the only component that speaks to a Helius node; SDP has no Photon client
by design.

## Boot preflight

zolana crates are unpublished and pinned by git revision, so a breaking account-layout change and a
routine patch are indistinguishable from a version number. That makes silent skew the realistic failure
mode, and its symptom would otherwise be a decode error on a user's real operation.

[`src/zolana/preflight.rs`](src/zolana/preflight.rs) moves that discovery to boot. It refuses to serve
if the configured program id is not the one the pinned revision derives PDAs from, or if the
protocol-config account is absent or not exactly 132 bytes. An unreachable RPC is *not* fatal — a cold
start during a blip should not crashloop — so the gateway serves with `protocolConfig: null`, which is
itself the alert. `/health` then reports the snapshot plus the zolana revision stamped in by
`build.rs`, so skew is visible in monitoring.

Each preflight read is bounded in-process. The agave client retries a `429` five times honouring
`Retry-After`, so a single read can otherwise take around 13 minutes without ever being unreachable.

## Running it

```bash
cargo test                 # 14 unit + 1 contract test
cargo clippy --all-targets --locked -- -D warnings
cargo fmt --check

HELIUS_GATEWAY_HMAC_SECRET_SDP_API=local-development-only-sdp-api-secret-32b \
HELIUS_GATEWAY_HMAC_SECRET_KEY_AUTH=local-development-only-key-auth-secret-32 \
SOLANA_RPC_URL=https://api.devnet.solana.com \
PHOTON_URL=http://127.0.0.1:8784 \
PROVER_URL=http://127.0.0.1:3001 \
cargo run
```

Both secrets are required at startup and both must be at least 32 bytes. With Cloud Run IAM absent —
local compose, self-hosted, integration tests — the HMAC is the only thing between a request and a
decrypted nullifier key.

CI runs the same three commands in
[`.github/workflows/rust-gateway.yml`](../../.github/workflows/rust-gateway.yml), which is
path-filtered to this directory. It is the crate's only correctness gate: Biome ignores `.rs`, the
`typecheck` job resolves this directory and then no-ops via `--if-present`, and CodeQL has no Rust
analysis.

## Findings

### The zolana git dependency needs 21 version pins

A git consumer is the resolution root and does **not** inherit upstream's
`[workspace.dependencies]` table — such an entry only constrains crates that reference it via
`workspace = true`. Resolving fresh produced 47 trait-mismatch errors inside `solana-message`, all of
the form `Address: SchemaWrite<__WincodeConfig> is not satisfied`.

The cause is a `wincode` 0.5/0.6 split across the agave wire graph:

| crate | wincode 0.5 era | wincode 0.6 era |
| --- | --- | --- |
| `solana-address` | 2.6.1 | 2.7.0 |
| `solana-reward-info` | 6.2.0 | 6.3.0 |

Two `=` pins live in `Cargo.toml`; the other 19 are `cargo update --precise` alignments to upstream's
own `Cargo.lock`, which is a known-good resolution. Aligning to it rather than forward-resolving guards
against a serialization mismatch, which in a ZK protocol is silent and catastrophic.

**This means `Cargo.lock` is load-bearing and 19 of the pins are invisible in `Cargo.toml`.** A bare
`cargo update` undoes them and reintroduces the 47 errors. CI passes `--locked` everywhere for that
reason.

**Upstream fragility worth reporting:** zolana pins `solana-reward-info = "=6.2.0"` for exactly this
reason but only `solana-address = { version = "2.6", … }` — a caret range that admits 2.7.0. Only
their committed lockfile is holding their own build together; `cargo update` on their side reproduces
this failure.

## Omissions

- **No SDP-side env vars added** to `apps/sdp-api/src/types/env.d.ts`, `scripts/secret-keys.mjs`,
  `turbo.json` or `packages/sdp-env-config/src/fields.ts`. Those variables configure SDP's client for
  this gateway, which does not exist yet; declaring keys nothing reads would be speculative. The
  gateway's own variables are read by this process and belong in compose and Cloud Run config, not in
  the API's `Env` interface.

## Open questions

1. **Does a proof survive a borsh round trip?** Serialize a `TransactIxData` from `prove_transact`,
   store it, deserialize, assemble, and check the proof still validates. Nothing in the pipeline derives
   `serde`, so if borsh does not round-trip, the gateway cannot be stateless on a scale-to-zero
   platform. The stateless design depends on this, and it is unverified.
2. **Can transfer and withdrawal pin their input set?** `MergeParams` has
   `inputs: Option<Vec<[u8; 32]>>`; `TransferParams` and `WithdrawalParams` have none. Without pinning,
   a lost response leads to a re-synced wallet selecting *different* notes, producing disjoint
   nullifiers, and **both transactions landing — the recipient paid twice.** Determine whether
   `ConfidentialTransfer::new(address, inputs, payer)` is a workable fallback.

## Upstream asks

- **P0: add `inputs: Option<Vec<[u8; 32]>>` to `TransferParams` and `WithdrawalParams`.** One field.
  Without it no integrator can build an idempotent custodial flow in any language.
- Pin `solana-address` exactly, as `solana-reward-info` already is. See the finding above.
